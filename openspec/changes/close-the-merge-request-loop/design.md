## Context

A ship ends at a commit. From there the owner's question is one sentence: does this merge request need a person, or can it merge? Today the answer is "a person, always", for three independent reasons the explore brief established and the proposal summarises:

- `/interlock:mr` publishes a verdict but runs no review on the merge request's diff, posts nothing but the verdict block, fixes nothing, replies to nothing, and never pushes. The review skills review a diff before the merge request exists and write their record nowhere the verdict reads.
- A lean ship (the default) leaves `review` and `handoff` null in its evidence file, and the file is refused whole the moment any later commit lands, so the run's own record is lost to exactly the merge requests that needed a fix.
- `risk.class` reads the change's artifact prose, and the words an honest design uses to name a policy file, a stage marker or a user's identity flow read `high` or `critical`, so this repository's changes read amber on that signal whatever the diff touched. Ledger decision D1 of `label-and-harden-the-merge-verdict` recorded the question and left it open.

Constraints that shape every decision below:

- Thresholds live in the CLI. The round cap, the bands and every gate verdict are code; prose reads them from `interlock limits` or lets the command decide.
- `bin/interlock` is under a shipped-file size pin with about five kilobytes of headroom, and `lib/run.mjs` has less. New surface goes in new modules.
- Every skill instruction is pinned by token in `test/skills.test.mjs`; the `mr` skill alone has forty pins, and the loop must keep them all.
- Degradation is spoken. A path that cannot run (no graph, no profile, GitLab lines nobody exercised) says so in output, never silently.
- The verdict is a claim about one commit. Every input the loop hands it must be bound to the head it describes, or refused out loud.
- `openspec/` is written through the CLI; this change edits living specs only through its delta specs.

## Goals / Non-Goals

**Goals:**

- After a ship, one person-invoked command carries the branch to a merge request whose verdict reflects a review of that merge request's diff, the fixes made on it, and the replies that say what each finding became.
- The verdict can read `MERGE` for a change of this repository when the evidence supports it: the loop produces the review, verification and confirmation evidence a lean ship did not, the run's record survives the fix commits, and the risk signal reads the diff rather than the prose.
- Every new instruction in the skills is a token a test asserts; every new CLI behaviour is a scenario a test runs.

**Non-Goals:**

- A CI job that re-assesses on push. The loop runs where the person invoked it.
- Reading platform review comments written by people into findings. The loop replies to the comments it posted; a person's comment is a person's business.
- A live read of the platform's branch rules (required checks, approvals). `--required` stays the caller's declaration, and the verdict says so (D15): `MERGE` is a statement about the local signals, not that a ruleset, required approvals, code owners, a draft state, unresolved review threads or a merge queue would let the merge request merge.
- Resolving review threads. The findings and the replies are issue comments; a platform rule that requires conversation resolution reads nothing from them, and the block's legend line (D15) names that among the rules the verdict does not read.
- Stacked or dependent merge requests. The loop assesses one merge request against the target the platform reports; `--base origin/<target>` pointing at a parent merge request's branch is not a trunk check, and a `MERGE` on the top of a stack says nothing about the stack merging to trunk.
- Any change to the strict tail's single-worker review inside a ship run. The loop is the merge request's review; the run's review stays what it is.
- Merging, approving or requesting changes. The skill still never does any of these.
- Exercising the GitLab lines. They are written from documentation and marked so, as the three platform recipes already are.

## Decisions

### D1. The loop lives in `/interlock:mr --review`, not in the ship run

**Decision.** The review, remediation, reply and re-assessment loop is a new section of the `mr` skill, entered only with `--review`, after the merge request exists. The ship run is unchanged; its summary gains one line naming the next step.

**Why.** The loop needs the merge request: a comment to post to, a head the platform holds, checks to wait for. A ship run ends before any of that exists, and a run that pushed and opened merge requests would turn an uninterrupted local loop into one that talks to a remote on every close. The `mr` skill already holds the platform detection, the pipeline reader and the assessment; the loop is its missing middle.

**Alternatives.** (a) A `--push`/`--mr` tail on `interlock ship`: rejected, it moves remote I/O into the run and still needs everything `mr` has. (b) Copying the user-level `mr-code-review` and `mr-blast-radius` skills into the repo: rejected, they are GitLab-only, use a different severity scale, run no skeptics, write nothing `interlock review` or `merge-confidence --review` can read, and fail four existing skill pins. Their two ideas worth keeping, the blast-radius lens and the reply-table shape, are absorbed (D10, D4).

**Invocation stays person-only.** `disable-model-invocation: true` is kept. The loop pushes, posts and commits on a remote the person owns; a model deciding on its own to start it is the one thing the owner asked never to happen. `Agent` is added to `allowed-tools` because the skill now spawns a fixer and a confirmation worker (D5, D7), and the Agent pin requires it.

**Preconditions are code (added after the PR #23 review).** Where the loop changes state (stage, revert, commit, push), its precondition is a CLI answer or a fixed, pinned shell line, never a step the model reasons out. That covers a clean tree (`interlock mr tree-check`), a fixer result that accounts for every finding (`interlock mr fixer-result`), the stop rule as a `STOP:` prefix, the protected list computed from a copy of the profile, a NUL-separated revert under `--literal-pathspecs`, and a head the platform holds. The ship loop puts its own preconditions in `lib/run.mjs` for the same reason.

### D2. One pass of the loop, and the order its evidence is produced in

With `--review`, after §1–§3 of the skill and the push/create step (D11), the skill runs, in this order:

1. **Review the merge request's diff.** Invoke `/interlock:review-code <change> --base origin/<target> --out .claude/ship/mr/review-r0.json`. The pipeline is the existing one: seven bundled dimensions plus `blast-radius` (D10), two skeptics per blocker and warning, `interlock review --findings --verdicts --changed --base --metrics <change> --head <sha> --out <file> --json`, `interlock gate`. The record lands in a file (D3) bound to the head it reviewed.
2. **Post the findings.** `interlock mr comment --review .claude/ship/mr/review-r0.json --head <sha> --round 0` renders the comment; the skill posts it with `gh pr comment <n> --body-file -` (GitLab: `glab mr note <iid> --message`). An empty surviving list still renders a one-paragraph comment saying the review ran on `<sha>` and found nothing: the trail is the point.
3. **Fix, round by round.** For `r = 1, 2, …` while `interlock mr remediate-brief --review .claude/ship/mr/review-r<r-1>.json --round <r> --change <change> --head <sha> --pr <n>` exits zero (D5): spawn one fixer subagent with the printed briefing. Then stage everything the fixer left (`git add -A`) and classify every path that differs from HEAD, staged or not: `git diff --cached --name-only | interlock mr test-paths --changed -`. Revert every protected path it names with `git restore --staged --worktree --source=HEAD -- <paths>`, which also removes a protected file the fixer created, and print `REMEDIATION TOUCHED TESTS: <files> — reverted` (D6). If nothing is staged after that (`git diff --cached --quiet` exits zero) the fixer changed nothing the round can keep: commit and push nothing, render `interlock mr replies --before review-r<r-1>.json --after review-r<r-1>.json --head <sha>`, in which every finding reads `open`, post it, and end the loop, because pushing nothing is not a round. Otherwise commit `fix(review): answer the PR #<n> review round <r>` with a `Refs: #<n>` trailer; push; re-review the new head with `review-code … --out .claude/ship/mr/review-r<r>.json`; post the reply table `interlock mr replies --before review-r<r-1>.json --after review-r<r>.json --head <sha>` renders (D4). Beside the push the skill says, once, what the push did on the platform: a new commit dismisses the stale approvals a ruleset marks, and takes the merge request out of auto-merge or a merge train; the loop's verdict does not restore them, and the skill does not re-request a review. When the rounds are over and this pass created the merge request as a draft (D11), it is marked ready here, after the last push: `gh pr ready <n>` (GitLab: `glab mr update <iid> --ready`, not exercised), whatever the verdict will be. Ready says the loop is finished; the verdict and the labels say the rest.
4. **Confirm the scenarios.** `interlock mr conformance-brief <change> --changed <files> --base origin/<target> --head <sha>` prints the checklist briefing (D7); one worker answers it into `.claude/ship/mr/handoff.json`, with the head beside the counts (D3).
5. **Verify the head.** `interlock verify plan --context final --changed <files> --json`, each step through `interlock verify exec`, then `interlock verify judge … --head <sha> --json > .claude/ship/mr/verify.json` (D3). When the plan ran a coverage step, `interlock verify coverage --base origin/<target> --json > .claude/ship/mr/coverage.json` produces the coverage figures for this head and the assessment passes them with `--coverage`. When the verdict skipped coverage as not configured, no coverage file is written and that skip is what the coverage signal reads; the loop produces no coverage figure any other way (D8).
6. **Wait for the platform's checks.** `gh pr checks <n> --watch`. GitLab: poll `glab ci get --merge-request <iid> --output json` until the merge request's head pipeline leaves `running` and `pending` (not exercised); `glab ci status --live` is not used, because it follows the branch pipeline, and a branch pipeline is not the pipeline GitLab's merge check reads. Whatever the wait reports, the pipeline input is then re-read from the platform's own document exactly as §4a does today, and the suite pins that the §4a pipe sits after the wait line and before the assessment, so the pipeline sha is the pushed head's and never the pre-fix commit's.
7. **Assess.** The existing `merge-confidence` lines gain `--review .claude/ship/mr/review-r<last>.json --verify .claude/ship/mr/verify.json --handoff .claude/ship/mr/handoff.json` beside `--run .claude/ship/merge-confidence.json`, and `--coverage .claude/ship/mr/coverage.json` when that file exists. `<last>` is the round of the last re-review, the record whose `head` is the pushed head; the suite pins the literal `review-r<last>.json`, not the `review-r` prefix, so a line that passed round 0 after a fix commit fails the suite rather than being refused by the command at run time. Then the description, labels and the confidence comment as today.

**Why this order.** Review before fix so there is something to fix; re-review on the *pushed* head so a reply never cites a commit the platform has not seen (PR #22's reply tables cite `c028d7d`, which a later force-push removed); confirmation and verification after the last push so they describe the head under assessment, and each bound to it (D3); checks last because they are the slowest and the only input the loop cannot produce itself, and the pipeline document read after them so it names the head the checks ran on.

**Evidence home.** Everything the loop produces lives under `.claude/ship/mr/` (gitignored with its parent): `review-r<n>.json`, `dimensions-r<n>.json`, `remediate-r<n>.json`, `handoff.json`, `verify.json`, `coverage.json` when coverage ran. The pipeline input stays at `.claude/ship/pipeline.json` because three pins name that path. A new pass of the loop clears the directory first, so a stale `review-r2.json` from last week cannot outlive a fresh `review-r0.json`.

### D3. `interlock review --out <file> --head <sha> --dimensions <file>`, and every loop record bound to its head

**Decision.** `interlock review` gains `--out <file>`, writing the same JSON `--json` prints (created directories included); `--head <sha>`, recorded in the output as `head`; and `--dimensions <file>`, a JSON record `{ selected, ran, unavailable, skipped: [{ name, reason }] }` the `review-code` skill writes beside its findings file, validated by `lib/review-core.mjs` (arrays of strings; a `skipped` entry carries a string `name` and `reason`; anything else exits 1 naming the fault, and nothing is written to `--out`) and recorded in the output as `dimensions` with `completed: true`. Without it the output carries no dimension record and `review.ran` reads it green with the `dimensions-unrecorded` flag, which is what every review the skill produced has read until now: the run's review step was the only writer of that record, so the loop's own review would have carried the flag on every pass and a skipped dimension would never have reached the verdict.

`merge-confidence` refuses any of `--review`, `--verify` and `--handoff` whose record carries a string `head` that is not the head under assessment, says so on standard error in the words the `--run` refusal uses ("it describes another commit"), and reads that input's signals as with no file. A record with no `head` is read as today. `interlock verify judge` gains `--head <sha>`, recorded on the verdict as `head`. The conformance briefing (D7) names the head and tells the worker to write it as `head` beside the five counts; the command strips it from the counts as it strips `verdictsRequired`. The handoff's binding is as good as the worker's compliance, which is why the spec reads an unbound handoff as before rather than refusing it, and why the briefing names the head twice.

**Why.** The `mr` skill's delivery requirement forbids passing "a review file left in the working directory by any other means". The loop needs to pass its own records, so each file must be able to say what it is a record of. A head in the record is how the command, not the skill's discipline, tells a review of this head from last Tuesday's; the same holds for the verdict and the handoff, which a second pass, a split session or a hand-run of `merge-confidence` could otherwise pass from the previous head unnoticed. Binding all three is what the constraint above ("every input the loop hands it must be bound to the head it describes, or refused out loud") already requires, and it closes ledger D4.

**`review-code` gains `--base <ref>` and `--out <file>`** as pass-throughs to its `interlock review` line, which already carries `--base`, and writes the dimension record before that line whether or not `--out` was given, so a standalone review stops carrying the `dimensions-unrecorded` flag too. The skill's argument hint grows accordingly.

### D4. One finding identity, shared by the comment and the replies

**Decision.** `lib/findings.mjs` exports `findingKey(finding)`: the trimmed `file`, a NUL separator, and the title normalised by trimming, collapsing internal whitespace to one space, case-folding, and stripping trailing `.`, `:`, `;` and `!`. `findingId(finding)` is `F-` plus the first eight hex characters of the SHA-256 of that key. `interlock mr comment` labels every finding with its id; `interlock mr replies` computes, for each surviving finding of the record before a round, `fixed` when no finding in the record after the round shares its key, else `open`; and `new` for each key in the after-record that the before-record lacks. Both read through the one function, so a title a re-reviewer re-cased or re-punctuated is the same finding.

**Readers enumerated.** The identity has three readers after this change: `mr comment`, `mr replies`, and the reply-table pin in the skill test (which asserts ids, not titles). `lib/review-core.mjs` keys skeptic verdicts to findings by exact title narrowed by file and is **deliberately left on that form**: a verdict is produced in the same session from the same list, its existing fileless-match asymmetry is a documented choice, and widening it to case-folded titles could make a verdict adjudicate a finding its skeptic never saw. That reader is named here so the omission is a decision, not a gap.

**Alternatives.** Keying by title alone: rejected, two files can carry the same title (and did in PR #22's reviews). Keying by line: rejected, a fix moves lines. Hashing the description: rejected, a re-reviewer rewrites descriptions freely.

### D5. A fix-only briefing, and an independent re-review

**Decision.** `lib/prompts/mr-remediate.mjs` exports `assembleMrRemediatePrompt({ change, round, plan, head, prNumber, protectedPaths, resultPath })`. It is built from the same `planRemediation(findings, { round, limits, band })` plan the ship loop uses, under the ship loop's own stop rule, so the round cap is `interlock limits`' `remediationRounds` and nothing else. That rule, as `run remediated` applies it: round 1 fixes every surviving blocker and warning; a later round is briefed only while a blocker survives, otherwise the plan is rebuilt at the verdict round (`remediationRounds + 1`), which plans no fix; and the planner refuses any round beyond the verdict round. `interlock mr remediate-brief` exits 1, with the planner's reason on standard error and nothing on standard output, whenever the plan it holds has nothing to fix or halts: an empty surviving list, suggestions only, the verdict round (the reason names the round and the published cap), the halt (unresolved blockers after the cap) and a refused round all end the loop the same way. One rule, so the loop neither briefs a fixer after the budget nor stops a round early. Unlike the run's briefing it carries **no re-review section**: the fixer fixes, writes `{ ok, fixed: [ids], notFixed: [{ id, reason }] }` to `.claude/ship/mr/remediate-r<n>.json`, and stops. The re-review is a fresh `review-code` pass on the pushed head, by reviewers who did not write the fix.

**Why.** A fixer that re-reviews its own work is the arrangement the ship run uses because a run has one worker per stage; the merge request has no such constraint, and the owner's question ("is it fixed?") is better answered by a reviewer who did not make the fix. It also makes the reply statuses honest by construction: `fixed` means "the independent re-review on the pushed head did not raise it", not "the fixer said so".

**The briefing's rules, pinned by token:** fix the root cause of each listed finding; never edit a path in the protected list (the test guard's predicate, D6); do not commit, the skill commits; write the result file. The briefing names the head and the merge request so a fixer cannot mistake which diff it is on.

### D6. Test edits are detected with the guard's predicate, reverted, and spoken

**Decision.** The test-path predicate and the profile readers (`isTestPath`, `loadTestProfile`, `testRootsFromProfile`) move from `hooks/_shared.mjs` to a new `lib/test-paths.mjs`; the hook module re-exports them so `guard-tests` is unchanged. `interlock mr test-paths --changed <files|-> [--json]` prints `{ protected, unprotected, profile, reason }`. The skill hands it every path that differs from HEAD, staged or unstaged: it stages the fixer's whole tree with `git add -A` and pipes `git diff --cached --name-only` into `--changed -`, because `git diff --name-only` lists unstaged paths only and a fixer that staged a test file would otherwise commit it unseen. The protected paths are reverted with `git restore --staged --worktree --source=HEAD -- <paths>`, which restores a tracked file and removes one the fixer created. With no profile, `protected` is empty and `reason` says `no test profile at .claude/testing/profile.json — nothing is protected`; the skill prints that line as `TEST PATHS UNKNOWN: …` and reverts nothing.

**Why.** The guard that denies test edits during a run's `remediation` stage does not run here: there is no stage marker after a close. The same rule must hold for the loop's fix rounds, and the only honest way to hold it is with the same predicate, exposed, over the same set of paths the commit would carry. Reverting (rather than refusing the round) keeps the non-test part of the fix; speaking it keeps the reader informed; a missing profile fails open as every guard does, out loud.

**Alternative.** Importing `hooks/_shared.mjs` from `lib/`: rejected, `lib/` does not depend on `hooks/`, and the predicate is a decision, which is what `lib/` is for.

### D7. A confirmation briefing from the CLI's own checklist

**Decision.** `interlock mr conformance-brief <change> --changed <files> --base <ref> --head <sha>` runs the gather `interlock conformance <change> --changed --living --base --json` already performs and prints a briefing asking one worker to confirm each scenario C1..Cn and each living requirement L1..Ln against the diff, answering with the five keys `HANDOFF_RESULT_SCHEMA` already defines (`scenariosChecked`, `scenariosUnconfirmed`, `requirementsChecked`, `requirementsUnconfirmed`, `detail`) and `head`, the sha the briefing names (D3), into `.claude/ship/mr/handoff.json`; the schema gains `head` as an optional string. When the living list could not be built (a base that names no commit, no graph) the briefing still lists the scenarios, says why the living list is absent, and asks for the same five keys with the two requirement counts reported as zero. With nothing to confirm at all it prints nothing, says so on standard error, and exits 0. The skill passes that file with `--handoff`; the verdict's denominators stay the command's own counts, as today.

**Why.** The two conformance signals are unobserved after a lean ship for want of a handoff, and a lean ship is the default. The strict tail's worker answers exactly this checklist; the loop asks the same questions of the merge request's head, through the same CLI, so the two cannot drift. Learnings, the manual test plan and the decision whether a test plan is needed stay with the run's handoff: they are not merge evidence.

### D8. The run's evidence file carries its run record to descendant commits

**Decision.** `readRunEvidence(file, { change, headSha, base, descendsFromRecordedHead })` returns `{ usable: true, evidence, dropped: [] }` when the head is the recorded commit, as today. When `descendsFromRecordedHead` is `true` and, with a base, the file's base equals the merge base, it returns `{ usable: true, evidence: { run }, dropped: [{ key, reason }, …], carriedFrom: file.headSha }`, dropping `review`, `verify`, `handoff` and `coverage` with the reason that each describes the tree at the recorded commit. The fact is three-valued: `false` is a commit git says is not an ancestor, and the file is refused with the existing "another commit" reason; `null` is an ancestry git could not decide (a commit missing from a shallow clone, no git at all), and the file is refused with its own reason, that the ancestry could not be decided, so the reader is not told the file names another commit and sent to the wrong repair. With no base given, or any other mismatch, the file is refused whole, as today. `bin/interlock` computes the fact with `git merge-base --is-ancestor <recorded> HEAD` through a helper that maps exit 0 to `true`, exit 1 to `false` and anything else to `null` with the git failure on standard error (the existing `isAncestorOfHead` folds the third case into `false` for the coverage baseline, where that reading is documented; the run-record read needs the distinction, so it gets a helper that keeps it), prints one standard-error line naming the commit the record was carried from and one per dropped key, and passes the run record on. The module stays free of git.

**Why.** The run record is evidence about the run (halts, prompts, unticked tasks), and a fix commit the loop made on top of the run's commit does not change what that run did. The tree-bound entries are evidence about a tree the head no longer is, and the loop produces fresh review, verification and confirmation records for the head (D2). Coverage is replaced only where the loop produced figures: when the profile configures coverage, `verify coverage` for the head (D2 step 5); when it does not, the final verdict's coverage-not-configured skip is what greens the signal. Nothing else can, an unobserved coverage signal reads `HUMAN`, and the descendant scenario names that condition rather than claiming the loop replaces every dropped entry. The merge-base condition keeps the existing rule that a branch of five hand commits is not a reviewed branch: only a branch that starts where the run started carries the record. No base is still never taken from the file.

**Alternative.** Having the loop's close rewrite `merge-confidence.json` for the new head: rejected, the file is the run's statement and nothing but a run's close writes it.

### D9. The risk signal reads touched paths at merge

**Decision.** `classifyRisk(input, { allowedClasses, pathsOnly })` gains `pathsOnly`: when true, artifact text is not read even if supplied, and the severity path rules are evaluated over the changed paths that are neither documentation (`isDocsPath`) nor test paths (`TEST_PATH`); the docs-and-tests-only rule and the unmatched-source rule are unchanged, and no paths at all still fails closed to the unclassifiable class. `readRisk` in `lib/merge-confidence.mjs` calls it with `pathsOnly: true` and no artifacts. `interlock risk`, the continuity gate and the spec-stage checkpoint keep reading both sources.

**Why.** The living requirement's own title says "computed over the touched paths"; the body said paths and artifact text, and the code followed the body. At the spec stage, prose is all there is and keyword classification is the right fail-closed read. At merge there is a diff, and a word in a design document is not a touched surface. Skipping documentation and test paths in the severity rules closes the second half of the same hole: `test/spine/review-policy.test.mjs` is not a policy surface, and `test/payments/charge.test.mjs` is not a payment surface. One consequence is named here so it is a decision and not a surprise: a signal that has only a text rule cannot fire at merge. `idempotency` is the one such signal, so a diff whose only critical clue was the word in a design document floors at the unmatched-source class at merge; the word was never evidence about the diff, and the spec-stage checkpoint still reads it. This resolves ledger D1 of `label-and-harden-the-merge-verdict`; the resolution is recorded `agent_resolved` in this change's ledger and the owner can reverse it by one line in `readRisk`.

**Alternative.** A per-repository allow-list of prose words: rejected, it moves a threshold into prose and asks every repository to curate it.

### D10. An eighth review dimension: `blast-radius`

**Decision.** `skills/review-code/dimensions/blast-radius.md` asks: for every exported symbol or shared value the diff changes, who calls it outside the diff (`interlock-graph consumers <symbol>`), what behaviour those callers see before and after, data and concurrency effects, and whether the change can be rolled back alone. It reports findings in the existing schema under `dimension: "blast-radius"` with the existing severity rubric, and only when a caller outside the diff would observe a change. It runs whenever `.claude/graph/graph.json` exists; without one the skill prints `BLAST RADIUS SKIPPED: no graph at .claude/graph/graph.json — run /interlock:graph`, runs the other dimensions, and records the skip in the dimension record it hands `interlock review --dimensions` (D3) as `skipped: [{ name: "blast-radius", reason }]`. `review.ran` adds the `blast-radius-skipped` flag beside `domain-skipped` for that entry: a flag lowers the score and moves no band, because the other dimensions still ran with their rubrics, and the verdict's reader sees that the eighth did not instead of a green signal that says nothing. The error line for an unknown dimension name now says `list the eight`.

**Why.** The one thing the user-level `mr-blast-radius` skill did that nothing here does is ask "who else does this touch" with the graph in hand. It belongs as a dimension, not a skill: it then gets the skeptics, the policy, the quality band and the metrics for free, and its findings reach the verdict through the same file. Its skip reaches the verdict the way the domain skip does, for the same reason: a line printed in the session is spoken degradation for the person watching, and a flag on the block is spoken degradation for the reviewer who was not.

### D11. `--create` pushes, and with `--review` creates a draft; nothing else pushes

**Decision.** With `--create`, the skill pushes before creating: `git push -u origin HEAD` when the branch has no upstream, `git push` when it has one and the local head is ahead. The loop's fix rounds push their own commits. With `--create --review` the merge request is created as a draft (`gh pr create --draft`; `glab mr create --draft`, not exercised) and marked ready after the loop's last push and re-review (`gh pr ready <n>`; `glab mr update <iid> --ready`, not exercised; D2 step 3), whatever the verdict: code owners are not requested on a draft, so they are asked once, for the head they will read, and no approval is dismissed by a fix commit the loop was always going to make. With `--create` and no `--review` the merge request is created ready, as today. Without `--create` the skill still never pushes a branch that has no merge request; the stop message becomes "re-run with `--create`" and says nothing was pushed. The existing paragraph telling the reader to push when the pipeline input describes another commit stays, because that case (a hand commit after the loop) still exists. The push, the draft and the stop line are a requirement with scenarios in the delivery spec, and `git push -u origin HEAD` is pinned apart from a round's `git push`, so the create-time push cannot be dropped while a round's push keeps the suite green.

**Why.** The owner's ideal starts with "pushes to a new feature branch and creates the merge request". A merge request cannot be created without a pushed branch, so `--create` pushing is not a new decision, it is the one the flag always implied. It is a new remote side effect all the same, which is why it gets its own requirement rather than a sentence in this file.

### D12. The ship summary names the step

**Decision.** `lib/receipt.mjs` prints `NEXT — push the branch and open the merge request: /interlock:mr --create --review` on a close that did not halt and recorded a commit, directly before the archive reminder. A halt, a close with no commit, and leftovers print no such line. Existing contract lines are untouched.

**Why.** The only shipped text naming `/interlock:mr` is one line in the commit skill; the summary a person actually reads after a ship ends in "Do not start another ship run", which answers a question nobody asked and leaves the one they did unanswered.

### D13. `interlock mr` in its own module

**Decision.** `lib/mr-cli.mjs` exports `mrCommand(io, root, positional, flags, json)` and the five subcommands (`comment`, `replies`, `remediate-brief`, `conformance-brief`, `test-paths`); `bin/interlock` adds one import and one dispatch line, on the `noteCommand` precedent, and `interlock mr --help` is printed from the module. The subcommands read files through the same `readJsonInput` helpers the rest of the CLI uses and refuse a review record without `surviving` in the words `merge-confidence --review` uses.

**Why.** `bin/interlock` has about five kilobytes under its pin and the help text alone for five subcommands would spend most of it. A `-cli` module is the established shape for a command family with its own I/O.

### D14. This repository's `REVIEW.md` names its CI as always-human

**Decision.** `REVIEW.md` gains `## Always Human Review` with `.github/workflows/`. The `policy.humanPaths` signal already reads the list from the base ref; a merge request that edits a workflow reads `HUMAN` by policy, with the path in the evidence.

**Why.** A workflow edit can grant a token or a trigger no diff reviewer sees; the user-level `review-context` primer called this "CI trust". The verdict already has the mechanism; the repository had not used it. The list is not widened further: this repository has no `CODEOWNERS`, and `.github/` outside `workflows/` holds issue templates, a pull request template and agent prompts, none of which gates a merge.

### D15. The block says what `MERGE` is not

**Decision.** The `--markdown` block carries, in every verdict, one legend line: `MERGE` means every local signal is green; it is not a statement that the platform's branch rules would let the merge request merge, and the line names required checks, required approvals, code owners, a draft state, unresolved review threads and a merge queue as the rules the verdict does not read. `lib/merge-confidence.mjs` renders it beside the verdict line. The `mr` skill's paragraph that already says it never merges says the same in one sentence, pinned by token.

**Why.** The owner's question is "can it merge?", and the verdict's word answers it in the platform's vocabulary. Every platform has gates the loop never reads (non-goals), a fix push clears some of them (D2 step 3), and a merge queue re-runs required checks on a sha that is not the head. A reader who takes `MERGE` as the platform's answer is misled by the one line this design controls, so the line says what it is. No live read of the rules is added.

## Risks / Trade-offs

- **[`bin/interlock` size pin]** Three small additions (one dispatch line, `review --out/--head`, the per-key `--run` warnings) land in a file with about five kilobytes of headroom → every other byte of new surface lives in `lib/mr-cli.mjs` and `lib/prompts/mr-remediate.mjs`; the size test runs in the first wave, not the last.
- **[GitLab lines unexercised]** `glab mr note`, the `glab ci get --merge-request` poll, `glab mr create --draft`, `glab mr update --ready` and GitLab's lack of a comment-reply primitive are written from documentation → marked "not exercised" in the skill and docs exactly as the existing GitLab recipes are; the GitHub lines are the ones this repository runs.
- **[A reply that cites a commit the platform never saw]** → the re-review and the reply table are computed only after the push, from the pushed head, and the reply header carries that sha; pinned by token.
- **[Carrying `run.integrity` across fix commits could read as "the fixes were a clean run"]** → the carry-over is spoken on standard error with the commit the record came from, every tree-bound entry is dropped with its reason, and the loop's own fresh review, verification and confirmation records replace three of them; coverage only where the loop produced figures (D8); the signal's meaning (the run that made the ancestor commit was not degraded) is stated in the spec's rationale.
- **[The loop's review record carries no dimension record, so `review.ran` can never be clean and a skipped dimension is invisible]** → `interlock review --dimensions` (D3) records what the skill selected, ran and skipped, and the `blast-radius-skipped` flag (D10) carries the skip to the block; the standalone `review-code` gains the same.
- **[A stale `verify.json` or `handoff.json` from the previous head passes unnoticed]** → both are head-bound (D3); the handoff's binding depends on the worker writing `head`, so the briefing names it twice and the spec says an unbound handoff is read as before, not refused.
- **[`MERGE` is read as the platform's answer]** → the block's legend line and the skill's sentence (D15) say what the verdict does and does not read; nothing in the loop approves, resolves a thread or re-requests a review.
- **[A fixer that edits tests to pass]** → `interlock mr test-paths` with the guard's predicate, revert plus banner; with no profile, nothing is protected and the banner says so rather than pretending.
- **[The loop re-posts on a re-run]** A second `--review` pass posts a new round-0 comment → acceptable: each comment names its head and round, and the directory is cleared per pass; telling a fresh round from comments already on the merge request is the non-goal "reading people's comments".
- **[Widening `fixed` to a normalised title merges two distinct findings in one file with titles that differ only in case]** → the key keeps the file, and a re-reviewer who raised both would raise both again; the transform-boundary scenario in the spec pins the exact normalisation.
- **[D1's resolution changes a signal's answer for every merge request of every repository]** → recorded in this change's ledger as `agent_resolved` with the reversal named (`pathsOnly: false` in one call site); the spec-stage classifier is untouched, so the checkpoint still reads prose.
- **[Round cap exhaustion with open blockers]** → the loop ends when `remediate-brief` exits 1; the last reply table shows what stayed `open`, the verdict reads the surviving blocker red and `BLOCK` is the honest answer. No prose number, no re-argument.

## Rollout

No data moves and no file format changes shape: `interlock.merge-evidence/1` is read with one more accepted condition; a review record gains an optional `head` and an optional `dimensions` record from the skill; a verification verdict and a handoff gain an optional `head`; the `--markdown` block gains one line. Rollback is removing `--review` from an invocation; the skill without it behaves as 1.8.0 does, except that `--create` pushes and the block carries its legend line. Ships from 1.8.0 that left an evidence file keep working, and a file written before `head` existed in any record is read as before. The living specs change through this change's delta specs at archive time, and docs 01, 07, 12 and 15 change in the same commit as the code they describe.
