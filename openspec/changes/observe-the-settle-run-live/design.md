## Context

`hooks/mod.mjs` is the plugin's hooks module. It runs inside the Claude Code engine with no Node, reaches the world only through `$`, and draws two runs today: the ship run (`/interlock-meter`, from the CLI's step records) and the spec run (`/interlock-spec`, from the lines the spec flow runs). Both obey one rule: the module shows what the CLI already said, counts what the engine already counted, reads the clock, and decides nothing. Every word on a pane is a CLI field, an engine field, or a clock reading; degradation is spoken; no threshold lives in the module.

The settle loop (`skills/settle/SKILL.md` §5–§11) is the third long-running flow and the only one with no meter. A pass runs a review-code fan-out (dimension reviewers, two skeptics), posts a comment, runs fix rounds (a CLI-briefed fixer, a result check, a commit and push, a re-review, replies), marks the PR ready, confirms scenarios with a conformance worker, verifies the head, waits for the platform's checks, assesses merge confidence and publishes. The real pass on PR #25 (2026-10-26, lean depth) took 26m 39s; its fixer ran 10m 45s and its conformance worker 4m 05s, with nothing on screen but the transcript. The explore brief (`.claude/handoff/explore-observe-the-settle-run-live-20261026-184512.md`) holds the keyed-line inventory, the engine's event shapes and the pin checklist this design relies on.

Constraints that shape the design: the engine's spawn event carries no effort field; the module's static pins (`test/spine/mod-pins.test.mjs`) fix its allowed calls, hooked event names, one status composer, the `deny` and `complete` word rules and the Node-free import walk; `bin/interlock` is 173 bytes under the shipped-file size edge; the role keys the meter reads (`roles.review-dimension`, `roles.review-skeptic`, `settle-fixer`, `settle-conformance`) are the contract of the living `openspec/specs/spawn-routing/spec.md`, and this change modifies neither it nor `review/review-depth`, `review/settle-loop` or `review/merge-confidence`.

## Goals / Non-Goals

**Goals:**
- Draw a live `/interlock:settle --review` pass as a grouped timeline: review (dimensions, skeptics, the review record, the comment), each round (brief, fixer, result, commit and push, re-review, replies, or the STOP line), ready, conformance, verify, checks, merge confidence, publish, drift — with clock readings and durations.
- Show, per spawned agent, its role, the model requested, resolved and served, the effort the CLI routed for its role and the effort the engine reported per step, its requests, tokens, duration and the host's end reason.
- Keep the one-status-line rule: a live run outranks a finished one (D5).
- Speak every degradation: a spawn matching no source, a routing line not yet seen, a result the skill redirected to a file, a routing banner.
- Pin the whole guarantee statically: role sources, skill lines, module calls and words.

**Non-Goals:**
- A standalone `/interlock:review-code` run outside settle (D18, pending).
- Any change to a skill's prose, to the CLI, to `types/index.d.ts`, or to the ship meter's agent tally.
- A timer, a quiet word, a price or cost figure, a verdict of the module's own.
- Reading any file under `.claude/ship/settle/` from the module.

## Decisions

**D1 — Roles are read from the prompt's first source line against four pinned sources.** `noteSpawn` already receives the spawn input and result; the settle module's `roleOf(prompt)` reads the prompt's lines from the top and stops at the first line that matches a source, each match anchored at the line's start after whitespace and covering the whole sentence, never a substring inside a line. The scan does not stop at line one because `skills/review-code/SKILL.md` §2 prepends a repo's `REVIEW.md` prose to each reviewer's instructions as a delimited block, so in a repo that has one a dimension reviewer's first line is the policy, not its brief. The two CLI-printed sources are the whole prompt (the CLI's `briefing` field), so they are tested against the first non-blank line only and win over the other three: a fixer brief that quotes a finding's text can never be read as a skeptic. The sources: `# Dimension: <words>` (a dimension reviewer, the words kept as the brief wrote them), `You are a skeptical code reviewer.` (skeptic, refute), `You are an independent reviewer giving a second opinion.` (skeptic, second opinion), `Fix round <r> for change "<c>", … at head <sha>.` (the fixer of round r) and `Confirm change "<c>" against its diff at head <sha>.` (the conformance worker). The first two sources are bundled brief files and review-code's own blockquotes handed over verbatim (`skills/review-code/SKILL.md:56,113,118`); the last two are printed by `lib/prompts/settle-remediate.mjs:101` and `lib/settle-cli.mjs:851`. Alternatives: an Agent `description` grammar (rejected: the description is free text the model types, and the grammar would be a prose instruction with no code behind it) and a CLI-emitted marker for every role (rejected: two roles already have one, the other two would need skill edits for no gain).

**D2 — Effort is shown by source and labelled.** The spawn event has no effort field (`claude-code.d.ts:261-408`). The module keeps the `model`, `effort` and `banners` of every `interlock routing` line that crosses in the pass — the role listing (`roles.review-dimension`, `roles.review-skeptic`, `review.skeptics`, `depth`) and the per-role lines (`settle-fixer`, `settle-conformance`) — and draws each group's figure as `routed <model> · <effort>`; before any routing line has crossed the group reads `routed: not seen`. Beside it, each agent row carries the engine's own `effort` from its `turn.step` input as `step <level>` (D23). A banner the routing line printed is repeated verbatim in the pane's banners area. Nothing is compared and no mismatch word is drawn: both figures are facts the reader can set side by side.

**D3 — Three model figures, each from its own event.** Requested: the spawn input's `model`, or its `parentModel` drawn as `inherit` when the call named none. Resolved: the spawn result's `model`. Served: `usage.model` from each `turn.step` result, kept as the distinct values seen, as the ship meter's `models[]` does. The string is drawn as the engine gave it, alias or id; which spelling the host uses for a routed alias is the probe task's finding (D17), not a design assumption.

**D4 — Live only on a settle load that carries `--review`.** `observeLoad` already reads the first word of a submitted prompt and the skill a Skill call names (`hooks/mod.mjs:566-578`). A settle reader in the pure module, `settleLoad(name, args)`, returns `settle` when the plugin's settle skill is named and the arguments contain the word `--review`, `review` when `interlock:review-code` is named, else `null`; the existing `skillRole` and its pinned nulls are untouched. A `--create`-only load draws nothing, as the living settle-loop requirement makes `--review` the loop's only entry. The load is passed on exactly as it came.

**D5 — Status line precedence: a live run outranks a finished one.** `setStatus` composes, in order: `run.phase === 'live'` → the ship position; else a live spec → the spec line; else a live settle → `interlock settle <change> #<pr>: <group> · <figure>`; else a checkpointed spec → the spec line; else a done settle → the settle line; else nothing. The session this meter serves is spec, then implementation, then `/interlock:settle --review` in one conversation, and a spec run holds its checkpoint until `clear`, `resume`, `fork` or a ship launch: with a checkpoint ranked above a live settle, the status line would read `interlock spec: <change> · checkpoint` for the whole pass. A ship launch during a settle run takes the line and leaves the settle record and pane alone; there is no hand-over, because settle does not lead into ship. The composer stays the module's one `$.ui.status(` call.

**D6 — Ends.** The run moves to `done` at the `interlock drift --changed` line alone, the settle skill's last step (§11), which runs on every pass. The labels line is not an end: it runs before drift (§9b), it does not run at all when the head moved or the assessment stopped, and §9c's `merge-confidence … --markdown | gh pr comment` and §10's comments cross after it. The labels, label-removal, label-names and late markdown lines are `publish` rows (D14). A keyed line after `done` changes nothing and is named once on the debug log. `done` keeps the status words D25 gives (the merge-confidence group's last words) and the pane until a classic session-start event whose source is `clear`, `resume` or `fork`, which resets the settle record in `endRunAtBoundary` beside `run` and `spec`; `startup` and `compact` leave it. A second settle load in the same session starts the record over and says so once on the debug log, as the spec meter does.

**D7 — Redirected results are drawn as the command word and the exit code.** `interlock verify plan|judge|coverage` send stdout to a file in the skill's own lines, and a model may redirect `merge-confidence --json` too. The module reads no settle file; a keyed line whose result carries no stdout is drawn as its word, its exit code and `result not seen (redirected)`. The skill documents that a `judge` exit 1 with a verdict is a halt, so the exit code is the CLI's contract, not a guess. A CLI `--out` for `verify judge` would be a follow-up change to the living `review/settle-loop` spec.

**D8 — Pipe stages are split by the settle reader.** `argvOf` stops at the first unquoted `|` (`lib/spec-meter.mjs:101-139`), which hides `interlock settle tree-check` behind `git status …`, `gh pr comment <n>` behind `interlock settle comment …`, and `interlock pipeline` behind `gh pr view <n> …`. `settleLines(command)` applies `segmentsOf`, then splits each segment at unquoted `|` and at `$(` — including a `$(` inside double quotes, because the GitLab lines are written `glab mr note <iid> --message "$(interlock settle comment …)"` — and keys every stage by its own first words, so the interlock stage and the `gh`/`glab`/`git` stage are both read. The body of a quoted heredoc (`<<'EOF'` … `EOF`) is one argument and is never re-split. The PR number is taken from whichever stage carries it.

**D9 — Unattributed spawns are spoken, not named.** A spawn during a live settle run whose first line matches no source is drawn under the current group as `<subagentType> · unattributed` with its engine figures (models, step effort, requests, tokens, duration, end reason). The Agent call's `description` is never drawn: it is neither a CLI field nor an engine count.

**D10 — No skill prose changes; the role sources are pinned.** A spine test reads the first line of each of the eight `skills/review-code/dimensions/*.md`, the two skeptic blockquotes' first sentences in `skills/review-code/SKILL.md`, the first line `assembleSettleRemediatePrompt` prints and the first line `conformanceBriefCommand` prints (both called through the real modules), and asserts `roleOf` classifies each as its role, and classifies one composed prompt (a delimited `REPOSITORY REVIEW POLICY` block followed by a dimension brief) as that dimension, as `skills/review-code/SKILL.md` §2 composes it. Neither skeptic sentence is pinned today (`test/skills.test.mjs:2108-2240`); from this change a reword fails the suite instead of emptying a group silently. A settle skill-lines pin, modelled on `test/spine/spec-meter.test.mjs:575-625`, splits each fenced `interlock`, `gh`, `glab` and `git` line of `skills/settle/SKILL.md` and each fenced `interlock` line of `skills/review-code/SKILL.md` with `settleLines` itself and checks every stage: a stage whose first word is `interlock` SHALL have a `settleLineKind`, never an allow-list entry, so a new `interlock` verb cannot hide behind an allowed `git` or `gh` prefix; a non-`interlock` stage is keyed or matches one of these written-down prefixes: `git status`, `git rev-parse`, `git diff`, `git add`, `git fetch`, `git log`, `git remote`, `git --literal-pathspecs restore`, `gh pr view`, `gh pr create`, `gh pr comment`, `gh label create`, `glab mr view`, `glab mr create`, `glab mr note`, `glab mr update <id> --description`, `gh pr edit <id> --body`, `gh pr checks <n> --required`, `cat <<` (the heredoc carrier of a description), and `rm -f .claude/ship/settle/` (the `|| rm -f .claude/ship/settle/coverage.json` fallback of §6's coverage line, which the `||` split leaves a stage of its own). The test's list is this list, entry for entry; a stage the skill adds is a line here and a line there, in one change.

**D11 — No timer.** The ship meter's interval is pinned to a live ship run (`openspec/specs/hooks/ship-meter/spec.md:294`). The settle pane redraws on each Bash result and on each `turn.step` and `turn.complete` of a settle agent; a running fixer's elapsed figure advances on its own steps, and the row's last clock reading shows when it last did. No `quiet <n> min` word.

**D12 — A separate agents tally.** `settle.agents` is a map keyed by `agentId` holding `{ role, group, round, requested, resolved, served[], stepEffort, firstStepEffort, requests, sums, firstAt, endAt, durationMs, reason }`, filled from `noteSpawn`, `turn.step` and `turn.complete` under a settle gate (`settle.phase === 'live'`) that sits beside, not inside, the ship gate. `run.agents`, `agentOf` and `addUsage` are untouched; the token fields and figure formatters are shared.

**D13 — `interlock-settle`, registered after `interlock-spec`.** `SETTLE_PANE = 'interlock-settle'` is declared in the module as the pure module exports it, with the same constant pin as `SPEC_PANE`; the command's description is "Open the Interlock settle meter: the live /interlock:settle --review run, its review, rounds, agents and verdict". The four registration enumerations (`test/mod/meter.test.ts:282,289`, `test/mod/session-start.test.ts:105`, `test/mod/spec-meter.test.ts:209`) gain the fifth name last. What the validator records for the shipped module (`npm run validate`, 2026-10-27), which the spec's static-pin scenario names:

**D14 — Group labels are the settle skill's section words, and one table says which line opens which.** `review`, `round <n>`, `ready`, `conformance`, `verify`, `checks`, `merge confidence`, `publish`, `drift`, held in one `GROUPS` table in `lib/settle-meter.mjs` beside the keyed lines. The record holds one open section; a line either opens a section or appends to the one open. Sections only move forward in the table's order: a line whose kind opens an earlier section appends to the section already open (so §9c's late `merge-confidence --markdown` row lands in `publish`).

| section | opened by | also appends here while it is open |
|---------|-----------|------------------------------------|
| `review` | the run's first keyed line, Skill load or spawn | review-code's lines and the `interlock review --out …review-r0.json` record; `interlock settle comment --round 0`; dimension and skeptic spawns |
| `round <r>` | `interlock settle tree-check` after `review-r<r-1>.json` has crossed, or `interlock settle remediate-brief --round <r>` when no such tree-check did | the brief, `interlock routing settle-fixer`, the fixer spawn, `fixer-result`, `test-paths`, `git commit`, `git push`, the nested review-code lines and its dimension and skeptic spawns (the round's re-review), `interlock review --out …review-r<r>.json`, `interlock settle replies` |
| `ready` | `gh pr ready <n>` / `glab mr update <iid> --ready` | — |
| `conformance` | `interlock settle conformance-brief`, `interlock routing settle-conformance` | the conformance worker's spawn |
| `verify` | `interlock verify plan\|exec\|judge\|coverage` | — |
| `checks` | `gh pr checks <n> --watch` / `glab ci get --merge-request <iid>` | — |
| `merge confidence` | `interlock pipeline`, `interlock merge-confidence <c> … --json\|--markdown` | — |
| `publish` | `gh pr edit --add-label\|--remove-label`, `glab mr update --label\|--unlabel`, `interlock merge-confidence --label-names` | any later `merge-confidence` row |
| `drift` | `interlock drift --changed` | — |

A line with no round of its own (`tree-check` before any review record, `surface`, `domain-context`, `routing`, `gate`, `test-paths`, the nested review-code Skill load) appends to the section open. A `git commit` or `git push` outside a round (§4's create path) passes through unread. An unattributed spawn joins the section open. No other label word exists in the module.

**D15 — Toasts.** Four: the `STOP: …` line of `remediate-brief` (its stderr text, verbatim); the merge-confidence verdict and score (`merge-confidence: HUMAN 58`); a settle agent's `turn.complete` whose `reason` is not `answer`, in the host's word (`<role>: aborted`), raised inside a try as the ship meter's turn-end toast is; and the unplaced-open toast when the pane's unasked open is declined. Agent rows end with the host's reason word, never a tick or a verdict.

**D16 — Changelog under `## [Unreleased]`.** The top heading today is `## [1.10.0] - 2026-10-26`; the changelog test accepts an Unreleased heading. The version is bumped at release time, not here.

**D17 — Fixtures with provenance.** Task 1 captures, through `scripts/host-probe.mjs`, one general-purpose Agent-tool spawn made with `model` and `effort` parameters and its `turn.step` and `turn.complete` events, and copies the Bash results the kit needs from the PR #25 pass records under `.claude/ship/settle/` (a `remediate-brief` JSON, a `fixer-result` line, a `review` record, a `merge-confidence` JSON, the `pipeline` text line), re-run through `node bin/interlock` where the stdout form is needed. Each JSON carries `_provenance` and `test/fixtures/mod/settle-run.mjs` mirrors them, deep-equalled in `mod-pins` as `spec-run.mjs` is. Until the spawn capture lands, the kit drives the module with the Explore capture's shape plus `model` and `subagentType: 'general-purpose'`, which the engine's declared types permit.

**D19 — Non-interlock keyed lines.** Besides the `interlock` lines, the settle reader keys `git commit` (the `-m` message's first line drawn) and `git push` (exit code), both inside a round only; `gh pr ready <n>` / `glab mr update <iid> --ready`; `gh pr checks <n> --watch` / `glab ci get --merge-request <iid>` (drawn `background` when the Bash input ran in the background, else the exit code); `gh pr edit <n> --add-label …` / `glab mr update <iid> --label …` (the label names drawn) and `gh pr edit <n> --remove-label …` / `glab mr update <iid> --unlabel …` (drawn `removed <names>`); and the `gh pr comment <n>` / `glab mr note <iid>` stage, read for its pull request number only. Every other Bash line is passed through at the first line, its result unread.

**D20 — Rounds and the review record.** The current round is the open `round <r>` section of D14, opened by the round's own `tree-check` (which crosses before its `remediate-brief`) or by `remediate-brief --round <r>`; `fixer-result --round <r>` and `comment --round 0` name theirs; `interlock review … --out …/review-r<n>.json` belongs to round n (n = 0 is the review group's record; n ≥ 1 is round n's re-review row); `settle replies` belongs to the current round, never to its `--after` file's suffix, because the nothing-to-keep reply of round r is written `--before review-r<r-1> --after review-r<r-1>` (`skills/settle/SKILL.md` §5c). The `interlock review` result is read for `counts`, `dimensionStats`, `head` and `dimensions.{ran,skipped,depth}`; `dimensions.completed` is never read, so the module's `complete` word pin extends to the pure module.

**D21 — The nested review-code skill is part of the settle run.** A Skill call naming `interlock:review-code` while a settle run is live changes no section: the first one (§5a) lands in `review`, which is already open, and every later one (§5c's re-review, once per round) lands in the round already open, so a re-review's fan-out is never drawn back in `review`. Review-code's own lines (`interlock surface`, `interlock domain-context`, `interlock routing --json`, `interlock review`, `interlock gate`) are keyed by the settle reader for as long as the settle run is live. The same load with no settle run live starts nothing (D18 keeps a standalone review-code run out of scope).

**D22 — Agents join the group that is current when they spawn.** Dimension and skeptic roles join the section open (D14): `review` before the first round opens, the open round's re-review after; the fixer joins the round its first line names; the conformance worker joins `conformance`; an unattributed spawn joins whatever group is current. Each group row shows `<k> spawned · <m> <reason>` counts from the engine's events.

**D23 — Step effort is the latest value, with the first kept.** The agent row draws `step <latest>`; when an agent's first and latest step levels differ it draws `step <first> → <latest>`. The engine declares the level rewritable per step, so one value per agent would hide a change.

**D24 — Narrow panes fold the agent rows.** The pane reads the engine's `bodyColumns` from its draw props, as the wave board does; below 110 columns (the width at which the engine seats an unasked pane) an agent row keeps role, served model, duration and reason and drops the requested → resolved and token columns. Both surfaces draw the same keyed lines by field.

**D25 — The settle meter's words.** The header reads `interlock settle — <change> · PR #<n> · <depth> · head <sha7> · <elapsed>`; `<depth>` is the routing listing's `depth` or the review record's `dimensions.depth`, and reads `depth: not seen` before either. The status line reads `interlock settle <change> #<n>: <group> · <figure>`, where the group is the section open and the figure is the group's last CLI words or, while one or more attributed agents of the group run, `<k> live · <role> <elapsed> · <requests> req` for the longest-running attributed agent (`<k> live` is left out when k is 1). Unattributed spawns (D9), including children a fixer spawns, are counted in their group's row but never take the status figure. `publish` and `drift` never retarget the status line: from the merge-confidence group on, the line keeps that group's last words, so a finished pass reads its verdict and score (or the `(unparsed)` or exit-code row when the assessment drew none). The dimensions row draws the routing listing and the engine's count as two labelled facts, `review dimensions <names> · <k> spawned`: the listing is the depth's always-on set, and conditional dimensions (domain, blast-radius, devops, security) spawn without appearing in it. Examples from the PR #25 pass, whose routing line printed `review dimensions: language, technical-lead` and whose review record ran four: the dimensions row `review dimensions language, technical-lead · 4 spawned`; the status lines `review · 4 live · language & framework 2m 10s · 14 req`, `review · 6 raised · 0 dismissed · 6 surviving`, `round 1 · fixer 6m 10s · 18 req`, `round 1 · 1 fixed, 0 not fixed`, `round 2 · STOP`, `merge confidence · HUMAN 58`.

**D26 — Repeated lines append; nothing is one slot per kind.** The spec meter keeps one slot per kind; the settle record keeps rows in the order they cross, because the pass runs the same command more than once by design: `merge-confidence --json` (verdict and score) then `--markdown` (§6b, §6c; the exit code), `tree-check` once per round, `interlock routing` once per role. A later row never replaces an earlier one. `interlock merge-confidence --label-names --json` (§9b, when the assessment stopped) is its own row in `publish`, drawn from `labels.verdictNames` and `labels.scorePrefix`; it carries no verdict field and is never drawn `(unparsed)`.

**D27 — Both Bash-hook branches feed the settle reader.** The Bash hook returns early on its `!watching()` branch when no ship run is live and the spec reader declined the line (`hooks/mod.mjs:2031-2032`). A settle pass is exactly that case, and `interlock gate` and `interlock drift` are spec-meter kinds that `specReader` declines once the spec run is at its checkpoint. So `settleLines` is read before that early return whenever the settle run is live, independently of the spec reader's answer, and again on the watching branch, so a settle line that crosses after a ship launch still files. Each reader files into its own record; neither one's answer gates the other.

## Risks / Trade-offs

- [The host may spell the requested model as an alias and the resolved as an id] → the three figures are labelled by source and drawn as given; D17's capture settles the spelling before the kit test is written.
- [A model redirects a line the design expects on stdout] → the row reads `result not seen (redirected)` with the exit code; nothing is read from disk.
- [Per-review versus per-finding skeptics are indistinguishable from the first sentence] → the skeptics row carries the engine's spawn count and the routing listing's `review.skeptics` word.
- [Replies and comment markdown are piped into `gh`] → the round row carries `fixer-result` and re-review counts; replies and comment rows carry exit codes.
- [A model skips §11, so the drift line never crosses] → the run stays live until the boundary or the next settle load; the status line still reads the merge-confidence group's last words (D25), so nothing reads finished that did not finish.
- [A prompt that is not a settle role quotes a dimension heading or a skeptic sentence as a whole line] → it is attributed to that role; the CLI-printed sources win on the first line, and the dimension and skeptic sources are whole-line matches, so a quote inside a sentence never matches.
- [`gh pr checks --watch` never returns a tool result] → the checks row reads `background`; the `pipeline` text line later carries the counts.
- [A subagent raises no `turn.step` for a while] → the elapsed figure holds at the last reading, which the row shows as a clock time, so a frozen figure is visible as such.
- [The `complete` word pin now covers the pure module] → the reader never names `dimensions.completed`; the kit asserts the word appears nowhere in the pane.
- [Four registration enumerations and three living hooks specs move together] → one section of tasks owns all of them; `mod-pins` fails loudly if the order drifts.
