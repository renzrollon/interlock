### ↩️ Rollback

A revert is safe for data. No receipt, outcome or trajectory schema gains or loses a field (D8). The 1.15.0 strings (`push: removed …` rows, degradations without `PUSH FAILED`) are text that 1.14.0 never parses. A revert restores `notifyTimeoutMs`, the options and the hook together. **Three exceptions.** A person who followed the Upgrading note and removed the saved topic (D9) gets no push after a revert until they save it again, and the restored doctor row says `skip`. A revert ships as a new release: the 1.15.0 tarball and its `release` commit, both without `CHANGELOG.md`, stay published. A close replayed after a revert returns the stored copy at `LAST_CLOSE_PATH` unchanged, so a run closed under 1.15.0 with `--notify` replays its `push: removed` row once.

### ✅ Manual checks for UAT

1. **Upgrade with a saved topic (B1):** on a machine where 1.14.0 has a saved `ntfy_topic`, install the 1.15.0 bundle and start a session in an OpenSpec repo. The session starts with `interlock preflight OK`, with no option prompt and no hook error in `claude --debug`. The plugin settings show no Interlock options. `grep -c NTFY "$CLAUDE_ENV_FILE"` prints `0`. The file holds only the PATH line and `INTERLOCK_PLUGIN_DATA`, and `.claude/ship/preflight.json` is rewritten.
2. **Close on every path (B2):** run four closes: one ship to completion, one `interlock run close --halt "uat"` mid-run, one `run close` in a repo with no `.claude/ship/run.json`, and one with that file replaced by `{}`. Exit codes are 0 / 1 / 1 / 1. The first two remove `.claude/ship/<change>/stage.json`, and the last one reads as a foreign manifest and records nothing. No summary has a `push:` row. The clean run says `No degradation banners`, and its trajectory `run-receipt` has no `PUSH FAILED`. Repeat the halted close with `--notify`: same exit, the same banners, and one `push: removed — interlock sends no notifications` row.
3. **The notify command (B3):** with `INTERLOCK_NTFY_TOPIC=<a test topic>` exported, `interlock notify checkpoint demo` prints `checkpoint: demo — waiting for review; nothing is sent` and exits 0, and nothing arrives on the topic. Its `--json` is `{"sent":false,"reason":"nothing is sent: interlock sends no notifications"}`. `interlock notify --title x` prints the removed line and exits 0, and `interlock notify checkpoint ""` exits 1. Run `/interlock:spec` to its checkpoint: the spec meter shows the checkpoint reached. `which -a interlock` lists the plugin's `cli/` first, or note which older CLI shadows it.
4. **Driver skew (B4):** close a run started by a 1.14.0 `workflows/ship.js` on the 1.15.0 CLI. It closes with its usual exit and the retired row. Ship one change with 1.15.0 and a topic exported in the shell: nothing arrives on the topic, and the summary has no `push:` row.
5. **Lows (B5–B9):** `interlock doctor --json` has no check with id `notify`. `interlock limits` has no `push timeout (ms)` row, and `interlock limits --json | jq .limits.notifyTimeoutMs` prints `null`. `npm pack --dry-run` lists no `CHANGELOG.md`. The `INTERLOCK_PLUGIN_DATA` line in `$CLAUDE_ENV_FILE` is single-quoted and equals `$CLAUDE_PLUGIN_DATA`.
