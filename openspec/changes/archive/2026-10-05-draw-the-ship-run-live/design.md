## Context

See proposal.md for the motivation. The wiring as it stands, and the facts the module can stand on:

- **Every CLI call of a ship run is one Bash tool call inside a ping subagent.** `cli()` in `workflows/ship.js` builds `interlock <argv> --results <path> --json` (argv tokens shell-quoted) and asks an `interlock:ping` agent (tools `Bash`, `Read`, `Write`) to run exactly that line and copy its stdout verbatim into `cliStdout`. The driver then parses `cliStdout` as JSON and requires an `action`. So the CLI's own bytes already cross the host's `tool.call` for `Bash`, in a subagent loop (`e.agentId` set), and the resolved result's `text` is the stdout the model read. The engine's declaration (`claude-code.d.ts`, written by 2.1.286 on this machine) says `tool.call` fires for a subagent's calls and that the result from core is `{ ref, result, text, isError?, isReadOnly? }`.
- **A step record is `{ schema: 'interlock.run-step/1', action, then, spawns, ...rest }`** (`makeStep` in `lib/run.mjs`). `action` is one of `ACTIONS` (`run-batch`, `test-wave`, `verify`, `replan`, `done`, `halt`, `classify`, `verify-final`, `review`, `remediate`, `verdict`, `handoff`, `commit`, `close`, …). `rest` carries the wave-state pass-through (`wave`, `waveIndex`, `waveKind`, `batchIndex`, `batchCount`, `remainingBatches`, `mode`, `runMode`, `reason`, `summary`, `kind`, `failures`, …) and, on steps that raised one, `banners` (an array of strings: `haltStep` and the review and verify steps pass it; `runStart` carries its banners and `notes`). Each spawn carries `label`, `kind`, `model`, `effort`, `type`, `tools`, `schema`, `isolation`, `worktree`, and the briefing's `promptPath` and `promptSha256`. `runClose` returns `{ action, exitCode, summary, banners }` and the CLI prints the close's record under `--json`.
- **The Workflow tool is a built-in whose shapes the declaration pins:** input `{ script?, name?, args?, scriptPath?, resumeFromRunId? }`; result `{ status: 'async_launched' | 'remote_launched', taskId, taskType?, workflowName?, runId?, summary?, transcriptDir?, scriptPath?, sessionUrl?, warning?, error? }`. `guard-ship-relaunch`'s capture showed a typed `/interlock:ship` reaches the tool as `Workflow({ name: 'interlock:ship', args })` and answers `status: 'async_launched'` with `taskId` and `runId`.
- **Model requests and turns carry the agent.** `turn.step` is a streaming (generator) hook: `e` carries `turnId`, `index`, `model` (as resolved for this request), `effort?`, `messageCount` and `agentId?` inside a subagent's loop; `const result = yield* next(e)` resolves with `result.usage: TurnUsage | null`, where `TurnUsage = ModelUsage & { model }` (`input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens` as one number, and the id the API reported). `turn.complete` carries `answer`, `durationMs`, `isAborted`, `turnId`, `usage?`, `reason` (`answer` | `aborted` | `refusal` | `error`) and `agentId?`. The declaration says of `agentId`: "A workflow's agents and the engine's own forks carry ids no list names", so the runtime's agents are expected to carry one; whether `agent.spawn` fires for them is undocumented.
- **Drawing.** `$.ui.open({ id, title, focus?, closeOnEscape?, … })` resolves `{ isPlaced: true }` or `{ isPlaced: false, reason }`; opened unasked it seats only from 144 terminal columns (110 once the person has opened that id). `ui.render` on `{ component: 'Pane', requestId }` draws it with `const { Box, Text } = $.ui.resolve(e)`; `ui.render` on `{ component: 'Spinner' }` may pass `next({ ...e, props: { ...e.props, suffix } })`. `$.ui.status(text | undefined)`, `$.ui.toast(text, { timeoutMs })`, `$.ui.log(text, { to: 'debug' })`, `$.ui.invalidate('ui.render')`. `$.session.usage()` returns `{ startedAt, context, rateLimits: [{ kind, percentUsed, resetsAt? }], cost? }`; `$.session.version()` returns `{ version, base?, builtAt }`. Redraws are throttled by the engine.
- **The module's environment.** No Node and no DOM; `$` is the only way out. Imports must be relative, inside the plugin, or the bare `claude-code`; `lib/limits.mjs` imports nothing and is importable, while `lib/ship-stage.mjs`, `lib/run-log.mjs`, `lib/launch-ledger.mjs` and `hooks/_shared.mjs` import `node:fs` and are not. `claude plugin validate` reads the module statically and requires every engine call spelled in full as `$.ns.method`, event names as string literals and no dynamic `import()`. A hook that throws or exceeds its 10-second budget is skipped and the chain runs; a `.catch` handler is the one way to fail closed.
- **Hosts on this machine, 2026-10-05.** `claude` on PATH is 2.1.274 (no `plugin test` subcommand); a mise-installed 2.1.289 has `plugin test` and, in a module-less directory, reports `no hooks module to load`, which is the "mods can load here" answer; a Homebrew 2.1.161 is a third, older target; the Desktop engine behind this session is 2.1.286, below the floor. On the 2.1.289 binary `claude plugin validate . --strict` already fails this checkout for a warning that `CLAUDE.md` at the plugin root is not loaded as project context.
- **Tests and packaging.** `npm test` is `node --test $(find test -name '*.test.mjs' | sort)`, so a `.test.ts` file is never collected. `test/spine/package.test.mjs` walks only relative specifiers (`.`-prefixed) from every `bin` entry, so a bare `claude-code` import is not followed, and the hooks module is not a root today. `test/hooks.test.mjs` pins the manifest's inline `hooks` registrations by reading `.claude-plugin/plugin.json`. `.github/workflows/ci.yml`'s `validate-plugin` job installs the current CLI and runs `claude plugin validate . --strict`.

Constraints inherited (`CLAUDE.md`; the briefs' "Repository constraints every brief inherits" and "Repository constraints the mod briefs add"): the mod observes and the CLI decides; fail-open stays fail-open, so no `.catch` and no `tool.check`; inert outside a live run and in `-p`; no model calls, prompts, messages, network or process from the module; thresholds live in `lib/limits.mjs`, and the meter needs none; the hooks module is `.mjs` and only its tests are `.test.ts`; nothing is written to `~/.claude/dev-mods/`; older hosts are proved, not assumed.

## Goals / Non-Goals

**Goals:**

- Show the run while it runs, from the CLI's own records as they cross the host, with no file read on the hot path and no second measurement that could disagree with the receipt.
- Leave every other surface byte-identical: the settings hooks, the close summary, the receipt, the trajectory, and the run on a host that cannot load mods.
- Settle the module's shape, its test convention, its static pins and its CI step once, so the next change (the in-process launch guard) adds hooks and cases without reorganising anything.

**Non-Goals:**

- Recording anything. The per-agent sidecar, the briefing-sha join, the observed `hook` cache accounting and `MODEL SUBSTITUTED` are the CLI's (`observe-agents-and-resolve-state-home`), and the meter's figures are display only.
- Deciding anything: no deny, no rewrite of a model, an effort, a prompt or a tool call, no verdict on a substitution, no threshold on a plan window.
- Handing the CLI a value the mod observed (the reason word on `AGENT RETURNED NO RESULT`, plan windows on the receipt); both would need a write channel this change does not open.
- Drawing anywhere but the terminal and the Desktop Code tab, or redrawing anything Claude Code draws other than the spinner's suffix.

## Decisions

### D1 — The step envelope is the meter's one source, and `banners` is a field on both ends

The mod reads each step from the Bash result's `text`: `JSON.parse` guarded, accepted only when it is an object with a string `action`, exactly the test the driver applies. From it the mod takes `action`, `wave`, `waveIndex`, `batchIndex`, `batchCount`, `remainingBatches`, `spawns[].{label, kind, model, effort, promptSha256}`, `banners`, `notes`, and on the close record `summary`, `exitCode` and `banners`. It recognises no banner by its text: a toast is `$.ui.toast(text)` for each entry of `banners` whose exact text has not been toasted in this run (a `Set` of texts; a banner carried from one step to the next is shown once). Where a step today raises a banner into the summary without carrying it on the step (the audit in task 2.1 lists each: every `pushBanner`/`manifest.banners.push` site whose step omits `banners`), the CLI gains the field from the same list; `runClose`'s returned `banners` is printed in the close's JSON record beside `summary`. That is the one CLI change, and it is additive.

*Alternatives considered.* Reading the banner lines by the strings `docs/04` documents: couples the mod to wording, and a reworded banner would silently vanish from the meter, the exact failure the banner exists to name. Reading the trajectory with `$.fs.read`: a 4 MiB whole-file read with no tail, and the step stream is already parsed. Reading the stage marker: the action on the step already names the stage, and the marker is a file.

### D2 — The command match is the driver's own line

The Bash hook acts only when `e.command` begins with `interlock ` (what `cli()` emits, with the optional quoting of a following argv token) and the run is live; anything else is `return next(e)` on the first line. It does not match `node bin/interlock`, `./bin/interlock` or `npx`, because the driver emits none of them; a future driver that did would get the meter by emitting the same line, which the no-policy sweep already requires it to keep. The match is on the command's prefix, not its argv, so a `--root` or `--state-home` the driver adds later changes nothing. A `pingModel`-style field for the meter on the step is not needed: the step is the data.

### D3 — The live flag is module state, re-derived from the next step

`live`, the run id, the change, the tallies, the banner set and the surface facts are module-level variables. A reload (dev hot-reload only; an installed plugin loads once per session) resets them, and the next `interlock` step that crosses the module re-derives the change and run id from the record (`run start`'s step carries both; later steps carry the wave position). `$.state` and a `types` contract are not introduced here: `types` is a manifest key an older host may strip with a warning that `--strict` turns into a failure, and task 1 is the first place that is measured. The next change introduces `$.state` with the contract, after that measurement.

*Alternative considered.* `$.state` now: cleaner, redraw-on-write for free, but it couples this change's older-host gate to a second unknown.

### D4 — What makes a run live, and what ends it

Live begins in the `Workflow` hook: `const r = await next(e)`; when `isShipLaunchInput(e)` (the input's `scriptPath` ends in `workflows/ship.js` or its `name` matches `interlock:ship`, the same two handles `lib/launch-ledger.mjs` matches) and `r.deny === undefined`, `r.isError !== true` and `r.result?.status` is `async_launched` or `remote_launched`, the mod keeps `r.result.runId`, `workflowName` and `transcriptDir`, sets `live`, opens the pane unasked (D7) and returns `r` unchanged. Live ends when a step whose `action` is `close` or `halt` crosses, or when the close record (the `run close` call's result, recognised by `then === null` and the presence of `summary` and `exitCode`) crosses; the status line is cleared with `$.ui.status(undefined)`, the tallies are kept for the pane until the next launch. The two handles are duplicated as two regular expressions in the module rather than imported, because `lib/launch-ledger.mjs` imports `node:fs`; the next change extracts the rule into a Node-free module and the meter switches to importing it.

### D5 — Tallies are per agent id, display only, and never zero

`turn.step` is registered as a generator: `if (!live || !e.agentId) return yield* next(e)` first; else `const result = yield* next(e)`, then the agent's record gains one request, `result.usage` summed field by field when it is an object (`input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`), the `model` added to the agent's set, and `partial = true` when `result.usage` is `null`. A field a request omits leaves that figure `null` for the agent, the `foldCacheUsage` rule one level up. `turn.complete` with `agentId` records `reason`, `durationMs` and the summed `usage` when present. `agent.spawn`, when the host raises it, maps `result.agentId` to the `sha256` matched in `e.prompt` by the same expression `lib/agent-usage.mjs` uses for the bootstrap (`/Expected sha256: ([0-9a-f]{64})/`, last match), so a wave row whose spawn `promptSha256` equals it carries the agent's figures and the agent's row carries the lane label; with no spawn event the row is keyed by a shortened agent id and reads `lane: unknown`. No comparison of the served model against the routed one is made in the module: both are shown side by side, and the verdict stays `modelSubstitution` in `lib/run.mjs`. The pane prints one line, `live figures; the close summary and the receipt are the record`.

### D6 — The status line and the spinner

`$.ui.status('interlock: <change> · <action> · wave <waveIndex+1>/<waveCount> · batch <batchIndex+1>/<batchCount>')`, with each position omitted when the step carries no such field (the classify and close steps have none). The wave count is `waveIndex + 1 + remainingBatches`-style arithmetic only when the fields allow it; otherwise the wave index alone. The spinner suffix is the same text without the `interlock:` prefix, through `next({ ...e, props: { ...e.props, suffix } })`, and `next(e)` when nothing is live. Both are cleared at close. No colour, no threshold.

*Found during implementation, 2026-10-05.* Two facts narrow what the status line can say on the Workflow host. (1) Every `interlock run` step reaches stdout through `relayStep`, whose `RELAY_STEP_FIELDS` whitelist (`schema`, `action`, `then`, `spawns`, `banners`, `change`, `wave`, `reason`, `pingModel`) exists to bound the bytes a model retypes; `waveIndex`, `batchIndex` and `batchCount` are dropped, so on that host the line reads `interlock: <change> · <action> · wave <w>` and the batch position appears only where a step carries it. Widening the whitelist is a separate decision with its own cost (every relayed step grows) and is not taken here. (2) `wave` is the task-section group the wave dispatches, not a position, and no step carries a wave total, so the line never reads `wave i/n`. The spec scenario was corrected to say so. A clean close's record has `action: 'complete'`, not `close`, so the module recognises the close record by its shape (`then === null`, a string `summary`, a numeric `exitCode`); a `halt` or `close` step clears the status line and keeps reading until that record crosses, so the summary lands on the pane.

### D7 — Pane policy and contents

At live the mod calls `$.ui.open({ id: 'interlock-meter', title: 'Interlock', closeOnEscape: true })`; `isPlaced: false` produces exactly one `$.ui.toast('/interlock-meter opens the ship meter')` and nothing else. `/interlock-meter` is registered in `session.start` with `immediate: true` so it opens mid-run, answered by a `command.run` hook that opens the same id and returns `{}`. The pane is `Box` and `Text` only (both surfaces): header (change, run id, action, `live figures …` line), wave table (one row per spawn seen on the newest `run-batch` or `test-wave` step and on earlier ones still live: label, routed model, served models from the joined agent or `?`, effort, state from `turn.complete`'s reason or `running`), per-agent lines for agents with no lane, plan windows from `$.session.usage().rateLimits` read in the render hook (kind, percent, reset time as the host gave them; off a subscription the list is empty and the section says so), banners so far in order, and after the close the summary text verbatim. With no run live: one dim line, `no ship run is live in this session`. The Desktop's seating rule for an unasked pane is a probe; the code does not depend on it.

### D8 — Observe-only, pinned twice

Allow-list, exactly: `$.ui.status`, `$.ui.toast`, `$.ui.log`, `$.ui.open`, `$.ui.invalidate`, `$.ui.resolve`, `$.command.register`, `$.session.usage`, `$.session.version`. Forbidden tokens, exactly: `.catch(`, `deny`, `tool.check`, `$.model`, `$.prompt`, `$.process`, `$.http`, `$.session.send`, `$.fs.write`, `$.store`. `test/spine/mod-pins.test.mjs` reads `hooks/mod.mjs` as text (never imports it: the bare `claude-code` specifier does not resolve under Node, and the suite runs on Node 18), extracts every `$.<ns>.<method>` and asserts the subset, asserts no forbidden token, asserts `hooks/hooks.json` names exactly one module that exists, and walks the module's relative imports asserting each resolves inside the plugin and that no file in the closure imports a `node:` module or a bare specifier other than `claude-code`. The CI validate's `hooks:` and `calls:` lines are recorded here once the module exists (task 3.2) and compared by eye at review; they are not parsed by a test, because their format is the engine's.

### D9 — The `mods` doctor row and the engine's own line

`MODS_MIN_HOST_VERSION = '2.1.287'` joins `SUBAGENT_MODEL_DEFAULT_ONLY_MIN_VERSION` and `SUBAGENT_MODEL_FORCE_MIN_VERSION` in `lib/host/claude-env.mjs`, read through the existing `compareVersions`. `checkMods(version)` in `lib/doctor.mjs` takes `checkClaudeEnv`'s posture (own try/catch, `ok`/`skip`, never `fail`), fed by the same `claudeVersionOf(env, probe)` the `claude-env` row already paid for, so the preflight spawns nothing new. Its detail names the probed binary (`claudeCommandArgv(env)[0]`), the version, the floor, and that a Desktop session's engine may differ from it. Because the doctor can only speak about PATH, the mod itself logs once at `session.start`, through `$.ui.log(…, { to: 'transcript' })` in an interactive session and `{ to: 'debug' }` otherwise: `interlock meter: engine <$.session.version().version>, drawing on <surface>` or `… nothing draws here`.

### D10 — CI, tests, and the precondition this change does not cause

`claude plugin test .` is added to `validate-plugin` after `claude plugin validate . --strict`; the tests are `test/mod/meter.test.ts`, written against `claude-code/testing` (`test`, `expect`, `mock`), each UI case looped over `['terminal', 'desktop'] as const`. The job already installs the current CLI, which is the version `plugin test` needs. The precondition named in the proposal is recorded here as a decision: on 2.1.289 the strict validate fails this checkout for the root `CLAUDE.md` warning, with or without this change, the moment CI's `npm install -g` picks that release up. Task 1 records the exact warning text and whether the plugin manifest reference offers a key that silences it; the `plugin test` step is added regardless; and making the strict validate green on that release is a separate, small change, because `CLAUDE.md` is this repository's canonical root instruction file and moving it is not this change's call. Until that lands, the job's red is the warning's, and the test step's own result is visible in the same log.

### D11 — Packaging

`test/spine/package.test.mjs` gains the hooks module as a closure root: for each path in `hooks/hooks.json`'s `modules`, resolved against that file, `importClosure` runs and every reachable file must be covered by `files`. `files` already lists `hooks` and `lib`, so nothing moves; the test exists so a `lib/` file the module imports can never fall out of the whitelist. `relativeSpecifiers` is unchanged: `claude-code` is bare and is the engine's.

### D12 — Older hosts: task 1 is the gate

Task 1 is run before any test is written. With the 2.1.161 and 2.1.274 binaries and the 2.1.289 binary, each of: `claude plugin validate . --strict` on a scratch plugin carrying `hooks/hooks.json` with `modules` beside manifest `hooks` (expected on the older two: ignored or warned, both acceptable only if the settings hooks still register; refused is a stop); the same scratch plugin with a `types` manifest key (measured now for the next change, not used here); a `--plugin-dir` session on the oldest binary that can run one, confirming the preflight runs and a guard denies. Also recorded: whether `tool.call` fires for the ping's Bash with the CLI's whole stdout in `text`; whether `turn.step` and `turn.complete` carry an `agentId` for the runtime's agents; whether `agent.spawn` fires for them; what the Desktop seats for an unasked pane. The first three decide whether the change ships; the rest decide which rows the pane can label.

### D13 — `hooks/hooks.json` carries an empty `hooks` record beside `modules`

Task 1.1 found 2.1.161 refusing a `modules`-only `hooks/hooks.json` (`hooks: Invalid input: expected record, received undefined`): that build reads the path as the legacy settings-hooks file, and 2.1.161 is inside the plugin's documented v2.1.154+ floor. The file is therefore `{ "hooks": {}, "modules": ["./mod.mjs"] }`, which passes `--strict` on 2.1.161, 2.1.274 and 2.1.289. The record stays empty: the settings hooks stay inline in the manifest, where `test/hooks.test.mjs` pins them, so the file contributes no settings hook on any host and a reader of either kind finds what it expects. `test/spine/mod-pins.test.mjs` pins the `hooks` key as present and an empty object, so a later edit cannot drop it (old hosts refuse) or move a guard into it (two places to pin).

*Alternatives considered.* Stopping and raising the documented floor past 2.1.161: a floor move is a bigger decision than a meter, and the dual shape costs one key. Moving the settings hooks into the file's `hooks` record: duplicates or moves the manifest registrations the existing pins read, for no gain.

*Runtime half, recorded.* 2.1.161 loading the dual-shape plugin through `--plugin-dir` runs the manifest's settings hooks: the `SessionStart` context and the `PreToolUse` deny both reached the model (Open Questions, task 1.1). The change proceeds on this shape.

## Risks / Trade-offs

- [An older host refuses `hooks/hooks.json` or drops the manifest's settings hooks] → task 1 stops the change and records what the plugin's version floor would have to become; nothing ships.
- [The mods API moves between releases; the declaration header says so] → the module is written against the type file the running engine writes, `claude plugin validate` runs before every commit and in CI, and a refused hook shape is one dim transcript line and the engine drawing its own, never a failed run.
- [`tool.call` does not fire for the ping's Bash, or `text` is not the whole stdout] → the meter has no step stream; task 1 finds it and the change stops, because the status line and the toasts are the point.
- [`agent.spawn` does not fire for the runtime's agents] → rows are keyed by agent id and say the lane is unknown; the wave table still shows routed models and the agent rows still show served models, without the join.
- [A `turn.step` tally and the receipt disagree] → the pane says which is the record, tallies are never written, and `TurnUsage` carries no tier split so the pane never shows one.
- [The unasked pane is declined in a narrow terminal] → one toast names the command; the status line and toasts need no pane.
- [A second toast per repeated banner] → the per-run text set shows each once; the pane lists all.
- [Node 18 cannot import the module] → the pins test reads it as text and the kit runs it under the engine; `npm test` never collects `.test.ts`.
- [The CI job is red on 2.1.289 for the root `CLAUDE.md` warning] → named in D10 as a pre-existing precondition with its own fix; this change adds its step and hides nothing.
- [A hook exceeds its 10-second budget parsing a huge stdout] → the step record is small by construction (`verifySpillBytes` and `verifyPreviewChars` bound what the CLI prints), and a throw or a timeout is skipped, not fatal.

Additive. New files `hooks/hooks.json`, `hooks/mod.mjs`, `test/mod/meter.test.ts`, `test/spine/mod-pins.test.mjs`; a `banners` field on steps and the close record where only text carried it; a `mods` doctor row; one CI step; two `CLAUDE.md` sentences.
