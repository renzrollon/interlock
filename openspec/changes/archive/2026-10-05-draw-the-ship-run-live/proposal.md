## Why

A ship run speaks at close. Every soft continue in `docs/04-when-it-stops.md` (`GRAPH UNAVAILABLE`, `MODEL ROUTING OVERRIDDEN`, `CACHE ACCOUNTING PARTIAL`, `MODEL SUBSTITUTED`, the rest) is printed in the summary of `interlock run close`, which an agent reads and the trampoline relays. For the twenty minutes before that, the operator watching the Desktop Code tab or a terminal sees a spinner. The halt resume card exists because nobody was watching; this change exists because somebody was, and could see nothing. A settings hook cannot draw and a status line is the user's, not a plugin's; a mod draws a pane, a status line and toasts in exactly the two places `/interlock:ship` is typed (Brief 7 of `briefs/claude-code-teams-and-orchestration-briefs.md`, read with the 2026-10-05 addendum: mods-3, mods-13).

The facts the meter needs already cross a mod's hooks, host-observed and without a file read. Every `interlock` CLI call a ship run makes is a Bash tool call inside an `interlock:ping` subagent, because the Workflow script has no shell: `cli()` in `workflows/ship.js` builds `interlock <argv> --results <file> --json` and the relay copies the CLI's stdout verbatim, so the step the CLI emitted, the wave it belongs to, the spawns it named and the banners it raised cross `tool.call` the moment they are produced. The Workflow tool's own result names the run (`status: 'async_launched'`, `runId`, `workflowName`, `transcriptDir`). Each model request inside the run carries the model that answered and its usage with the agent's id (`turn.step`), each agent's turn ends with a reason and a duration (`turn.complete`), and the account's plan windows are one call away (`$.session.usage()`).

One premise of the briefs has inverted since they were written, and it changes the meter's shape. Brief 9 paired the meter with a second measurement route, on the assumption that Brief 4's transcript probe would fail. It passed: `observe-agents-and-resolve-state-home` landed the recorder, the per-agent sidecar, the briefing-sha join at close, the observed `hook` cache accounting and the `MODEL SUBSTITUTED` verdict. The CLI already records what Brief 9 would have recorded. So this change takes Brief 9's display half only: the meter shows the run live and says in its own text that the close summary and the receipt are the record. It writes nothing, joins nothing and decides nothing.

## What Changes

- **The plugin gains a hooks module, and the settings hooks stay exactly as they are.** `hooks/hooks.json` is created with `{ "hooks": {}, "modules": ["./mod.mjs"] }`; the manifest's inline `hooks` merge with it (mods-2), so the five guards, the preflight and the recorder are untouched. The empty `hooks` record is there for older hosts: 2.1.161, inside the plugin's v2.1.154+ floor, reads `hooks/hooks.json` as the legacy settings-hooks file and refuses one without a `hooks` record, while this dual shape passes `claude plugin validate --strict` on 2.1.161, 2.1.274 and 2.1.289 (task 1.1, recorded in the design). `hooks/mod.mjs` is an ES module that exports `register(on)` and imports only Node-free modules from the plugin (`lib/limits.mjs` today). It runs in the engine's own environment, with no Node, and `$` is its only way out.
- **Every hook observes.** `session.start` registers the `/interlock-meter` command (`immediate: true`), records the surface and whether the session is interactive, logs once which engine version it is on and whether anything draws here, and in a non-interactive session (`-p`, the SDK, a runner lane) leaves the module inert for its life. `tool.call` on `Workflow` lets the call run and, when the input names the plugin's ship workflow and the result says it launched, marks the run live and keeps the result's `runId`, `workflowName` and `transcriptDir`. `tool.call` on `Bash`, while a run is live and the command begins with `interlock `, lets the call run and reads the CLI's own stdout from the result text as a step envelope: the action, the wave and batch position, the spawns with their label, kind, routed model, effort and briefing sha, the banners and the notes; every other Bash call is `next(e)` at the first line. `turn.step` tallies per agent id, while a run is live, the tokens of each request and the model that answered. `turn.complete` keeps each agent's reason and duration. `agent.spawn`, if the host raises it for the runtime's agents, maps the resolved agent id to the briefing sha in the spawn's prompt, so a per-agent row can carry its lane label; if it does not fire, rows are keyed by agent id and say so. The spinner gains a suffix naming the step and wave. The pane is drawn from the tallies on request. No hook returns `{ deny }` or `{ result }`, no `.catch` handler exists, and the module calls no `$.model`, `$.prompt`, `$.session.send`, `$.process`, `$.http`, `$.fs.write` or `tool.check`.
- **The status line and the toasts.** `$.ui.status('interlock: <change> · <action> · wave i/n · batch j/k')` follows the steps the CLI emits and is cleared when the close or the halt step is seen. Each degradation banner a step carries becomes one `$.ui.toast` the moment the step crosses the mod, and the pane lists every banner so far. The source is the step envelope's `banners` field and the close's JSON output, never a regular expression over the summary's prose: the mod displays what the CLI named and recognises nothing itself.
- **The pane.** `/interlock-meter` opens it at any width. At run start the mod opens it unasked, which the engine seats only in a wide terminal (144 columns, 110 once the person has opened it; the Desktop's rule is a probe), and otherwise one toast says the meter is available. It is `Box` and `Text` only, so it draws on both surfaces: the change and run id, the current action, a wave table (lane label, routed model as the step named it, served model as `turn.step` reported it, effort, state), per-agent tokens (input, output, cache read, cache creation as one number, because `TurnUsage` carries no lifetime-tier split), the plan windows from `$.session.usage()` (kind, percent used, reset time) with no threshold and no colour, the banners so far, and at a halt the resume card's path from the close's summary. One line says that these figures are live and the receipt is the record.
- **The step envelope is pinned as the meter's source.** The `banners` field the CLI already carries on a step that raised one, and the `banners` the close's `--json` output carries beside its summary, become a stated contract of `ship/run-program`, because a second reader now depends on them. Where a banner reaches the summary only as text today, the CLI gains it as a field, derived from the same list it prints. No new threshold, no new limits key.
- **Doctor gains a `mods` row.** `ok` when the `claude` the preflight probes reports 2.1.287 or later, `skip` with the version otherwise, never `fail`; the floor is a named constant beside the other host-version floors in `lib/host/claude-env.mjs`. The row says which binary it read, because in a Desktop session the engine behind the Code tab is not the `claude` on PATH, and the mod's own `session.start` log line names the engine it actually loaded in.
- **`claude plugin test .` joins CI.** The `validate-plugin` job already installs the current CLI; it runs the mod's tests after `claude plugin validate . --strict`. The tests live in `test/mod/` and are named `*.test.ts`, because that command runs nothing else; `npm test` is unchanged and its `find` collects only `*.test.mjs`. A precondition is recorded in the design: on the 2.1.289 binary installed on this machine, `claude plugin validate . --strict` already fails this repository for a warning about `CLAUDE.md` at the plugin root, so the job will be red the day CI installs that release, with or without this change.
- **The conventions say so.** `CLAUDE.md` gains two sentences under Conventions: the mod's tests are the one `.test.ts` exception and why; the hooks module imports only Node-free modules. `docs/13-the-guards.md` gains a row and a section for the mod (what it hooks, that it decides nothing, where the engine reports a skipped hook). `docs/04-when-it-stops.md` says banners now also appear live as toasts and that the summary at close is unchanged and remains the record. `docs/07-cli-and-configuration.md` documents `/interlock-meter` and the `mods` doctor row.
- **The module's reach is pinned twice.** A `node --test` case reads the module as text and asserts its `$.` calls are a subset of an allow-list, that it contains none of the forbidden tokens, that `hooks/hooks.json` names exactly one module and it exists, and that every import of the module resolves inside the plugin and names no `node:` module. The CI `validate-plugin` job's `claude plugin validate . --strict` prints the `hooks:` and `calls:` lines the design records.
- **Older hosts are proved before anything ships.** Task 1 validates a scratch plugin carrying `hooks/hooks.json` on the three binaries on this machine (2.1.161, 2.1.274, 2.1.289) and loads it through `--plugin-dir` on the oldest to confirm the settings hooks still run. If an older host refuses the file or drops the settings hooks, the change stops there and records what the plugin's version floor would have to become.

No breaking change: a session whose host cannot load mods runs exactly today's run, and the close summary prints every banner as before.

## Capabilities

### New Capabilities

- `hooks/ship-meter`: the plugin's hooks module and what it draws. The file layout and the merge with the settings hooks; inertness outside a live ship run and in non-interactive sessions; the live flag read from the Workflow launch; the step stream read from the ping's Bash result and what it yields (status line, toasts, wave rows); the per-agent tallies as display-only figures; the pane's contents on both surfaces; the observe-only guarantee and the static pins that hold it; the one `.test.ts` exception.

### Modified Capabilities

- `ship/run-program`: modifies "The CLI SHALL emit every step of the lean run as a versioned record that names its own continuation" so a step carries the degradation banners it raised as a `banners` field, and the close's JSON output carries its banners beside the summary, because the meter is a second reader of both.
- `hooks/session-preflight`: adds the `mods` doctor row (advice; `ok` or `skip`, never `fail`; names the binary it read and the floor).
- `distribution/npm-package`: modifies "The published tarball SHALL be a whitelist closed over the declared binaries" so the closure also starts from the hooks module `hooks/hooks.json` names, because a `lib/` file the module imports that is not in `files` loads cleanly from the plugin checkout and fails in the installed package.

## Impact

**Code**

- `hooks/hooks.json` (new), `hooks/mod.mjs` (new). `.claude-plugin/plugin.json` is unchanged in this change (no `types` key until the next change has the older-host result).
- `lib/run.mjs`, `bin/interlock`: the `banners` field on any step and on the close JSON where only text carries it today, derived from the existing list.
- `lib/host/claude-env.mjs`: `MODS_MIN_HOST_VERSION = '2.1.287'` beside `SUBAGENT_MODEL_FORCE_MIN_VERSION`. `lib/doctor.mjs`: `checkMods` on `checkClaudeEnv`'s posture, fed by the same `claude --version` probe.
- `.github/workflows/ci.yml`: `claude plugin test .` in `validate-plugin`, after the strict validate.
- `CLAUDE.md`: the two convention sentences.

**Tests**

- `test/mod/meter.test.ts` (new, run by `claude plugin test`): `session.start` interactive and not; a `Workflow` call with a stubbed result carrying `runId` makes the run live and a non-ship `scriptPath` does not; a Bash call whose stubbed `text` carries a step with one banner sets the status line to the step's action and wave and raises exactly one toast; `turn.step` stubs for two agent ids tally separately with the model each reported; `turn.complete` keeps the reason; the Pane mounts on `terminal` and on `desktop` and `find` returns the wave row and the banner on both; nothing is tallied, set or toasted in a non-interactive session.
- `test/spine/mod-pins.test.mjs` (new, `node --test`): the allow-list, the forbidden tokens, the single module, the resolvable Node-free imports.
- `test/hooks.test.mjs`: the manifest's inline `hooks` still register every settings hook with `hooks/hooks.json` present.
- `test/spine/doctor.test.mjs`: the `mods` row. `test/spine/run.test.mjs`: the `banners` field on the steps and on the close JSON. `test/spine/package.test.mjs`: the module as a closure root.

**Docs**

- `docs/13-the-guards.md`, `docs/04-when-it-stops.md`, `docs/07-cli-and-configuration.md`, `CHANGELOG.md` under Unreleased.

**Dependencies and ordering**

- Depends on nothing in code. Lands before `guard-ship-relaunch-in-process`, which adds hooks to this module, state to a contract this change does not yet declare, and cases to the same test files.
- Touches no `CAPABILITY_VALUES` entry in `lib/host/registry.mjs`: whether anything draws is a fact about the session's surface, not a host capability.
- No runtime dependency. The engine-written `claude-code.d.ts` (2.1.286 on this machine, "as of v2.1.289" on the reference page) is the contract the module is written against, and `claude plugin validate` is run before every commit; the API is early access and may move between releases, which is why the type file the running engine writes, not a copy, is the authority.
- The CI precondition: the `validate-plugin` job's strict validate is red on 2.1.289 for the root `CLAUDE.md` warning. The design names it as a decision to settle before the test step is added; it is not caused by this change and is not hidden by it.

**Out of scope**

- Any deny or rewrite (the next change), any file write (Brief 9's recording half, now redundant with the recorder the CLI already joins).
- The two residual Brief 9 items that would need the mod to hand the CLI a value: the reason word on `AGENT RETURNED NO RESULT`, and plan windows on the receipt.
- Redrawing `ToolUse` rows, `AskUserQuestion`, or any site Claude Code draws, other than the spinner's suffix. `Client`, `Raster`, `Image`, `Svg`.
- The runner host: its lanes are `-p` processes where nothing draws, and the adapter reads their envelopes.
- `interlock board` across sessions, and a plan-window ceiling: both are app ideas with their prerequisites as the briefs state them.
