## Why

`/interlock:spec` has no CLI-side spine to draw from. Ship has one: the run program prints every step as JSON, the ping's Bash result carries it across the engine, and `hooks/mod.mjs:564-578` reads it off `r.text` and draws the status line and the pane. Spec is a prose skill that runs in the parent conversation (`docs/10-agentic-workflow-ship-and-spec.md`, "Spec/explore/review-artifacts still run in the parent conversation"), drives two CLIs through Bash, writes its artifacts with the Write tool, and ends at a human checkpoint. Nothing it does publishes a stage: `lib/ship-stage.mjs:52`'s `STAGES` are ship's, `interlock notify checkpoint` is pure transport and writes nothing (`lib/notify.mjs:8-12`), and `openspec` keeps no status, lock or log file; its artifact ladder exists only in the stdout of `openspec status --change "<name>" --json`, which the skill re-runs after every write (`skills/spec/SKILL.md:123, 139`). The deep-research report (`reports/Interlock mods beyond the ship meter.md`; `research_notes/Interlock mods beyond the ship meter/spec_mod_feasibility.md` §3, §6, §7; `candidate_mod_catalog.md` candidate 5) answered the question "is a mod for `interlock:spec` possible" with yes, in one shape: a write-nothing observer, keyed on the skill load, that draws only what crossed the Bash tool. This change is that shape.

Everything the observer needs already crosses the engine in process, and after the sibling `print-json-from-the-spec-gate-lines` lands, all of it is JSON. `skill.prompt` "fires when the engine expands a skill's prompt for the model (`/name`, the Skill tool, a preload)" and carries `{ skill, text }` (`claude-code.d.ts`, 2.1.289 build, `:4150-4160`, `:11337-11345`). `agent.spawn` "fires when the Agent tool is about to start a subagent" with `subagentType` (`:3967-3974`, `:263-290`), which is what explore's `Explore` investigators are (`skills/explore/SKILL.md:85`). A `tool.call` on `Bash` resolves with the CLI's stdout as `text` (`test/fixtures/mod/tool-call-bash-interlock.json`, captured on 2.1.289), and the Bash result record carries `stdout`, `stderr` and `interrupted` but no exit code (`:19172-19205`), which is why the sibling's `--json` matters: the verdict field (`blocking`, `ready`, `passed`) is in the text, so the exit is not needed. The sibling pins by token, in the flow's order, every line this meter keys on: `interlock drift --json`, `openspec new change`, `openspec status --change … --json`, `interlock ledger … --json`, `interlock validate … --json`, `interlock gate … --json`, both `interlock autonomy` lines, `interlock notify checkpoint`, and `--json` on the continuity `interlock ready` line (`openspec/changes/print-json-from-the-spec-gate-lines/specs/spec/machine-readable-gate-lines/spec.md`, "The lines an observer of the spec flow keys on SHALL be pinned by token"). Without those pins a reword that dropped `--json` would leave this pane reading `not run yet` forever, the `--metrics` failure mode `.claude/CLAUDE.md` names; with them, the reword fails the skill suite by name.

What a person sees today is the transcript. The ship meter goes live only on an accepted ship launch (`hooks/mod.mjs:531-568`; `watching()` at `:118`) and draws nothing in a spec session: no status line says which change is being specified or which gate it is at, no pane shows the artifact ladder, and the one line that matters at the end, that the run stopped at the checkpoint and is waiting (`skills/spec/SKILL.md:247`), reaches the person only if they are reading the transcript when it prints. Spec also waits on a person at several points by design (the open-ended intent question, the bug-fix evidence gate, pinned versions, continuity's ledger rows, the checkpoint itself), so the ship meter's `quiet <n> min` would measure the human, not the run; research §7 says so, and this change draws no such word.

## What Changes

- **The spec meter lives in the same hooks module, and goes live on the spec skill load alone.** `hooks/mod.mjs` (one module is pinned; a "second mod" is more hooks in the same module) gains a `skill.prompt` hook. When the skill named is the plugin's spec skill and the session is interactive (`session.start.isInteractive`), the module starts a spec run record, opens the `/interlock-spec` pane unasked (one toast names the command if the engine declines to seat it), and sets the status line. `openspec` commands alone never start a run: stock `/opsx:propose` runs the same CLI (`docs/10:130`) and draws nothing. The prompt is passed on as it came; rewriting `skill.prompt` is a rejected mechanism and the hook returns `next(e)`.
- **The change name comes from the CLI only.** From the argv of `openspec new change "<name>"`, from `--change "<name>"` on any `openspec` line, from the explicit name on `interlock ledger|validate|ready|notify checkpoint "<name>"` and `--metrics <name>`, or from `changeName`/`change` in a result's JSON. Until one crosses, the status line and the pane read `change: unknown until named`. The record keeps results per change name, so a session that touches two active changes draws the one the CLI named last and lists the others.
- **The stage is the last thing the CLI printed, in its own words.** While a spec run is live the `Bash` hook, which today reads only driver lines during a ship run, also reads the spec flow's keyed lines: `openspec new change`, `openspec status … --json` (the artifact ladder `artifacts[].{id, status, requires}` and `applyRequires`; never `isComplete` or `isPlanningComplete`, per OpenSpec issue #795), `interlock drift --json`, `interlock ledger … --json` (`blocking`, `needsHuman`, `invalidCount`, `missing`, `unparseable`), `interlock validate … --json` (`ready`, `problems`), `interlock gate … --json` (`passed`, `counts`, `malformed`, `metrics.written`, `metrics.reason`), `interlock autonomy record|clean` (command tokens only; never a level, never a count), `interlock ready … --json` on the continuity path (`ready`, `blockers`), and `interlock notify checkpoint`. The status line reads `interlock spec: <change> · <stage>`, for example `explore (3 investigators)`, `status 2/4 done · next: design`, `ledger blocking (needs_human 2 · invalid 0)`, `validate READY`, `gate BLOCKED (blocker 1 · warning 3)`, `checkpoint`. A result that is not JSON, the old skill's text lines included, is shown as `<line> (unparsed)` with its first line on the pane, never as a verdict. `$.ui.status` is one line per plugin, replaced by each call (`claude-code.d.ts:2365-2375`), so one composer in the module owns it: the ship position while a ship run is live, else the spec line.
- **Writes and spawns are counted, never read as validity.** The `Edit` and `Write` `tool.call` hooks the sibling `speak-permission-prompts-and-guard-denials` adds (its design D4) are reused, not duplicated: during a live spec run they also note writes to `openspec/changes/<name>/` (per artifact file, a count and the last time), to `.claude/handoff/explore-*.md` (the brief's path) and to `.claude/metrics/review-artifacts-<change>-<ts>.json` (the findings file's path). No write ever sets an artifact's status: the table is what the last `openspec status --json` printed, and a file a tool wrote with no status call since reads as written, not done. `agent.spawn` with `subagentType === 'Explore'` counts investigators; the loads of `/interlock:explore` and `/interlock:review-artifacts` inside a live run name their stage.
- **The `/interlock-spec` pane shows fields, not sentences.** The change and schema, the artifact table exactly as the last status printed it (`id · status · outputPath`, `applyRequires` named), explore (`<n> investigators spawned`, the brief's path or `no brief written yet`), drift (`unarchived <n> · broken <n> · aging <n>`), the ledger, validate, gate and readiness results verbatim by field or `not run yet`, the autonomy command last run, the writes, `last activity <ISO>` or `last activity unknown`, and a record line: `the artifacts on disk, the findings file and the gate's exit are the record`. No tick from file presence, no colour, no threshold, no `complete`, no `ready to ship`, no quiet word and no repeated-fact counter (both named as follow-ups below).
- **The run ends at three points.** At `interlock notify checkpoint` crossing the module, the run stops at its checkpoint: the status line reads `checkpoint` and stays, because the checkpoint waits for a person and the line is what tells them (`skills/spec/SKILL.md:247`); the pane keeps the last results; later keyed lines are ignored and the first is named once on the debug log. At an accepted ship Workflow launch, judged by the same `isShipLaunch` and `isAcceptedLaunch` the launch guard uses (`hooks/mod.mjs:530, 534`), the spec run ends before the ship run becomes live, so the one status line hands over without two writers. At the `classic.SessionStart` boundary with source `clear`, `resume` or `fork`, the spec run resets with the ship run, in the hook that already does that. A second spec skill load in the same session starts the record over.
- **What it never does.** No `deny`, no `tool.check`, no `.catch(`, no `$.process` (it never re-runs a gate), no `$.fs.write` and no `$.fs.read` (nothing on disk is needed: it draws only what crossed the Bash tool), no `$.model`, no `$.prompt`, no `$.store`, no new `$.state` key (the record is module state, reset at the boundary), no restated threshold (`lib/limits.mjs` gains nothing), no `quiet <n> min`, no verdict word of its own (`stalled`, `complete`, `ready to ship`), no inference from presence, no rewrite of any prompt or result. The text rules live in a new pure, Node-free `lib/spec-meter.mjs`, so the module holds no parsing and no wording of its own.
- **Which pins move.** `HOOKED_EVENTS` in `test/spine/mod-pins.test.mjs` gains `skill.prompt`; `agent.spawn`, `tool.call`, `ui.render` and `command.run` are already there, and the pane and command are new matchers on existing events. `ALLOWED_CALLS` is unchanged, `FORBIDDEN_TOKENS` is unchanged, the one `deny` stays the launch rule's, `types/index.d.ts` is unchanged. Two pins are added: neither `hooks/mod.mjs` nor `lib/spec-meter.mjs` spells `isComplete`, `isPlanningComplete` or the word `complete`; and every keyed command line the sibling pins in the three skills is one `lib/spec-meter.mjs` classifies, read from the skill files themselves, so the meter and the pins cannot drift apart silently. `claude plugin validate . --strict` is expected to gain `skill.prompt`, `ui.render{component=Pane, requestId=interlock-spec}` and `command.run{command=interlock-spec}` on the `hooks:` line and nothing on `calls:`; the design records the expected lines against the archived quiet-time design D7 baseline plus each preceding sibling's additions.
- **Probes come first, and each has a fallback.** (1) The exact `skill` key a plugin skill carries on `skill.prompt` (`interlock:spec` or `spec`; the declaration's example is `commit`), and whether the event fires at all for a plugin skill loaded by `/interlock:spec` and by the Skill tool; if it does not fire, the fallback trigger is the first `openspec new change` that follows an `interlock drift --json` in the same session, and the design says that stock OpenSpec flows then draw nothing because they run no `interlock drift`. (2) Whether `agent.spawn`, `turn.step` and `turn.complete` fire for Agent-tool subagents (the `Explore` investigators), as opposed to Workflow agents, for which the archived meter design recorded that `agent.spawn` did not fire; if not, the explore line reads `investigators: not reported by this host`. (3) What a Bash `tool.call` result carries for a keyed line that exits non-zero (a blocking ledger, a blocked gate, an unresolved name): whether `text` still holds the JSON, and whether `isError` is set; the exit code itself is not in the record, which the design says. (4) Whether two `$.ui.status` writers in one plugin interleave or overwrite; the declaration says one line per plugin, replaced by each call, and the design keeps one composer whatever the probe shows.
- **Docs and the changelog.** `docs/07-cli-and-configuration.md` gains a spec-meter section beside the ship meter's (`/interlock-spec`, what each stage word means and which line it came from, what the meter never says); `docs/13-the-guards.md` adds `skill.prompt` to the module's row and section and says the hook observes and never rewrites; `docs/10-agentic-workflow-ship-and-spec.md` notes under the spec steps that a mods host draws the flow live; `CHANGELOG.md` Unreleased carries the change; `briefs/claude-code-teams-and-orchestration-briefs.md` gains a dated note that the spec-meter idea from the mods report was taken up as a write-nothing observer and that a mod-written spec trace was retired for the same reason Brief 9's recording half was.
- **Named follow-ups, not in scope.** A CLI-written spec trace on disk (outcome-class, with an `interlock report` reader on day one; `interlock notify` is pure transport today, `lib/notify.mjs`); a published spec stage marker; a repeated-fact counter (`same ready artifact on 3 consecutive status calls`, `ledger still blocking after 2 audits`), display-only with no verdict word and no cap, which the pane's `last result` and `last activity` lines stand in for in v1; `--json` on `openspec validate` and on the two `interlock autonomy` lines, each one line and one pin in the sibling's terms.
- **Serialization.** This change touches `hooks/mod.mjs`, `test/mod/`, `test/spine/mod-pins.test.mjs`, `docs/13-the-guards.md` and `CHANGELOG.md`, so it lands last of the mod changes, after `speak-lane-turn-ends-and-session-cost`, `speak-permission-prompts-and-guard-denials` (whose `Edit` and `Write` hooks it reuses), `show-preflight-and-interrupted-runs-at-session-start` and `draw-the-wave-board-in-the-meter-pane`; and after `print-json-from-the-spec-gate-lines`, whose lines and pins it reads. Its validate lines are diffed against theirs.

## Capabilities

### New Capabilities

- `hooks/spec-meter`: the spec meter, beside `hooks/ship-meter`: live only on the plugin's spec skill load in an interactive session, with the change name taken from the CLI alone; the status line and the pane in the CLI's own words, read off the Bash results of the lines the sibling pins, with writes and spawns counted and never read as validity; the three end conditions and the hand-over of the one status line to the ship meter; observe-only with the pinned calls, inert everywhere else.

### Modified Capabilities

- `hooks/ship-meter`: the inertness requirement states who owns the module's one status line (the ship position while a ship run is live, otherwise the spec meter's line) and that an accepted ship launch ends a spec run before the ship run becomes live; the observe-only requirement's recorded hooks gain `skill.prompt` and the spec pane's matchers, with its calls unchanged.

`spec/machine-readable-gate-lines` (the sibling's new capability) is the dependency: the lines, the field tokens and the order this meter reads are pinned there and are not re-declared here. `spec/continuity-provenance`, `spec/decision-ledger`, `review/evidence-gate` and `review/metrics-emission` are read and untouched: no verdict, no exit code and no corpus moves.

## Impact

- **Changed:** `hooks/mod.mjs` (the `skill.prompt` hook, the spec run record, the spec read in the `Bash` hook, the write notes in the `Edit`/`Write` hooks, the `Explore` count in `agent.spawn`, the hand-over in the `Workflow` hook, the reset in `classic.SessionStart`, the one status composer, the `/interlock-spec` pane and command); `test/spine/mod-pins.test.mjs` (`HOOKED_EVENTS` gains `skill.prompt`; the no-`complete` pin; the skill-lines-to-classifier pin); `docs/07-cli-and-configuration.md`; `docs/10-agentic-workflow-ship-and-spec.md`; `docs/13-the-guards.md`; `CHANGELOG.md`; `briefs/claude-code-teams-and-orchestration-briefs.md`.
- **New:** `lib/spec-meter.mjs` (pure, Node-free: the skill key, the line classifier, the change-name reader, the per-line field reader, the stage and status texts, the write classifier, the fresh record); `test/spine/spec-meter.test.mjs`; `test/mod/spec-meter.test.ts` (the kit cases on both surfaces); under `test/fixtures/mod/`, the captured `skill.prompt`, `agent.spawn` (Explore) and keyed-line Bash results, scrubbed, with a `.mjs` mirror the kit imports; `openspec/specs/hooks/spec-meter/spec.md` on archive.
- **Untouched:** every settings hook, `hooks/hooks.json` (one module), `lib/launch-rule.mjs`, `lib/meter-quiet.mjs`, `lib/limits.mjs` (no threshold), `types/index.d.ts` (no new session-state key), the CLI and every module under `lib/` it runs (`ledger`, `artifacts`, `findings`, `ready`, `drift`, `notify` print what they print), the three skills (the sibling's lines are read, not edited), the drivers, the trajectory and every corpus. Nothing is written by the module on any host.
