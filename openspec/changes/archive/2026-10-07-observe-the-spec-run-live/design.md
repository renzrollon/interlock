## Goals / Non-Goals

**Goals:**

- A person running `/interlock:spec` in a terminal or the Desktop Code tab sees which change is being specified and the last thing the CLI printed about it, the moment it prints, and is told by the status line that the run stopped at its checkpoint.
- Every word the meter draws is a field the CLI printed, a count of events the engine raised, or a time the engine's clock gave; a line the meter cannot read is said to be unread, by name.
- One composer for the module's one status line, so the spec meter and the ship meter never write it at once.
- No new engine call, no new state key, no number, no new `deny`, and nothing written anywhere.

**Non-Goals:**

- Deciding or re-deciding any gate: re-running a line, reading the exit code as a verdict, reading `decisions.md`, a findings file or any artifact from disk.
- Recording the spec run: no trace, no corpus, no file. The artifacts, the findings file and the gate's exit are the record.
- Drawing stock `/opsx:propose`, a standalone `/interlock:explore`, or a spec flow run with `claude -p`.
- Changing what any skill prints or runs: the lines are `print-json-from-the-spec-gate-lines`'s, read as they are.
- A quiet word, a repeated-fact counter, a stage marker or a band above the prompt (D8, Open Questions).

## Decisions

### D1 — The run goes live on the spec skill's load as it crosses the module, observed and passed on

**Probe 1 outcome (task 1.1, 2026-10-07, Claude Code 2.1.291), and the trigger this change ships.** `skill.prompt` never reached a hooks module for a plugin skill: not for `/interlock:spec` typed in a tty session, not for the same line given to `claude -p`, and not for `interlock:explore` loaded through the Skill tool. The logger hooked the event with no matcher and recorded every other event of those sessions. Two events the module can already hook carry the load instead, and both were captured: `prompt.submit` with `text: "/interlock:spec add a hello file --no-explore"` verbatim (`test/fixtures/mod/prompt-submit-spec.json`; origin `sdk` under `-p`, `composer` when typed), and `tool.call{tool=Skill}` with input `{ skill: 'interlock:explore', args }` resolving `text: 'Launching skill: interlock:explore'` (`tool-call-skill-explore.json`). The fallback this decision named below (the first `openspec new change` after an `interlock drift --json`) was weighed against the same captures and rejected: in probe 1c the model ran `ls -la; git ls-files; …; interlock drift --json`, one compound line whose drift segment no begins-with reader sees, so that run would never have started. The person chose (2026-10-07) to start on the load as it crosses:

- **A typed load.** The existing `prompt.submit` hook, while `session.interactive`, asks the pure `promptSkill(e.text)` for the skill a prompt names: the first word of the text after leading whitespace when it is `/` followed by a skill name, else `null`. It reads that word and nothing else, before it returns `next(e)` exactly as it does today; it never builds a prompt and never reads one for a change name (D2). A prompt hook that awaited `next(e)` first could resolve only after the turn the prompt starts, so the read is made before the hand-on.
- **A Skill tool load.** A new `tool.call{tool=Skill}` hook returns `next(e)` at its first line unless `session.interactive`; otherwise it awaits `next(e)` once and, inside a `try` whose failure is one debug line, files the load when the result is not errored and `skillRole(e.skill)` names a role. It returns the result as it came.

`skillRole(name)` accepts the namespaced names only (a leading `/` is dropped): `interlock:spec` starts a run, `interlock:explore` and `interlock:review-artifacts` set the stage of a live run. A bare `spec` is not accepted: neither event carries the skill's text to tell another plugin's `spec` apart, and the engine named the plugin's skills by their namespace in every capture. `HOOKED_EVENTS` is unchanged (`prompt.submit` and `tool.call` are already there); `claude plugin validate` gains `tool.call{tool=Skill}` on `hooks:` (D11). Wherever the rest of this design names the `skill.prompt` hook, read these two observations; the pins that kept that hook from returning a text of its own (D10) apply to both, and the docs say that a host that stops raising either event for a skill load draws no spec run.

*As first designed, before probe 1:* one `on('skill.prompt', …)` hook with no matcher, so `claude plugin validate` records it as the bare `skill.prompt` and one hook sees the three skills the meter cares about. Its first line returns `next(e)` unless `session.interactive`. Otherwise it awaits `const r = await next(e)`, then, inside a `try` whose failure is one debug line, asks the pure module what the expansion was (`skillRole(e)`, D9) and returns `r` as it came. Nothing in the hook builds a `{ text }`, spreads `e` into `next`, or touches `r`.

- `spec`: a fresh spec record (`freshSpec()`) is set live with `startedAt` from the clock, replacing any record (`interlock spec: a new spec run replaced the previous one` on the debug log when the old one was live, at its checkpoint or handed over); the status line is set through the composer (D7) to `interlock spec: change: unknown until named`; the `interlock-spec` pane is opened with the shared opener, and when it resolves unplaced one toast says `/interlock-spec opens the spec meter`.
- `explore` and `review-artifacts`, while a spec run is live: the stage is set to that word and the composer redraws. Outside a live run they change nothing, so a standalone explore draws nothing.

*The key (probe 1).* The declaration's example is a bare name (`commit`) and the engine namespaces plugin skills as `interlock:spec` on the command line. `skillRole` accepts `interlock:spec`, `interlock:explore` and `interlock:review-artifacts`. If probe 1 shows the bare form for a plugin skill, `spec` is accepted only when `e.text` contains `GOAL MET: interlock spec stopped at the checkpoint.`, a line `test/skills.test.mjs` already pins in that skill, so another plugin's or the user's own `spec` skill never starts a run; `explore` and `review-artifacts` in the bare form are accepted only inside a live run, where the spec skill has just told the model to run them. Reading `e.text` is observing it; the pin in D10 keeps the hook from returning one.

*Why the skill load and not the CLI.* Stock `/opsx:propose` runs the same `openspec` lines in the same conversation (`docs/10-agentic-workflow-ship-and-spec.md:130`); a meter keyed on them would draw a spec run and then show `ledger: not run yet` and `checkpoint` lines for stages that flow never promised. *Why after `next(e)`.* The engine's expansion is resolved before the module opens a pane, so the pane open never sits inside the expansion's own path; the result is the engine's either way.

*Fallback if `skill.prompt` does not fire for a plugin skill (probe 1).* The run goes live at the first `openspec new change` that follows an `interlock drift --json` in the same session, both read from the `Bash` hook; stock OpenSpec flows run no `interlock drift`, so they still draw nothing. Spawns before the start are then not seen, and the explore line reads `explore: not observed (the run was recognised at its first change)`. `HOOKED_EVENTS` then does not gain `skill.prompt`, and the spec-meter requirement's first sentence and its happy-path scenario are amended to the fallback before §2 starts, which task 1.1 records here.

### D2 — The change name comes from the CLI's argv or JSON, and results are kept per name

`changeOf(kind, command, value)` in the pure module returns a name or `null`, in this order: the argv, tokenised with single and double quotes and cut at the first unquoted `|`, `;`, `&`, `>` or `<`: the positional after `openspec new change`; the value of `--change` on any `openspec` line (so `openspec instructions <id> --change "<name>" --json | node …`, which is otherwise unread, names the change from its command alone); the first positional after `interlock ledger`, `validate`, `ready` and `notify checkpoint`; the value of `--metrics` on `interlock gate`. Then, from a parsed result, a non-empty string `changeName` or `change`. A token that still holds `$`, a backtick or `<` after unquoting (an unexpanded variable, a placeholder) names nothing. A file path, the skill's text and a tool input other than the Bash command never name a change: the `Write` classifier (D4) files a write by its directory and never sets the name.

The record keeps `current` (the name the CLI named last) and `changes`, a map from name to that change's results: `status`, `ledger`, `validate`, `gate`, `ready`, `writes` and `findings`. `explore`, `drift`, `autonomy`, `stage`, `lastActivityAt`, `checkpointAt` and `handedOverAt` are the run's. A result whose line and JSON name no change is filed under `current`, or, before any name crossed, under an unnamed slot the pane does not draw (D6), so the edge scenario's `not run yet` lines hold. The pane draws `current` and lists every other name seen as `other changes named this run: <names>`.

*Why last-named and not first-named.* The skill continues an existing change with no `new change` line when asked (`skills/spec/SKILL.md:117`), and review-artifacts picks "the most recently modified" change when it has no name (`skills/review-artifacts/SKILL.md:22`); in both cases the CLI's latest argv is the best evidence of what the model is working on, and the other names stay visible.

### D3 — The Bash hook reads the flow's keyed lines, by field, and names what it cannot read

`lineKind(command)` classifies a command that begins, after leading whitespace, with one of: `openspec new change` (`new-change`), `openspec status` (`status`), `interlock drift` (`drift`), `interlock ledger` (`ledger`), `interlock validate` (`validate`), `interlock gate` (`gate`), `interlock autonomy record` and `interlock autonomy clean` (`autonomy`), `interlock ready` (`ready`), `interlock notify checkpoint` (`checkpoint`). It keys on the command words and not on `--json`, so a consumer repository still on the previous skill text has its ledger line classified and shown unparsed rather than ignored. `openspec instructions` is `naming-only`: its argv may name the change and its result is never read. Every other command is `null`.

The hook (as `speak-permission-prompts-and-guard-denials` leaves it) gains, before its existing branches: `if (!session.interactive || typeof e.command !== 'string') return next(e)`; `const kind = lineKind(e.command)`. A `null` kind on a command that is not a driver line returns `next(e)` at once, its result unread, which is every Bash call in a stock OpenSpec flow and every Bash call in a session with no spec run. A keyed kind while no spec run is live: one debug line the first time after a boundary or after the checkpoint (`interlock spec: a <kind> line crossed after the checkpoint; not drawn`, or `… with no live spec run; not drawn`), and `next(e)`. A keyed kind while the spec run is live joins the hook's one `await next(e)`, and after the existing ship reads (unchanged: a keyed `interlock` line during a live ship run is still read as a step record and logged as not one, as today) `applySpecLine($, kind, e.command, r)` runs inside its own `try`.

`applySpecLine` reads the text through the pure `readResult(kind, command, r)` and assigns only what it returns, so a reader that throws leaves the record as it was:

- The text read is `r.result.stdout` when that is a string, else `r.text` (probe 3 decides which carries the JSON on an errored result). A result carrying `persistedOutputPath` is unparsed with the reason `output too large to read inline`: the meter does not read the persisted file.
- The JSON is found as `emit` prints it: from the first line that is exactly `{` to the last line that is exactly `}`, so an engine prefix line (`Exit code 1`, if probe 3 finds one) or a stderr tail (`interlock gate`'s `metrics not written` warning) does not defeat the parse. Nothing else in the text is read.
- Each kind names the fields it needs, and a parsed object lacking them is unparsed with the reason `fields missing: <names>`: `status` needs `artifacts` as an array of objects with string `id` and `status` (`outputPath`, `requires`, `applyRequires`, `changeName` and `schemaName` are kept when present; `isComplete` and `isPlanningComplete` are never read); `drift` needs `unarchived` (array) and `stale.broken`, `stale.aging` (arrays), kept as counts; `ledger` needs boolean `blocking` (`needsHuman`, `invalidCount`, `missing`, `unparseable` kept); `validate` needs boolean `ready` and array `problems`; `gate` needs boolean `passed`, `counts.{blocker, warning, suggestion}` and array `malformed` (`metrics.written`, `metrics.path`, `metrics.reason` kept); `ready` needs boolean `ready` and array `blockers`, kept as a count. For `ledger`, `validate` and `ready`, an object with a string `error` and an array `candidates` and no verdict field is read as `{ error, candidates }`, drawn as the name not resolving.
- `new-change`, `autonomy` and `checkpoint` read no text at all. `autonomy` keeps only `record` or `clean`, the second command word: the line's `--blockers <n>` and the CLI's `L1 (0/3 clean)` text never reach the record.
- An unparsed result keeps `{ kind, unparsed: <first non-empty line, cut at 200 characters>, reason }` and leaves one debug line, `interlock spec: <kind> result not read (<reason>)`. It replaces that change's earlier result for the kind, because the earlier one is no longer the last thing the CLI said.

**Probe 3 outcome (2026-10-07, 2.1.291, headless).** A keyed line that exits non-zero (`interlock ledger … --json` blocking, `interlock gate … --json` blocked, `interlock validate "no-such-change" --json`) resolves `isError: true` with `result` a **string**, `"Error: Exit code 1\n<stdout>"`, and `text` `"Exit code 1\n<stdout>"`: the JSON is intact behind one engine prefix line, and there is no `stdout` field to read on that arm. A clean exit (`openspec status … --json`) resolves `result: { stdout, stderr, interrupted, isImage, noOutputExpected }` with `text` equal to `stdout`. No field carries the exit code; the prefix line names it as text, and the meter reads it no more than any other line outside the JSON. So `readResult` reads `result.stdout` when it is a string, else `text`, and `findJson` skips the prefix; the fallback for a text with no JSON was not needed. The captures are `tool-call-bash-openspec-status.json`, `tool-call-bash-ledger-blocking.json`, `tool-call-bash-gate-blocked.json`, `tool-call-bash-validate-unresolved.json` and `tool-call-bash-ledger-text.json` (the old text line, also exit 1). The probe used a `decisions.md` with two `needs_human` rows so the ledger capture carries the figures the delta spec's happy path names; a missing ledger is built by hand in the Node cases.

**Compound lines (probe 1, chosen 2026-10-07).** In both spec runs probe 1 drove, the model chained keyed lines: `openspec new change "add-hello-file" && openspec status --change "add-hello-file" --json`, `interlock autonomy clean review-artifacts explore spec; interlock notify checkpoint "add-hello-file"`, `ls -la; …; interlock drift --json`. Read by its first words alone, the second run never reached its checkpoint. The person chose to split: `specLines(command)` cuts the command at every unquoted `&&`, `||`, `;` and newline, and classifies each segment by `lineKind`, in order. A segment of a kind that reads no text (`new-change`, `autonomy`, `checkpoint`) or that only names (`naming-only`) is applied from any position, by its own argv. A segment of a kind that reads text (`status`, `drift`, `ledger`, `validate`, `gate`, `ready`) is read when it is the only such segment in the command, since `findJson` then finds the one JSON object the command printed; when two or more text kinds share a command, each is kept unparsed with the reason `compound command`, because the meter cannot tell whose output is whose. The segments are applied in command order, so the stage is the last keyed segment's. A command none of whose segments is keyed is passed on at the first line as before.

*Why the exit code is not needed (probe 3).* The record carries no exit code, and the sibling's `--json` puts the verdict field (`blocking`, `ready`, `passed`) in the text; the field is the fact the exit is computed from (`bin/interlock:2258`, `:1881`, `:1873`). The probe settles where the text is, not whether a verdict can be had. *Why `stdout` first.* It is the CLI's own output with nothing in front of it, and `text` is what the model reads, which the engine may wrap on an error. *Why unparsed and not `not run yet`.* The sibling's design wrote `not run yet` for a text line (its Risks); the delta spec here is the authority and is more precise: the line did run, and saying so with its first line is the spoken degradation `.claude/CLAUDE.md` asks for, while `not run yet` stays for a line that never crossed.

### D4 — Writes are counted on the sibling's Edit and Write hooks, and never set a status

The `{ tool: 'Edit' }` and `{ tool: 'Write' }` hooks `speak-permission-prompts-and-guard-denials` adds are reused: their first-line gate widens from `watching()` to `watching() || specWatching()`, they still await `next(e)` once, the guard-denial read still runs only while `watching()`, and while `specWatching()` and `r.isError !== true` the pure `writeOf(e.file_path)` files the write:

- a path with a `openspec/changes/<dir>/<file>` segment, `<dir>` not `archive`: one more write of `<file>` for `<dir>`, with the clock's time; the write is filed under `<dir>` and never names the change (D2);
- `.claude/handoff/explore-*.md`: the run's brief path;
- `.claude/metrics/review-artifacts-<dir>-<YYYYMMDD-HHMMSS>.json`: that change's findings path;
- anything else: nothing.

`file_path` that is not a string files nothing. No write changes an artifact's status: the table is the last `openspec status --json`, and a file written since reads in the writes section with its count and time and no status word beside it.

*Fallback.* If the sibling's probe 2 took its outcome (b) and the two hooks were not added, this change adds them with the same gate and the spec read alone; `HOOKED_EVENTS` is unchanged either way (`tool.call` is already there), and D11 records the two matchers on the `hooks:` line as this change's.

### D6 — What the status line and the pane say

**Status line:** `interlock spec: <who> · <stage>`, `<who>` the current change or `change: unknown until named`, and ` · <stage>` omitted until a stage exists. The stage is the last keyed event, composed by `stageText(entry)`:

| crossed | stage |
| --- | --- |
| explore / review-artifacts skill load | `explore`, `explore (<n> investigators)`, `review-artifacts` |
| `openspec new change` | `new change` |

`READY`, `NOT READY`, `PASS`, `BLOCKED`, `CLEAR`, `MISSING` and `UNPARSEABLE` are the CLI's own text words (`lib/artifacts.mjs:305-316`, `lib/findings.mjs:314-339`, `lib/ledger.mjs:412-440`), composed only from the field that computes them, never from text.

**Pane** (`/interlock-spec`, `ui.render{component=Pane, requestId=interlock-spec}`), drawn by `drawSpecPane` from `specPaneLines(spec)`, a list of `{ key, text, bold?, dim? }` the module maps onto `Box` and `Text` and nothing else:

- No run: one dim line, `no spec run is live in this session`.
- `spec-header` (bold): the change, or `change: unknown until named`, then ` · schema <schemaName>` when the last status named one.
- `status: not run yet`, or one `spec-artifact-<id>` line per artifact, `<id> · <status> · <outputPath>`, in the order the CLI listed them, then `spec-apply-requires`, `applyRequires: <ids>`.
- `spec-explore`: `explore: <n> investigators spawned` or `explore: none reported by this host`, then ` · brief <path>` or ` · no brief written yet`.
- `spec-drift`, `spec-ledger`, `spec-validate`, `spec-gate`, `spec-ready`: `<kind>: not run yet`; or the fields by their JSON names, e.g. `ledger: blocking true · needsHuman 2 · invalidCount 0 · missing false · unparseable false`, `validate: ready false · problems 2` followed by one `spec-validate-problem-<i>` line per problem verbatim, `gate: passed false · blocker 1 · warning 3 · suggestion 0 · malformed 0 · metrics <path>` or `· metrics not written (<reason>)`, `ready: ready true · blockers 0`; or `<kind>: not read (<reason>) · <first line>`; or `<kind>: change not resolved · candidates <names>`.
- `spec-autonomy`: `autonomy: record`, `autonomy: clean`, or `autonomy: not run yet`.
- A bold `writes` section: one `spec-write-<file>` line per artifact file, `<file> · written <n>× · last <ISO>` (or `· last time unknown`), and `spec-findings`, `findings file: <path>`; `no artifact writes yet` when none.
- `spec-last-activity`: `last activity <ISO>` or `last activity unknown`.
- `spec-checkpoint`: `checkpoint reached <ISO>` (or `checkpoint reached, time unknown`), present once the checkpoint crossed; `spec-handover`: `handed over to ship at <ISO>`, present once a ship launch took the line.
- `spec-other-changes`: `other changes named this run: <names>`, present when there are any.
- One dim line: `the artifacts on disk, the findings file and the gate's exit are the record`.

No row carries a tick, a colour, a threshold, `complete` or `ready to ship`. `last activity` is stamped from `$.clock.now()` at the skill load, each keyed line read, each write filed and each `Explore` spawn counted; a clock that cannot be read leaves the stamp as it was and is named once per spec run, the ship meter's rule (`clockNow`, `:186-203`) applied to the spec record.

### D7 — Three ends, and one composer for the one status line

`let spec = freshSpec()` at module level, `phase` one of `idle`, `live`, `checkpoint`, `handed-over`; `specWatching = () => session.interactive && spec.phase === 'live'`.

- **Checkpoint.** A `checkpoint` line, whatever its result, sets `phase = 'checkpoint'`, `checkpointAt` and the stage, after `next(e)` resolves. The line stays: the person reads it while the checkpoint waits for them. Later keyed lines are named once and passed on (D3).
- **Ship launch.** In the `Workflow` hook's accepted branch, before `run.phase = 'live'`: when the spec record is `live` or `checkpoint`, `phase = 'handed-over'` and `handedOverAt` is the `now` the guard read. A refused launch (the guard's own refusal returns before `next(e)`) or an errored or unaccepted result leaves the spec run as it was.
- **Boundary.** In `classic.SessionStart`'s boundary branch, beside `run = freshRun()`: `spec = freshSpec()` with `afterBoundary: true`, so the first keyed line after it is named once (D3). `startup`, `compact` and an unreadable source leave it.
- **Reload.** `session.start` sets `spec = freshSpec()` beside `run = freshRun()`; a spec run held before a reload is not drawn again, as the ship run is not.

**The composer.** One function, `setStatus($)`, is the module's only `$.ui.status(` call: `$.ui.status(run.phase === 'live' ? statusText() : spec.phase === 'live' || spec.phase === 'checkpoint' ? specStatusText(spec) : undefined)`. The five existing calls (Context), and any a preceding change added, become `setStatus($)`; the ship cases read the same lines, because with no spec run the composer returns exactly what each call passed before (`statusText()` while live, `undefined` at close, halt and the boundary). The `interlock-spec` command is registered in `session.start` after the three earlier ones. The pane is never closed by the module.

**Probe 4 outcome (2026-10-07, 2.1.291, tty).** A scratch plugin set `$.ui.status('PROBE-STATUS-A')` in `prompt.submit` and `$.ui.status('PROBE-STATUS-B')` from its Bash hook fifteen seconds later. The screen read `⚠ probe-status: PROBE-STATUS-A` until the second call, then `⚠ probe-status: PROBE-STATUS-B`, never both: the declaration holds, one line per plugin, replaced by each call, behind the plugin's name.

*Why one composer and not two writers (probe 4).* The declaration says one line per plugin, replaced by each call; two writers would leave whichever wrote last, and the spec line would overwrite a live ship position on the next keyed line. With one composer the ship position wins while a ship run is live whatever the probe shows, and the probe only records whether the engine interleaves, which would matter to a future second plugin, not to this module. *Why the hand-over is in the `Workflow` hook.* It is the one place both facts meet: the launch rule's own judgement of a ship launch and its acceptance, already read there, so the hand-over adds no second reading of the launch.

### D8 — No quiet word and no counter in v1

The spec meter draws no `quiet <n> min` and imports nothing from `lib/meter-quiet.mjs`: spec waits on a person by design (the intent question, the bug-fix evidence, pinned versions, continuity's ledger rows, the checkpoint), so the figure would measure the person, and research §7 says so. It counts no repeated fact (`same ready artifact on 3 consecutive status calls`): the count itself is display-only, but the first person to read `3` asks "is 3 bad?", and the only honest answer is a threshold this repository keeps in the CLI. `last activity <ISO>` and the CLI's last answer stand in for both. The ship meter's interval is never started for a spec run.

## Risks / Trade-offs

- [A file written is read as a valid artifact] → the table is only what `openspec status --json` printed; writes are counts and times with no status word; the pane says the artifacts on disk are the record; `isComplete` is never read and `complete` never drawn, pinned.
- [Stock `/opsx:propose`, or a second flow in the same session, draws a spec run] → only the spec skill's prompt expansion starts one, with the bare key checked against a pinned line (D1); within a live run, another change's lines file under their own name and the pane lists them, never merged.
- [The autonomy line is read as a score] → only `record` or `clean` is kept; no level, count or `clean`-ratio text from the CLI reaches the status line or the pane, pinned by the kit case.
- [The wrong change among several] → `change: unknown until named` until the CLI names one; the last-named change is drawn and every other is listed; a path never names a change.
- [Two meters on `--continue`] → the accepted launch ends the spec run before the ship run is live, inside the hook that judges the launch, and one composer owns the line (D7).
- [Silent prose drift: a reword drops `--json` or a keyed line] → the sibling pins every keyed line by token and in order; this change pins that every fenced `openspec`/`interlock` line in the three skills is classified or named as unread, and that every classified kind still occurs; a line that crosses without JSON is drawn `(unparsed)` with its first line, never silently absent.
- [A line the model composes differently (`cd x && interlock ledger …`)] → it does not begin with the keyed words and is passed unread, so its kind stays `not run yet`; the docs name the form the meter reads. Widening to compound commands would read lines the skill never ran.
- [A non-interactive session (`claude -p "/interlock:spec …"`, the SDK, a runner lane)] → every added hook returns at its first line, as the meter does; nothing is drawn or kept.
- [An output too large to keep inline (a gate over many findings) reaches the module as a preview] → read as unparsed with `output too large to read inline`, named on the debug log; the persisted file is not read.
- [The engine prefixes a plugin's status line with its name, so it reads `interlock: interlock spec: …`] → the same doubling the ship line has (quiet-time D7, probe 2); the text is pinned by both meters' kit cases and is left as it is.
- [A subagent that preloads the spec skill starts a run in the lead session's meter] → no agent in this plugin preloads it; the event carries no agent field to tell, which probe 1 records; the record starts over at the next real load.
- [The hand-over clears the line until the ship run's first step] → the ship meter's own behaviour at launch; the line is never both.
