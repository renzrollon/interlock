## Goals / Non-Goals

**Goals:**

- One toast, the host's word, once per agent per run, raised from the hook that already receives it.
- Two pane lines from the read the pane already makes, showing what the host answered and saying what it did not.
- No pin moved, no number added, no new call, no new event, no new state key.

**Non-Goals:**

- Naming a cause for a stopped lane, or deciding anything from the reason word. The driver's banner and the close summary remain the verdict and the record.
- Handing the CLI the reason word, or the plan windows, for the receipt (the two residual Brief 9 items, `draw-the-ship-run-live/proposal.md:67`).
- Any dollar figure of the module's own: no `MODEL_PRICES`, no token sum priced, no per-agent or per-run cost. The engine's `cost.usd` is a session figure and is labelled as one.
- Showing `refusal.category` and `explanation`, `isAborted`, `startedAt`, or a context breakdown. The breakdown is not free, and the rest is a later display decision.
- Hooking `session.measure`, a cost word on the status line or the spinner, or any toast on `answer`.
- Rewording the plan-window line for the no-window case, the status line or any other pane text.

## Decisions

### D1 — The toast is the host's reason word, raised in the existing `turn.complete` hook, once per agent per run

Inside the hook's existing gate (`session.interactive && run.phase === 'live' && e.agentId`), after the record is updated as today: when `str(e.reason)` is a word other than `answer` and the agent's record has not toasted yet, the module sets `a.endToasted = true` and calls `$.ui.toast(text)` with the text D2 states. The call sits in its own `try`; a refused toast is one debug line (`interlock meter: the turn-end toast for <id> was refused: <message>`) and the hook still returns `next(e)`. A missing or non-string reason raises nothing and is not logged: the row shows no reason, as today. The `closing` phase (after a halt or close step, before the close record) keeps the hook's existing `live`-only gate, so lanes the halt stops are not toasted one by one: the halt is already spoken by its step.

*Why the reason word and nothing else.* The word is the host's enum (`TurnCompleteReason`), and repeating it verbatim is the one way to say what happened without interpreting it. `isAborted` is redundant with `reason === 'aborted'` and would be a second reading of one fact. A refusal's `category` and `explanation` are the API's words too, but they are prose with no fixed set and belong, if anywhere, on the agent row; this change keeps the toast to one line.

*Why a word other than `answer`, not the three named words.* A later host that adds a reason word would otherwise be silent, which is the degradation this module exists to speak. The kit pins the three declared words and one undeclared word; the design treats `answer` as the only quiet case.

*Why once per agent.* A lane agent runs one loop, so one turn ends it; a resumed or forked agent may end again, and a toast per end would repeat one fact. The agent row carries the latest reason and duration regardless.

*Alternatives.* Toasting every turn end, `answer` included: a toast per lane per batch is the noise the inert-outside-a-run rule exists to prevent, and a lane that answered is drawn on the pane already. A status-line word: the status line is the run's position and the quiet word, both of which clear themselves; a stopped lane has no clearing event. Adding the text to `run.banners`: the banner list is "the list the CLI emitted" (`hooks/mod.mjs:8-9`), and the toast is the host's fact, not the CLI's.

*Probe 1 (task 1.1(a)).* Whether a Workflow-spawned run agent whose turn ends abnormally raises `turn.complete` with `agentId`, `reason` and `durationMs` on 2.1.289. Two provocations from a scratch workflow under `$TMPDIR` through `scripts/host-probe.mjs`, with the scratch logger mod the earlier captures used (`host-probe-harness.md`, "Engine event capture"): (i) `--mode tty`, a workflow whose one `agent()` runs a long Bash sleep, interrupted from outside the session with `tmux send-keys Escape` (and, if that does not reach the background agent, by killing the Bash child), expecting `reason: 'aborted'`; (ii) `--mode headless`, a workflow whose one `agent()` names a model id the API rejects, expecting `reason: 'error'`, or the runtime's own refusal before any turn. The captured input, scrubbed, is pinned as `test/fixtures/mod/turn-complete-subagent-<reason>.json` beside the `answer` one. If neither provocation produces a non-`answer` reason for a Workflow agent, the kit cases still pin the module on the declared enum, this section records that the toast is unproven on the host, and the docs say the toast fires "when the host reports" such an end.

*Probe 1, recorded 2026-10-06 (the 2.1.289 binary path now reports 2.1.291; scratch logger mod and workflows under the session scratchpad, no `--plugin-dir <repo>`).* (i) `--mode tty`, one `agent()` in `sleep 240`: an Escape sent with `tmux send-keys` reached nothing, because the lead turn had already ended and the composer was idle; a second typed prompt had the session call `TaskStop` on the workflow task, and the agent's turn ended with `turn.complete` `{ agentId: 'ad89469ac01966c2b', reason: 'aborted', isAborted: true, durationMs: 74366, usage }`. **An abnormal end of a Workflow agent does reach the module, with all three fields.** Scrubbed (`agentId` → `a1`, `turnId` dropped) and pinned as `test/fixtures/mod/turn-complete-subagent-aborted.json`. (ii) `--mode headless`, one `agent()` naming `claude-nonexistent-0`: no `error`. The runtime logged `[claude-code:unrecognized_model]` and served the agent on `claude-sonnet-5-5`, which answered (`reason: 'answer'`); an unknown model id is not a way to provoke `error` on this host, and `error` and `refusal` stay pinned on the declared enum under the kit only. Neither session raised `agent.spawn` for a Workflow `agent()`, so the join stays dormant and the live toast reads `lane unknown`; agent ids are 17 hex characters.

### D2 — The toast names the joined lane's title, else `lane unknown`, and always the agent id

Text: `<lane> · agent <id> · turn ended: <reason>`, where `<lane>` is the joined wave row's `title` (which is the CLI's descriptive title, or the label when a spawn carried none, `hooks/mod.mjs:340`) or `lane unknown` when no row is joined. A joined example: `1.1+5 · Add the relaunch guard to… · agent a1 · turn ended: error`. The common case on 2.1.289, where the join is dormant: `lane unknown · agent a1 · turn ended: error`. The engine draws the toast under the plugin's name, so the text carries no `interlock:` prefix (the status line's double prefix recorded in `show-quiet-time…/design.md` D7 is the reason to leave it out). A small `rowForAgent(a)` beside `laneForAgent` returns the row rather than its label; `laneForAgent` and the agent row's text are unchanged.

*Why the title and not the label.* The label (`1.1+5`) is the key every record joins on; the title is what the wave table and `/workflows` show a person (commit `4a1c06f`), and a toast is for the person. *Why the agent id always.* While the join is dormant the id is the only handle that matches the toast to a pane row, and when the join works it is the row's second field anyway. *Why no duration.* The declaration's example toasts one, and the row shows it; a toast that must fit a small box carries the one fact the row cannot push.

### D3 — The toast is earlier than the record, and the record is unchanged

On the Workflow host the driver raises `AGENT RETURNED NO RESULT` when `agent()` resolves null (`workflows/ship.js:305-311`) and folds it into the close through `--host-banners` (`:547-557`), so the meter's banner toast for it comes with the close record, after every later wave has run. The research note that proposed this change (`research_notes/Interlock mods beyond the ship meter/candidate_mod_catalog.md`, candidate 7) placed that banner on the next `record-batch` step; it is not there, which makes the turn-end toast the only live word about a stopped lane on that host, not merely an earlier one. The toast hands the CLI nothing and changes no step, no banner, no trajectory field and no exit code: a person who sees `turn ended: error` and then reads `AGENT RETURNED NO RESULT: <label>` in the close summary is reading one fact twice, the second time as the record. On the runner host nothing draws and `LANE STOPPED BY HOST` is the CLI's own.

### D4 — The pane's session lines come from the read it already makes, as answered, with no breakdown

`drawPane` keeps its one `await $.session.usage()`, moved ahead of the `plan windows` header so three consumers read one answer: a new bold `session` section with two keyed lines, `session-context` and `session-cost`, then the plan windows as today. The read's `try` keeps the answer or the failure's message; the plain call is made with no argument, because `breakdown` makes the engine count categories with the token-count API (`claude-code.d.ts:2601-2605`) and the pane is drawn often. Fields are read as answered: `context.tokens`, `context.window`, `context.percent` and `cost.usd`, each used only when it is a finite number. No percent is computed from `tokens` and `window` when the host left `percent` out: the fill is then said to be not yet reported, which is what the declaration says that absence means.

*Why poll at draw and not hook `session.measure`.* The event would add a hooked event to `HOOKED_EVENTS`, which this change exists not to do, and the pane is already invalidated at every step, request answer, turn end and quiet-word change, so a drawn pane is at most one draw stale. *Why the session's figure and not the run's.* `cost.usd` is "summed over every priced API response this session", which includes the lead session's own turns before and after the launch; the line says so (D6), and the receipt stays the run's record. *Why not on the status line.* A cost that changes every turn beside the position would draw attention to a figure the module did not make and cannot bound.

*Probe 2 (task 1.1(b)).* The exact `$.session.usage()` answer at runtime on 2.1.289: a scratch logger mod under `$TMPDIR` that writes `JSON.stringify(await $.session.usage())` to a scratch file from `session.start`, from a `turn.complete`, and from a `command.run` typed after a response, in a `--mode headless` session and in a `--mode tty` session. Recorded here: whether `cost` is present in each mode, whether `context.tokens` and `context.percent` appear after the first response, and whether the figure moves while a Workflow agent works (the open question on subagent requests). If `cost` is absent in a mode, the line says `session cost not reported by this host` there and nothing else changes; if `context` carries fields the declaration does not name, they are ignored.

*Probe 2, recorded 2026-10-06 (2.1.291).* Headless and tty answered the same shape. At `session.start`: `{ startedAt, context: { window: 200000 }, rateLimits: [], cost: { usd: 0 } }` — no `tokens` or `percent`, and `rateLimits` empty even on a subscription until the first response. After the first response, `context` carries `tokens` and `percent` (`{ tokens: 37133, window: 200000, percent: 19 }`) and `rateLimits` the `five_hour` and `seven_day` windows. **`cost` is present in both modes**, a zero before any request. **`cost.usd` moves with a Workflow agent's own requests**: read from that agent's `turn.step`s it went 0.1435 → 0.1821 → 0.1851 while the lead session was idle. A `command.run` typed after a response (`/probeusage`, tty) read `{ context: { tokens: 53042, window: 200000, percent: 27 }, …, cost: { usd: 0.1767308 } }`, raw floats with more than four decimals, which D6's `toFixed(4)` exists for. `context` carried no field the declaration does not name.

### D5 — No figure of the module's own, pinned statically

The module never imports from `lib/limits.mjs` directly (it reaches `LIMITS` through `lib/meter-quiet.mjs` and `lib/launch-rule.mjs` for the two caps and the ledger age) and never names `MODEL_PRICES`, `perMillionTokens` or `cacheMultipliers`; it sums no token field into a price and divides nothing. Two regression pins in `test/spine/mod-pins.test.mjs` hold this: the module's source contains none of those three tokens, and every `$.session.usage(` occurrence is the bare `$.session.usage()`. Both are green on today's module and stay green; they exist so the next change that wants a dollar figure has to move a pin by name, as the archived reservation (`…/surface-prompt-cache-cost/design.md:23`) intended.

### D6 — What the pane says

- `session-context`: `context <tokens> of <window> tokens · <percent>% used` when all three are finite numbers; `context <tokens> of <window> tokens` when `percent` is absent; `context: window <window> tokens · fill not yet reported` when `tokens` is absent; `context not reported` when `window` is not a finite number (the kit's default `context: {}` reads this way).
- `session-cost`: `session cost $<usd> · the engine's total for this session, not the run's` with `<usd>` as `usd.toFixed(4)`; `session cost not reported by this host` when `cost` is absent or `usd` is not a finite number.
- A failed read: `context unavailable: <message>`, `session cost unavailable: <message>` and, in place of the plan-window fallback, `plan windows unavailable: <message>`. A read that answers an empty `rateLimits` keeps today's `none reported (off a subscription the session has none)`: that text was written for the empty answer, and only the failed read is moved off it.
- No colour on any of these lines, no threshold word, and the existing `live figures; the close summary and the receipt are the record` line stays above the sections.

*Why four decimals.* The engine's `/cost` prints its total to four decimals; two would print `$0.00` for the first requests of a run, which reads as a measured zero, and the raw number can carry floating-point noise. The width is a format, not a figure: the number is the host's. *Why the formatting lives in the module.* There is no rule to hold: no cap, no comparison, no derived value. `tokensText` and `lastActivityText` are the precedent for display formatting inside `hooks/mod.mjs`, and the kit pins the text; a `lib/` module exists for rules a Node test must own.

## Risks / Trade-offs
