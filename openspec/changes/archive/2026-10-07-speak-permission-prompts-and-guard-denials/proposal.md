## Why

A ship run that stops on a permission prompt is "the one interruption the runtime cannot prevent" (`docs/04-when-it-stops.md:129`), and today it is spoken twice, both times after the fact: the recorder writes one file per `PermissionRequest` and `PermissionDenied` while a run is live (`hooks/recorder.mjs:31-33,153-169`), and `run close` counts those files into `PERMISSION PROMPTS DURING RUN: <n>` and `AUTO MODE DENIED <n> TOOL CALLS (<tools>)` (`lib/run.mjs:4102-4110`; `docs/04-when-it-stops.md:441-450`). While the run is waiting, the status line reads the last step and, after five minutes, `quiet <n> min`; nothing says that the quiet is a prompt waiting for the person at this terminal. The engine already raises the same two events to a hooks module as `classic.PermissionRequest` and `classic.PermissionDenied`, with the settings hook's whole stdin payload as `e` (`claude-code.d.ts:1066-1091`; the inputs at `:6888-6921`: `tool_name`, `agent_id`, and on a denial the host's `reason`), and the module runs before the settings hooks (`:1075-1077`), so the meter can say it the moment it happens and write nothing. This is the mod side of what the briefs call Brief 4's permission-event half, which "may still land as its own small change" (`briefs/claude-code-teams-and-orchestration-briefs.md:1038`); the recorder stays as it is.

The four settings guards have the same hole. Each denies with a reason that begins with its own name (`hooks/guard-tests.mjs:43,101-106`, `hooks/guard-tasks.mjs:31,98-104`, `hooks/guard-commit.mjs:24,69-74`, `hooks/guard-relaunch.mjs:46,64-69` over `lib/launch-rule.mjs:151-158`), in the `PreToolUse` deny shape `hooks/_shared.mjs:44-56` prints, and "today a denial reaches only the blocked agent as tool-error text" (`docs/13-the-guards.md:25`). A guard that denies only to a subagent is a run degrading with the operator unaware, the silent fallback `REVIEW.md:19` ranks Important. The engine's declaration says what a module sees of it: a settings hook's deny "ends the call with the errored result a session's `tool.call` hooks see (`isError`, the reason as `text`)" (`plugin-authoring/reference.md:68`; `ToolCallResult` at `claude-code.d.ts:11810-11870`). The in-process launch guard already computes its own refusal in the module (`hooks/mod.mjs:529-533`) and says nothing to the person either.

## What Changes

- **A permission prompt is spoken as it happens.** While a run is live, the module hooks `classic.PermissionRequest` and `classic.PermissionDenied` beside its other hooks. A request raises one toast naming the tool and the lane (the wave row's title where the agent joined one, `lane unknown` where it did not, `this session` for the main thread), appends ` · prompt waiting since <ISO>` to the status line and the spinner suffix, and lists the prompt on the pane. A denial raises one toast with the tool, the lane and the host's own `reason`. The pane counts both in the close summary's words, `permission prompts: <n>` and `auto mode denied <n> tool calls (<tools>)`, so the figure the person watched is the figure the close prints. The tool's input and the host's permission suggestions are never shown, as the recorder never writes them.
- **The waiting word clears on the engine's own evidence, not on a timer.** The declaration has no "permission resolved" event. A prompt is held per thread (the event's `agent_id`, or the main thread) and cleared when that thread makes its next model request (`turn.step`), because an agent asks again only after its tool call resolved. Parallel lanes keep stepping while one lane waits, so the clear is per thread, never the next activity anywhere. The list is emptied when the run ends at the close, the halt or the session boundary, as the status line is.
- **A guard's denial is repeated in the guard's own words.** The module's `tool.call` hooks on `Bash` and `Workflow` already see the result; they gain two siblings on `Edit` and `Write`, mirroring the manifest's `Edit|Write` matcher. When a result the engine hands back is errored and its text carries one of the four guard names, one toast repeats the text from that name on, once per distinct text per run, and the pane counts `guard denials: <n>` by guard. The module computes nothing: an errored result that names no guard is ignored, and the result is returned as it came. The in-process launch guard's own refusal, the one pinned `deny`, is toasted in the same words the moment the module returns it, and the pane gains `launch guard: next launch allowed`, `launch guard: next launch refused: <reason>` or `launch guard: facts unreadable; the next launch is allowed`, from the same state read and the same rule function the guard's branch already uses.
- **Which pins move.** `HOOKED_EVENTS` in `test/spine/mod-pins.test.mjs` gains `classic.PermissionRequest` and `classic.PermissionDenied`; the two new `tool.call` matchers add no event name. `ALLOWED_CALLS` is unchanged, the forbidden tokens are unchanged (`tool.check` stays forbidden: observing it is the rejected mechanism at `briefs/…:1353`), and the one `deny` stays the launch rule's verdict on its one pinned line. A new pin reads the four guard files and asserts the module's guard-name list is exactly their `GUARD` constants, so a renamed guard fails before a session loads the module. `claude plugin validate --strict` gains four `hooks:` entries and no `calls:` entry; the design records the expected lines against the archived quiet-time design D7 baseline.
- **Pure text rules live under `lib/`.** A new Node-free `lib/meter-refusals.mjs`, the way `lib/meter-quiet.mjs` holds the quiet word, carries the guard-name list, the reason slice, the waiting word and the pane lines, tested under `node --test`; the module holds no number and restates no reason. No `lib/limits.mjs` key is added: nothing here is a threshold.
- **Docs and the changelog.** `docs/13-the-guards.md` adds the two classic events to the module's row and section, says that on a mods host a guard's denial is also toasted to the person, and adds the launch-guard pane line; `docs/04-when-it-stops.md` says, beside `PERMISSION PROMPTS DURING RUN`, that the meter speaks each prompt live and how its count and the close's can differ; `docs/07-cli-and-configuration.md` lists the toast, the suffix and the pane section under the ship meter; `CHANGELOG.md` Unreleased carries it; `briefs/claude-code-teams-and-orchestration-briefs.md` gets a dated note that Brief 4's permission-event half is taken up on the classic events and not on `tool.check`.
- **Probes come first, and one can shrink the change.** (1) In a `--plugin-dir` terminal session on 2.1.289, do `classic.PermissionRequest` and `classic.PermissionDenied` reach the lead session's module for a background Workflow agent's tool call, with `tool_name` and an `agent_id` that matches the `agentId` on that agent's `turn.step`? (2) How does a settings hook's `PreToolUse` deny reach a module: as the errored `tool.call` result with the reason in `text`, as a `classic.PermissionDenied`, or neither, and with what text exactly? If (2) finds no reason text the module can read, the guard half shrinks to the in-process launch guard's toast and pane line, which need no probe, and the delta spec is narrowed before implementation. If (1) finds no `agent_id`, the lane reads `lane unknown` and the clear rule degrades to the next request in the session, and the design says so.
- **Serialization.** This change touches `hooks/mod.mjs`, `test/mod/meter.test.ts`, `test/mod/relaunch.test.ts`, `test/spine/mod-pins.test.mjs`, `docs/13-the-guards.md`, `docs/04-when-it-stops.md` and `CHANGELOG.md`, so it lands after `speak-lane-turn-ends-and-session-cost` and before `show-preflight-and-interrupted-runs-at-session-start`, `draw-the-wave-board-in-the-meter-pane` and `observe-the-spec-run-live`, which touch the same files. `draw-wave-plan-and-handoff-graph-from-the-cli` and `print-json-from-the-spec-gate-lines` share no file with it.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `hooks/ship-meter`: a new requirement for the spoken refusals (permission prompts and auto-mode denials from the classic events, the four settings guards' denials from errored results, the in-process launch guard's own refusal); the pane requirement gains the refusals section (the two counters, the waiting prompts, the guard-denial count, the launch-guard line); the inertness requirement gains the one toast allowed outside a live run, the launch guard's; the observe-only requirement's recorded hooks gain the two classic events and the two tool matchers, its calls are unchanged, and the classic answers pass through untouched.
- `hooks/launch-guard`, `hooks/tool-guards`, `hooks/agent-recorder`: checked and unchanged. The guards' decisions, words and transport are what they were, and the recorder keeps writing its files; what this change adds is a second reader of those words, specified under `hooks/ship-meter`.
