## Context

See proposal.md for the motivation. What shapes the approach:

- **The module today.** `hooks/mod.mjs` keeps one module-level `run` (`freshRun()`, `hooks/mod.mjs:88-116`) and one `session` flag, gates every meter hook on `watching()` (`:119`: interactive, and the run `live` or `closing`), composes the status line from `position()` and the quiet word (`shown()`, `:176`), toasts each banner once per text per run through `run.toasted` (`:348-354`), and draws the pane from the tallies (`drawPane`, `:410-479`). The launch guard's branch reads `$.state.get(LEDGER)` and `$.clock.now()` through `guardFacts` (`:131-140`), decides with `decideLaunch` and returns the one pinned refusal (`:529-533`). `test/spine/mod-pins.test.mjs` pins the allow-list (`:31-49`), the hooked event names (`:62-73`, read by `on('<name>'` so a matcher adds no entry, `:272`), the forbidden tokens (`:76-89`), exactly one line spelling the refusal (`:55`, `:198-221`: any other line containing `deny` fails, and `verdict` is assigned once), and the state keys against `types/index.d.ts`.
- **The permission events, from the 2.1.286 declaration.** Every settings-hook event is hookable as `classic.<Event>`, `e` being the hook's whole stdin input, base fields included (`claude-code.d.ts:1059-1091`); the chain is managed settings hooks, then the hooks modules, then the other settings hooks as core (`:1075-1077`), so the module's hook runs before the plugin's own recorder. `PermissionRequestHookInput` carries `tool_name`, `tool_input` and `permission_suggestions` and no reason (`:6916-6921`); `PermissionDeniedHookInput` carries `tool_name`, `tool_input`, `tool_use_id` and `reason` (`:6888-6895`); both inherit `agent_id?` and `agent_type?` from `BaseHookInput` (`:673-690`). The classic answer a module may add is `decision` (PermissionRequest) or `retry` (PermissionDenied) (`:1150-1163`, `:1198-1199`); this module adds neither. The declaration has no resolved-prompt event. The recorder's captured payload (`test/fixtures/hooks/permissionrequest.json`, 2.1.274 headless, a Workflow subagent's `Write`) carries `agent_id` and `agent_type: workflow-subagent`; its denial fixture is a documented shape, never provoked (`permissiondenied.json`).
- **A settings hook's deny, as a module sees it.** `tool.call`'s `next(e)` "runs the hooks beneath, then core (the permission prompt, the tool itself)" (`claude-code.d.ts:3664-3671`), and the resolved result from core is `{ ref, result, text, isError?, isReadOnly? }`, the error arm "present only when the tool reported an error (it threw, was interrupted, or answered an error): `text` is what the model read" (`:11810-11875`). The kit states the deny case outright: `$.tool.call` raises `classic.PreToolUse` beneath every plugin's `tool.call` hook, "so a deny ends the call with the errored result a session's `tool.call` hooks see (`isError`, the reason as `text`)" (`plugin-authoring/reference.md:68`; `claude-code.d.ts:13686-13693`). `tool.call` fires for a subagent's calls with `agentId` set (`briefs/…:972`, mods-5; `test/fixtures/mod/tool-call-bash-interlock.json`). The guards print their reason through `deny()` in `hooks/_shared.mjs:44-56` as `permissionDecisionReason`, each reason opening with the guard's `GUARD` constant (`guard-tests`, `guard-tasks`, `guard-commit`, `guard-relaunch`); whether the `interlockGuard` detail object reaches `text` is not stated anywhere and is not needed.
- **The lane join is dormant.** `agent.spawn` did not fire for a Workflow `agent()` on 2.1.289 (`openspec/changes/archive/2026-10-05-draw-the-ship-run-live/design.md:141-142`), so `laneForAgent` finds no row and agent rows read `lane unknown`; a toast naming the lane will read the same until a host raises the event.
- **The close's figure.** `run close` counts the recorder's files: `permissionPrompts` is the number of `request` files and `autoModeDenials` the `denied` ones, with the distinct tool names (`lib/run.mjs:4102-4110`). The recorder counts every such event in any session working in the root while the marker is live (`docs/04-when-it-stops.md:450`); the module can count only what crossed its own session while its run was live. The two agree in the ordinary single-session run and the close's line is the record, which the pane already says of every figure.
- **The rejected transport.** `tool.check` is where a mod could approve a call a `PreToolUse` hook blocked, and in auto mode an approval there skips the classifier (mods-6); the briefs reject it and leave "observing `tool.check` for the permission-event half of Brief 4" as a separate question (`briefs/…:1353`). This change answers it: no. The classic events carry the same facts with no verdict in reach.
- **The precedent for a pure rule.** `lib/meter-quiet.mjs` holds the quiet word's text and reads its caps; `lib/launch-rule.mjs` holds the guard's words. Both are Node-free, imported by the module, and walked by the pins' import checker.

## Goals / Non-Goals

**Goals:**

- The person at the terminal learns of a permission prompt, an auto-mode denial and a guard's denial the moment the host raises it, in the host's or the guard's own words, with the tool's input never shown.
- The waiting word clears on the engine's own evidence that the prompted thread moved on, per thread.
- The counts on the pane are the close summary's counts in the close's words, for the ordinary run.
- The in-process launch guard's verdict is visible: its refusal is toasted, and the pane shows the rule's current ruling over the session's record.
- No new engine call, no new state key, no number in the module, no new `deny`.

**Non-Goals:**

- Answering, suppressing or retrying a prompt; setting `decision` or `retry` on a classic answer; hooking `tool.check`.
- Reading the recorder's files back, or writing anything: the recorder and the close stay the record.
- Correlating a prompt to its tool call by id, or judging what a denial cost the run (`docs/04:450`: "a denial may or may not have changed what the agent reported, and the count cannot say which").
- Changing any guard's reason, transport or fail-open table, or the recorder's registrations.
- A toast for a settings-hook deny that names no Interlock guard: another plugin's denial is its own to speak.

## Decisions

### D1 — The transport for a permission event is the classic mirror, read before the settings hook

`on('classic.PermissionRequest', …)` and `on('classic.PermissionDenied', …)`, each returning `next(e)` at its first line unless `watching()`, and otherwise reading three fields and nothing more: `e.tool_name` (a non-empty string, else the event is unreadable), `e.agent_id` (a non-empty string, else the main thread), and on a denial `e.reason` (a string, else "no reason given"). The display work runs inside a `try` whose failure is one debug line, and the hook returns `next(e)` in every case, so the chain's answer is the settings layer's. `tool_input`, `permission_suggestions` and `tool_use_id` are never read, so there is nothing to leak. An unreadable event is one debug line: `interlock meter: a permission event carried no tool name; not drawn`.

*Why not `tool.check`.* It is the rejected mechanism (Context). *Why not the recorder's files.* `$.fs.read` is a new allow-list entry and a file read per event, for facts the engine hands the module for free. *Why before the recorder.* The chain order puts a module above the plugin's own settings hooks, so the module's toast lands before the recorder's file exists; nothing depends on that order, and the two never meet.

*Probe 1 settles the engine fact this leans on:* that the classic events reach the lead session's module for a background Workflow agent's tool call, and what `agent_id` carries (D2).

*Probe 1, answered (2026-10-07, Claude Code 2.1.291): they do not, and this decision is withdrawn.* In a terminal session a Workflow agent's `Write` raised the permission dialog in the lead terminal ("Create file · from the \"probe-write\" workflow"); the scratch logger's `tool.call` hook on `Write` entered with `agentId` `ab422061837409f6b` and resolved 63 s later, after the dialog was answered, with no `isError` and the tool's own text, and its `turn.step` hook saw the same `agentId` before and after. No `classic.PermissionRequest`, `classic.PreToolUse`, `classic.PostToolUse` or `classic.Notification` reached the module. A `-p` session whose main thread asked for a `Write` with no allow rule resolved the call errored (`Claude requested permissions to write to … but you haven't granted it yet.`) with no classic event either, and a minimal module hooking `classic.UserPromptSubmit` and a `classic.*` glob next to a `session.start` hook printed its `session.start` line and nothing for the typed prompt or a typed `/clear`. On this engine no classic event reaches a hooks module at all, whatever the declaration says ("Each fires wherever the engine runs the classic hook"). D1 to D3's permission half is not built: no `classic.PermissionRequest` or `classic.PermissionDenied` hook, no waiting word, no permission counters; the recorder's files and the close's count stay the only record (D9).

### D2 — A prompt is held per thread and cleared on that thread's next model request

*Withdrawn with D1 (probe 1): no permission event reaches the module, so nothing is held. The decision is kept below as the design a later engine that delivers the classic events would start from.*

`run.waiting` is a map from a thread key to `{ tool, who, since }`: the key is `e.agent_id`, or `main` when the event carries none; `since` is the module's clock read at the event (`clockNow($)`, `null` when it rejects), never a stamp of activity, because a prompt is the run not moving. The entry is removed when:

- a `turn.step` enters carrying the same key (`e.agentId`, or `main` when absent), read before the hook's existing live-run gate so the main thread's request counts too. An agent loop is sequential: its next model request follows the tool result of the call that prompted, so the next request is the engine's own evidence that the prompt resolved, approved or denied;
- a `classic.PermissionDenied` for the same key crosses: the host decided for that thread;
- the run stops being live: the `close` or `halt` step and the close record (`applyRecord`), the session boundary (`classic.SessionStart`), a new accepted launch and `session.start`, each of which already clears the status line or starts a fresh run.

The count `run.permissionPrompts` is never decremented; the waiting list is the status line's, the count is the pane's.

*Why per thread and not the next activity anywhere.* Lanes run in parallel: while lane A sits on a prompt, lane B keeps stepping, and a run-wide clear would call the prompt answered while the person has not seen it. *Why not the tool call's own result.* A request carries no `tool_use_id`, the module hooks four tools and a prompt can be for any, and a hook pending across the dialog would be a hook holding the person's wait on its own budget. *Why no timer.* A timer would be a threshold, and the module holds none.

*Probe 1 decides the key.* The classic payload's `agent_id` and the engine's `agentId` on `turn.step` are read from different sources; the Claude Code CHANGELOG for 2.1.289 says "one agent id across plugin hook events" (quoted in `research_notes/Interlock mods beyond the ship meter/candidate_mod_catalog.md`, the ecosystem section's CHANGELOG line), and the two ids recorded so far have the same 17-character shape (the settings hook's `agent_id` in `test/fixtures/hooks/permissionrequest.json`, scrubbed shape-preserving; the engine's `agentId` `aed8fcc283e53ec88` recorded in `openspec/changes/archive/2026-10-05-draw-the-ship-run-live/design.md:139`), but they came from different sessions and equality is not proven. If probe 1 shows them equal, the key is as above. If it shows the classic event carrying no `agent_id` for a Workflow agent, or an id the engine's events never carry, every prompt keys on `main`, the clear is the next model request anywhere in the session, the toast reads `lane unknown`, and this decision records that the clear is session-wide on that engine. Either way the kit cases pin the rule as written here, with the key the probe found.

### D3 — What the three places say

*Narrowed by probe 1: the request and denial toasts, the waiting word and the two permission counters are not built. What remains is the pane's `refusals` section with the `guard-denials` line (present only when a guard was counted) and the `launch-guard` line, and the no-run pane's `launch-guard` line.*

- **Toast on a request:** `permission prompt: <tool> · <who>`, where `<who>` is the wave row's `title` when `laneForAgent` joins the thread's agent to a row, `lane unknown` when the event names an agent the rows do not, and `this session` for the main thread. One toast per event, no dedupe: each prompt is a wait the person must end.
- **Toast on a denial:** `auto mode denied <tool> · <who>: <reason>`, the host's `reason` verbatim, or `no reason given`.
- **Status line and spinner suffix:** `shown()` becomes the position, then the quiet word, then the waiting word, joined by ` · `. The waiting word is `prompt waiting since <ISO>` for one entry, `<n> prompts waiting since <ISO>` with the earliest `since` for several, and `prompt waiting, time unknown` (or `<n> prompts waiting, time unknown`) when no entry has a time. The status line is set through the existing redraw path (`$.ui.status(statusText())` while live, then `$.ui.invalidate('ui.render')`); at close, halt and the boundary it is cleared as today.
- **Pane, a bold `refusals` section after `banners`:** keyed `permission-prompts` reading `permission prompts: <n>`; keyed `auto-mode-denials` reading `auto mode denied <n> tool calls` with ` (<tools>)` after it when any tool name was seen, in the close's order of first appearance; one keyed `prompt-waiting-<key>` line per waiting entry reading `waiting: <tool> · <who> · since <ISO>` (or `· time unknown`); keyed `guard-denials` reading `guard denials: <n>` with ` (<guard> <n>, …)` after it, present only when one was seen; keyed `launch-guard`, D5. The no-run pane keeps its one dim line and gains the `launch-guard` line beneath it.

The words `permission prompts` and `auto mode denied … tool calls` are the close banners' words in lower case (`PERMISSION PROMPTS DURING RUN: <n>`, `AUTO MODE DENIED <n> TOOL CALLS (<tools>)`), so a reader matches the pane to the summary by eye. No colour, no cause, no number that is not a count or a time.

### D4 — A settings guard's deny is read off the errored result, by the guard's name

Four `tool.call` hooks read it: the existing `{ tool: 'Bash' }` and `{ tool: 'Workflow' }`, and two new ones, `{ tool: 'Edit' }` and `{ tool: 'Write' }`, the tools the manifest's `Edit|Write` matcher names for `guard-tests` and `guard-tasks` (`.claude-plugin/plugin.json:86-99`). After `const r = await next(e)`, `speakRefusal($, r)` runs: when `r.isError === true`, `r.text` is a string and `guardReason(r.text)` (D6) finds a guard name, the text from that name on is toasted once per distinct text per run through `run.toasted`, `run.guardDenials` counts one more for that guard, and the pane is invalidated. Everything else about `r` is untouched and `r` is returned as it came. An errored result naming no guard, or a result that is not errored, changes nothing and logs nothing: a tool that failed, or another plugin's deny, is not this module's to speak.

Gates. The `Edit` and `Write` hooks and the `Bash` read return `next(e)` at the first line unless `watching()`: the three stage guards deny only while a stage marker is live, which is a live run, and a deny the module's own run does not hold (another session's run in the same root, or a run ended by `/clear`) stays the blocked agent's, as the inertness requirement demands. The `Bash` hook is restructured so a driver line keeps the step read and every other Bash call during a live run gets only the denial read: `if (!session.interactive) return next(e)`; `if (!watching()) return driver ? idleStep(…) : next(e)`; then `next(e)`, the denial read, and the step read for a driver line. The `Workflow` hook reads the denial whenever `session.interactive`, because the settings form's `guard-relaunch` refuses a launch when no run is live by definition; a refusal there reaches the module only when its own branch allowed and the settings form denied (D5 toasts the module's own).

*Why the name and not the shape.* The module sees `text`, not the hook's JSON; the four names are the one token every guard's reason opens with and the one thing the repository pins about those sentences. Anchoring on `\bguard-(tests|tasks|commit|relaunch): ` anywhere in the text, not at its start, tolerates an engine prefix in front of the reason (what the model reads may be wrapped), and the slice from the match drops that prefix so the toast is the guard's sentence.

*Probe 2, answered (2026-10-07, Claude Code 2.1.291): outcome (a), and the design stands.* A `-p` session with a scratch settings plugin denying every `Bash` call with the reason `guard-probe: PROBE-DENY-REACHED — the probe blocks every Bash call.` and a scratch logger mod: the module's `tool.call` hook on `Bash` resolved `{ ref, result, text, isError }` with `isError: true`, `text` `PreToolUse:Bash hook error: guard-probe: PROBE-DENY-REACHED — the probe blocks every Bash call.` and `result` the same text behind `Error: `. The engine puts `PreToolUse:<tool> hook error: ` in front of the reason, which the name-anywhere match was written to tolerate; the `interlockGuard` detail object does not reach `text`. No classic event crossed the module, before or after (probe 1 found none cross at all). The capture is `test/fixtures/mod/tool-call-denied-by-guard.json`, and `test/fixtures/mod/refusals.mjs`'s `denyText(reason, tool)` rebuilds that prefix so the kit's stubs hand the module the text a session would.

*Probe 2 settles the transport.* A scratch plugin whose manifest registers a `PreToolUse` deny on `Bash` with a reason opening `guard-probe: PROBE-DENY-REACHED` (the memory recipe), loaded with a scratch logger mod hooking `tool.call` on `Bash` and `classic.*`, in a `-p` session on 2.1.289 through `scripts/host-probe.mjs --mode headless`, prompted to run `echo hi` once. The logger records the module's `next(e)` result (`isError`, `text` verbatim) and every classic event that fired around it. Three outcomes: (a) `isError: true` with the reason in `text`, as the kit states: the design stands, the captured result is the fixture the kit cases use, and `guardReason` is pinned on its exact text; (b) a `classic.PermissionDenied` fires for the deny: then that event is the transport for guard denials too, D1's denial hook gains the name check, and the two tool hooks on `Edit` and `Write` are not added, which this decision records; (c) neither carries the reason: the guard half shrinks to D5 alone, the delta spec's settings-guard sentences and the guard-denial scenarios are removed before implementation, `HOOKED_EVENTS` moves by the two classic events only, and `docs/13-the-guards.md:25` keeps saying a denial reaches only the blocked agent.

### D5 — The launch guard speaks its own verdict, and the pane shows the rule's current ruling

The toast is one line before the pinned refusal in the `Workflow` hook:

```js
const verdict = decideLaunch(record, now)
if (launch && session.interactive && verdict.reason) $.ui.toast(verdict.reason)
if (launch && verdict.decision === 'deny') return { deny: verdict.reason }
```

The condition reads the verdict's `reason`, which `decideLaunch` sets only on a refusal (`lib/launch-rule.mjs:166,173`: every allow carries `reason: null`), so the toast line spells no `deny`, the pinned line stays the only refusal, `verdict` is still assigned once, and `test/spine/mod-pins.test.mjs` passes unchanged in its refusal pins. The toast carries the rule's own sentence (`guard-relaunch: a ship workflow was already launched …`), the one the model reads as the tool's error text, so the person and the model read the same words. No toast in a non-interactive session: nothing draws there, and the gate keeps the `-p` path at its first line.

The pane line is drawn from the same facts. `drawPane` calls `guardFacts($)`, the existing state and clock read with its existing debug line on failure, and `decideLaunch(record, now)` bound to `ruling`, not `verdict`, because the pin counts assignments to `verdict`; `launchGuardLine(ruling, now)` (D6) then reads `launch guard: next launch allowed` when the ruling allows, `launch guard: next launch refused: <ruling.reason>` when it refuses, and `launch guard: facts unreadable; the next launch is allowed` when `now` is `null`, which `guardFacts` returns only on failure (it returns an empty record and no time, and an empty record allows). The line's verdict is the rule's, over the record the guard's branch would read at that moment; the module adds no judgement. A `ui.render` hook that reads a `$.state` key is redrawn when the key is written (mods-14), so a human prompt that re-arms the launch redraws the line without a call from the module. The line is drawn in the no-run pane too: the guard runs in every session, and "is my next launch allowed" is the question the pane can answer when nothing else is live.

*Why not keep a copy of the ruling in module state.* The record is already the module's, held by the engine under `interlock.ledger`; a second copy would drift from it at every prompt and every reset. *Calls.* `$.state.get` and `$.clock.now` keep their callers (`guardFacts`), so the `calls:` line gains nothing.

## Risks / Trade-offs

- [The classic `agent_id` and the engine's `agentId` differ, so a thread's clear never fires and the waiting word outlives the prompt] → probe 1 reads both from one agent; on a mismatch the key is `main` for every prompt and the clear is the next request anywhere (D2), recorded before implementation. The list is emptied at close, halt and the boundary regardless.
- [A toast per prompt and per denial is noise on a lane that loops on a denied call] → a prompt is one wait each; a guard denial is deduped by text and still counted; an auto-mode denial is one event each, as the close counts it.
- [The pane's count and the close's `PERMISSION PROMPTS DURING RUN` disagree] → they count different things only when another session worked in the root or a prompt crossed outside the module's live window; the pane's standing line already says the close summary and the receipt are the record, and `docs/04` says where they differ.
- [A state and clock read on every pane draw] → two engine calls per draw, throttled by the engine's redraw cap; the same two the guard's branch makes per Workflow call.
- [The reason text reaches `text` wrapped or truncated by the engine] → the match is anchored on the guard's name anywhere in the text and the slice starts there; probe 2 records the exact form, and the fixture pins it.
- [Two more `tool.call` hooks fire on every `Edit` and `Write` in every interactive session] → each returns `next(e)` at its first line unless a run is live, the same cost as the `Bash` hook today.
- [`prompt waiting since` read as a verdict that the run is stuck] → it names the event the host raised and the time it crossed, nothing more; the quiet word beside it is the figure, and the docs say what each means.
- [The sibling mod change lands first and moves the same lines] → serialized; D8 diffs against what it recorded, and the status-line composition is one function (`shown()`) both edit in order.
