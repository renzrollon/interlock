## Goals / Non-Goals

**Goals:**

- One file, written by the hook that already holds every fact, read by the module at each prompt a person submits and recognised as new by its own stamp; nothing is derived on either side that the doctor, the hook or the card did not already say.
- The mark moves to the moment the person sees the note, in the direction that fails loud: an unmarked note is said again.
- The module gains exactly one engine call, no event, no state key, no number (the read rides the `prompt.submit` and `classic.SessionStart` hooks it already has); its inertness outside a run is amended in one sentence, not loosened.
- Every text the band and the two panes draw is pinned on both surfaces under the kit, and every Node-side rule under `node --test`.

**Non-Goals:**

- Deciding anything from the file or the card: no verdict, no staleness word, no button that runs a command, no mark from the module.
- Reading the trajectory, the spill, the manifest, the wave state or the recorder's sidecars with `$.fs.read`; the brief's rejection of a whole-file trajectory read stands.
- Listing or stating directories from the module (`$.fs.list`, `$.fs.exists`): the hook lists in Node and the file carries the result.
- Changing the doctor, its checks, its JSON, its exit code, or the preflight's advisory text.
- Rendering the card anywhere but the pane; the band names it and the command.
- The graph line and the test-profile line the catalog's candidate 3 sketched: the doctor already reports both as checks, and the band reads the doctor's own rows.

## Decisions

### D1 — The file: schema `interlock.preflight/1`, one object, these fields

`lib/preflight-file.mjs` (D7) exports `PREFLIGHT_SCHEMA = 'interlock.preflight/1'`, `PREFLIGHT_FILE = '.claude/ship/preflight.json'` and `buildPreflightReport(input)`, which the hook calls with what it already holds and which returns exactly this shape, every field present, absent facts `null` or `[]` and never omitted:

```
{
  schema: 'interlock.preflight/1',
  writtenAt: <ISO>,                      // the hook's clock at the write
  source: 'startup' | 'resume' | 'clear' | 'compact' | null, // the host's SessionStart event, from the hook's stdin; null when absent or unknown
  root: <absolute working root>,         // process.cwd()
  stateHome: <absolute> | null,          // the doctor's, resolved against root; null when the doctor did not run or parse
  surface: 'main' | 'linked-worktree' | 'lane-worktree' | 'unknown' | null,
  message: <string>,                     // run().message verbatim: the OK line, the failure block, or the could-not-run/parse text
  doctor: {
    ran: <bool>, parsed: <bool>,         // false/false: no stdout; true/false: stdout that is not JSON
    ok: <bool> | null,
    counts: { ok, warn, fail, skip } | null,
    checks: [{ id, status, detail, fix }] // fix null when the check carries none; evidence is not copied
  },
  notes: {
    spoken: [{ runId, change, stage, banner, marked: <bool>, marks: [{ root, marked, reason }] }],
    unreadable: [{ file, reason }]       // the hook's own full-path form: the home's named in full, the root's relative
  },
  cards: {
    listed: [{ path, change, runId, writtenAt }],  // absolute path; writtenAt is the file's mtime as ISO
    archived: <n>,                       // cards whose change has no directory under openspec/changes
    unreadable: [{ path, reason }],
    lookedIn: [<absolute handoff dir>, …] // every directory the listing opened or found absent
  }
}
```

*Why `message` verbatim and `checks` whole.* The band's first line and the pane's text are the hook's and the doctor's words; the module reads them and formats nothing it did not receive. `fix` travels so the pane can show it; `evidence` does not, because no reader draws it and the file is read into the plugin's environment whole. *Why `marks` is a list.* A note in both roots is spoken once and marked in both (the existing requirement); `marked` is true only when every mark landed, and the pane names the root that failed. *Why `writtenAt` on a card is the mtime.* The card carries no time of its own; the stamp has the change and the run. The time is a date on the pane, never compared with anything.

*Alternatives.* Writing the doctor's object as-is with the notes appended: it would put `pluginRoot`, `requiredCommands` and `evidence` into a file the module copies into memory, and the module would then be reading a schema the doctor owns and may change. Two files (preflight, handoff): the module would read twice per session start for one band.

### D2 — The `openspec/` gate and the remove-then-write rule, outcome-class

The hook writes only when `existsSync(join(cwd, 'openspec'))` names a directory. Elsewhere it writes nothing, creates nothing, and its stdout is byte-for-byte today's: the recorder's rule that a plugin hook runs in every repository and must leave the ones it is not for untouched. The gate is the working root's `openspec/`, not the state home's, because the module reads the file from the session's working directory (D5) and a worktree without `openspec/` can start no ship run.

The write is `rmSync(path, { force: true })`, `mkdirSync(dirname, { recursive: true })`, `writeFileSync(path, JSON.stringify(report, null, 2) + '\n')`, in a `try` whose `catch` writes one line to stderr, `interlock preflight: report not written: <path>: <reason>`, and continues to `report(lines)` as before. The remove comes first and unconditionally, so a write that fails leaves no earlier session's file; a `rmSync` that fails is part of the same `try` and the same line. No process is started and `.claude/ship/runs` is not touched. The file is session-shaped working state under `.claude/ship/`, which `.gitignore:30` already ignores.

*Why remove-then-write and not write-to-temp-then-rename.* The file is small and regenerated at every session start; the failure that matters is a stale report drawn as this session's, and removing first rules it out. A rename would also need the temp file cleaned on failure. *Why outcome-class.* The report is a pointer to facts that are in the session's context either way; losing it costs the band, not evidence. That is the resume card's class, stated in `lib/resume-card.mjs:19-24`, and the opposite of the trajectory's.

### D3 — The preflight marks each note it speaks; a failed mark is said in the file and fails toward speaking again

`interruptedLines` becomes `interruptedNotes(cwd, stateHome)` returning `{ lines, spoken, unreadable }`. For each unspoken note it speaks, after pushing the banner, it calls `lib.markSpoken(root, note.runId)` for every root in which that `runId`'s note was found (the existing both-places case: spoken once, marked in both), and records `{ runId, change, stage, banner, marked, marks: [{ root, marked, reason }] }`. The advisory text is unchanged: the banner line as today, and nothing about the mark, because the model has nothing to do with a mark. The failure is recorded in the file (`marked: false` with the reason) and is visible on `/interlock-preflight`; the note stays unspoken on disk, so the next session start and the next `run start` say it again. `markSpoken` is the same function `lib/run.mjs:2295` uses, so the two marks cannot disagree about what a spoken note looks like. The hook's header comment (`:18-19`) is rewritten to say it marks, and why. The mark is not gated on `openspec/`: a note is spoken wherever it is found, and a note spoken is a note marked.

*Why the hook and not the module.* The module never writes (`$.fs.write` is a forbidden token), its `$.state` is emptied at every boundary, and `$.store` is forbidden and machine-wide. The hook runs at the same session start, before the module reads (D5), in Node, with the library already loaded. *Why not keep "marks nothing" and dedupe in the module.* The module would need a key per note that survives `/clear`, which is exactly the state it cannot keep; and a note unspoken on disk is a note `run start` would speak a second time to the same person.

### D4 — `listResumeCards`, with the stamp parsed where it is written

`lib/resume-card.mjs` gains two exports beside `formatResumeCard`:

- `parseResumeCardStamp(line)`: `{ change, runId } | null` from the first line's `<!-- interlock.resume-card/1 change=<c> run=<r> -->`, one regular expression anchored on `RESUME_CARD_SCHEMA`, defined next to `:164` where the stamp is written, so the writer and the reader cannot drift apart without one test failing. `test/spine/resume-card.test.mjs` round-trips `formatResumeCard(...).split('\n')[0]` through it.
- `listResumeCards({ roots, changesDir })`: for each root in `roots` (the state home, then the working root when it differs: the same pair `interruptedNotes` walks, deduplicated through the hook's `sameDirectory`), opens `join(root, HANDOFF_DIR)`; an `ENOENT` is no cards and the directory is still recorded under `lookedIn`; any other error on the directory is one `unreadable` entry naming it. For each `ship-*.md` it reads the first line only (`openSync`, one `readSync` of 512 bytes, `closeSync`, cut at the first newline), parses the stamp, and sorts the card into `listed` when `statSync(join(changesDir, change)).isDirectory()`, into `archived` otherwise; a file whose first line is not a stamp, or that cannot be opened, is `unreadable` with its absolute path and reason. `writtenAt` is `statSync(path).mtime.toISOString()`. The function never throws and returns `{ listed, archived, unreadable, lookedIn }`; `listed` is unsorted (the pane orders at draw, D6). Nothing past the stamp is read, nothing is marked, moved or deleted, and the hook's advisory text does not change on account of a card.

*Why the first line only.* The requirement says the hook reads the stamp and nothing more; a whole-file read of every card at every session start would also be the first step toward a reader that decides from the body. *Why the open-change filter is a directory check.* `openspec/changes/<change>/` exists while a change is open and moves under `archive/<date>-<change>/` when it is archived; no OpenSpec CLI call is needed, and the hook starts no process. *Alternatives.* `$.fs.list` and `$.fs.exists` from the module, as the catalog's candidate 4 sketched: two more calls on the allow-list and a module that states directories; the hook already runs at the same moment in Node.

The hook loads `lib/resume-card.mjs` and `lib/preflight-file.mjs` on demand, as it loads `lib/interrupted.mjs`, so a plugin copy missing a library speaks `halt resume cards could not be listed: <reason>` into `cards.unreadable` and still writes the file. `detachedHook` in `test/hooks.test.mjs` copies `preflight-file.mjs`, `resume-card.mjs` and `limits.mjs` beside the two it copies today.

### D5 — The module reads at each human prompt, and after the classic session-start event where the engine raises one

*Probe 1 (task 1.1(a) and (c), 2026-10-07, 2.1.291, `scripts/host-probe.mjs --mode tty --cwd <this repository>`, a scratch logger mod beside a scratch plugin whose settings `SessionStart` hook writes a marker file).* Startup: `ui.render{AbovePrompt}` once, then `session.start` 36 ms later, both before the settings hook had run (the marker read `ENOENT`); a second `AbovePrompt` render ~190 ms later found the marker only because the stub hook is instant, and nothing reached the module again until the person typed; the first `prompt.submit` (`origin.kind: 'composer'`) found the marker. **No `classic.SessionStart` reached the module**, at startup or at `/clear`. `/clear` ran the settings hook again (a new marker) and raised no `session.start`, no classic event and no `prompt.submit` of its own; the next typed prompt found the new marker. `session.start` carries `cwd`, the working root; `$.fs.read('package.json')` and `$.fs.read(e.cwd + '/package.json')` read the same file. Not probed: a linked-worktree session (the Desktop engine cannot be launched by the harness, and the absolute form below is the primary either way) and `--mode headless` (a `-p` session is non-interactive, so the module reads nothing there by rule 1 below). None of the three outcomes the earlier draft of this decision named held: the primary order, its `session.start` fallback and its first-prompt fallback each assumed an event that would mark a `/clear`, and on this host none does.

So the read moves to the one event that reaches the module after the preflight has run, at startup and after every boundary alike: a prompt the person submits. And a report is recognised as new by its own `writtenAt`, which every session start's preflight rewrites, rather than by an event the module never sees.

1. `session.start` keeps `session.cwd = str(e.cwd)` beside `interactive` and `surface`, and resets `start = freshStart()` (D8).
2. `prompt.submit`, in an interactive session, for an origin in `HUMAN_ORIGINS` (the launch guard's own set), awaits `readPreflight($, session.cwd)` before it passes the prompt on unchanged. Any other origin reads nothing.
3. `classic.SessionStart` keeps its shape for the engine that raises it (the kit, and a later host): a non-interactive session `return next(e)`; the boundary branch as today plus `start = freshStart()`; `const r = await next(e)`; `await readPreflight($, typeof e.cwd === 'string' ? e.cwd : session.cwd)`; `return r`. On 2.1.291 this branch never runs outside the kit, and the docs say so.
4. `readPreflight($, cwd)` reads `$.fs.read(preflightFilePath(cwd))` inside a `try`, passes the text to `readPreflightReport`, and hands the outcome to `adoptPreflight(start, outcome, path)` (D7), which returns the next `start` and whether anything changed: a report with the held one's `writtenAt` and `root` changes nothing; a new report is held with `hidden` kept only when a report was already held and the new one's `source` is `compact`, and `named` cleared; a problem drops a held report (a file the next preflight removed and could not rewrite is no longer this session's) and is named once on the debug log, `interlock meter: no preflight report at <path>: <reason>`, until a report is adopted again. `$.ui.invalidate('ui.render')` only when something changed.

The hook records the session-start `source` from its own stdin event in the file (D1), so a compaction's report keeps the band hidden while a startup, `resume` or `clear` report shows it again (D6).

*Why per human prompt and not once.* It is the only event that crosses the module after the preflight finished, and after a `/clear`. The cost is one `$.fs.read` of a file of a few kilobytes per prompt a person types; a repository with no file costs one rejected read per prompt, named once. *Why only human origins.* A completion wake or a peer's prompt is not a person looking at the band, and the launch guard already draws that line. *What this costs the reader.* The band appears at the first prompt of a session, not before it: the engine raises nothing between the preflight's write and the person's first keystroke. Accepted; the facts are in the session's context from the start, as before this change. *Why `writtenAt` identifies a report.* The hook stamps it at each write and removes the previous file first (D2), so two different session starts never leave the same stamp, and a report re-read at a later prompt is recognised as the one already held, hide flag and all.

### D6 — What the band, the two panes and the Hide control say

**The band** (`on('ui.render', { component: 'AbovePrompt' })`) returns `next(e)` when the session is not interactive, when `e.props.hasSurvey` is true, when `start.hidden` is set, when no report is held, or when `bandLines(report)` is empty. Otherwise it awaits `next(e)` for what the other plugins drew, resolves `Box`, `Text` and `Button`, and returns a column `Box`: one `Text` per line of `bandLines(report)`, a `Button` keyed `hide` labelled `Hide` whose `onPress` sets `start.hidden = true` and calls `$.ui.invalidate('ui.render')`, and the tree from beneath as the last child when it is not null. The whole body sits in a `try`; a failure after `next(e)` returns what `next(e)` gave, one before it returns `next(e)`.

`bandLines(report)` (D7) is empty unless the report carries a check with status `fail` or `warn`, a doctor that did not run or parse, a note in `notes.spoken`, or a card in `cards.listed`; otherwise, in this order:

- `message.split('\n')[0]`;
- `<status> <id>: <detail>` for each check whose status is `fail` or `warn`, in the doctor's order;
- each `notes.spoken[].banner` verbatim;
- `<path> · <change> · run <runId> · written <writtenAt> — /interlock-handoff` for each listed card;
- `preflight written <writtenAt> · /interlock-preflight`.

No colour, no cause, no threshold word, no count the doctor did not print. The band keys its `Text` rows `preflight-<n>` so the kit finds them.

**`/interlock-preflight`** opens `{ id: 'interlock-preflight', title: 'Interlock preflight', closeOnEscape: true }`. Its `ui.render` hook draws, from `preflightPaneLines(report)`: the message verbatim, one row per check (`<status> <id>: <detail>`, then `fix: <first line>` and the continuation lines indented, as the hook prints them in its failure block), the notes spoken at this session start with `marked` or `not marked: <reason>` per root, the listed cards and `<n> card(s) of archived changes not listed`, the directories looked in, and every entry of `notes.unreadable` and `cards.unreadable`. With a problem held instead of a report, the pane says `no preflight report is held for this session start: <path>: <reason>`.

**`/interlock-handoff`** opens `{ id: 'interlock-handoff', title: 'Interlock handoff', closeOnEscape: true }`. Its `ui.render` hook orders `cards.listed` newest `writtenAt` first and, per card, draws the listing line keyed `card-<n>` and then `await $.fs.read(card.path)` inside a `try`: on success, `h(Markdown, { text: clampCard(text, card.path).text })`; on failure, a `Text` line `<path>: cannot be read: <reason>`, and the next card is drawn as before. With a report and no card the pane says `no halt resume card is on disk for an open change` and lists `cards.lookedIn`; with no report it names the preflight file's path. Every card is read at draw time, so a card written after the session start is still the file's listing but the body shown is the file on disk now. No element of either pane carries an `onPress`.

*Why the band carries the card and not a toast.* A toast is gone in seconds and the card is the thing the returning reader must know exists; the band stays until hidden. *Why `Hide` is module state.* The band example keeps it in `$.state`; this module adds no state key (the type contract would need widening) and the boundary that would reset it is the one the module already observes. *Why the meter pane is untouched.* It already says `no ship run is live in this session` with no run, which stays true; the preflight is not the meter's run.

### D7 — The pure module, the published cap and the Markdown clamp

`lib/preflight-file.mjs` is Node-free, imports only `./limits.mjs`, and exports: `PREFLIGHT_SCHEMA`, `PREFLIGHT_FILE`, `preflightFilePath(cwd)` (`cwd` a string: `cwd` with one trailing slash stripped, `/`, `PREFLIGHT_FILE`; else `PREFLIGHT_FILE`), `buildPreflightReport(input)` (D1: coerces every field, defaults every absence), `readPreflightReport(text)` (`{ report } | { problem }`: not a string, not JSON, not an object, or `schema !== PREFLIGHT_SCHEMA`, each named), `shouldDraw(report)`, `bandLines(report)`, `preflightPaneLines(report)`, `noReportText(path, problem)`, `orderCards(report)`, `noCardText(report)`, `clampCard(text, path)`, `freshStart()`, `adoptPreflight(start, outcome, path)` (D5, D8) and `HANDOFF_PANE_CHARS`.

`lib/limits.mjs` gains `handoffPaneChars: 10_000`, with a doc comment saying it is the `Markdown` element's own bound on 2.1.286, printed by `formatLimits` as `handoff pane chars`. `clampCard(text, path, cap = LIMITS.handoffPaneChars)` first replaces every control character other than tab and newline with a space (the element refuses them), then, when the text is longer than `cap`, cuts it so that the text plus `\n\n_… <n> characters left out; the whole card is <path>_` is exactly within `cap`, and returns `{ text, cut: <n> }`; a text within the cap returns `{ text, cut: 0 }`. `test/spine/limits.test.mjs` pins that the cap is printed with its value, that `lib/preflight-file.mjs` reads `LIMITS.handoffPaneChars`, and that `hooks/mod.mjs` contains none of `handoffPaneChars`, `10_000`, `10000`. The cap-authority sweep finds its reader under `lib/` by construction.

*Why the cap equals the element's bound and is not below it.* The number is the engine's; publishing a smaller one would be a second number with no reason behind it. The clamp, not the cap, leaves room for the note. *Why a truncation note inside the text.* The requirement is that the cut is visible where the text is read; a separate `Text` line could scroll apart from it.

### D8 — The module's state, and what resets it

`let start = freshStart()` at module level, `freshStart()` (from `lib/preflight-file.mjs`) returning `{ report: null, path: null, problem: null, hidden: false, named: false }`. ## Risks / Trade-offs

- [The band appears only at the first prompt, not at startup] → probe 1: nothing reaches a module between the preflight's write and the first prompt, nor after a `/clear`. The facts are in the session's context from the start; the band is a second, later place for them.
- [A read per human prompt] → a file of a few kilobytes; a repository with none costs one rejected read per prompt, named once.
- [`$.fs.read` is a whole-file read into the plugin's environment] → the preflight file is one session's report with no evidence arrays; a card is bounded by `LIMITS.resumeCardListRows` per list and the halt reason by 500 characters; neither approaches 4 MiB, and a read over the cap is a rejection the module names.
- [A card over 10,000 characters is cut] → visibly, inside the rendered text, naming the file; the whole card is still on disk at the path the listing line shows.
- [A mark that lands for the preflight but the person never reads the band (a non-interactive session, a host below the mods floor)] → the note is still in the session's context, which is what it was before this change; `run start` still speaks every unspoken note, so a note marked by a `-p` session's preflight is said to that session's model. Accepted: the alternative, marking only on an interactive host, would have the hook read a fact it does not have.
- [A band at every session start in a repository with a standing warning] → `Hide` for the session; the doctor's warning is the thing to fix, and the band says which. The all-ok report draws nothing.
- [The hook grows two more dynamic imports and a directory listing per session start] → one `readdirSync` and one 512-byte read per card; no process, no git.
- [`detachedHook` copies drift from the hook's imports] → the detached cases fail on a missing library the moment an import is added, which is the intended direction; the hook speaks the missing library by name.
- [A kit `world()` without an `fs.read` answer makes every existing meter case read a file] → the module catches the rejection and logs once; probe 2 records whether a deny stub is needed in `meter.test.ts`.

## Migration Plan

None. The file is created by the hook at the next session start and ignored by git; a host below the mods floor writes it and nothing reads it. Rollback is reverting the hook, the module, the pure module and the limits key; a `.claude/ship/preflight.json` left behind is inert. The notes' `spokenAt` field and the card's shape do not change.

- Whether the kit refuses a second `on('fs.read')` beside a first in one test, as it does for `clock.now`; the session-start cases answer every path from one stub keyed by `e.path`, so the question does not change them.
- Whether the Desktop surface draws the band while a Workflow run holds the session; the band is drawn before any launch and is not the meter's, so it does not change the design.
