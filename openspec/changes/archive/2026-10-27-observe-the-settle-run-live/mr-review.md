### ❓ To investigate

- Whether the engine's pane `Text`, `$.ui.status` and `$.ui.toast` pass ESC, CSI or OSC sequences to the terminal, and whether they truncate (M10's real exposure). Probe: `node scripts/host-probe.mjs` with a logger mod that renders `Text('\u001b]52;c;dGVzdA==\u0007x')` and sets a 5,000-character status line.
- Which comes first, stdout or stderr, in an errored Bash result. This decides which wrong row M8 draws. Probe: `printf 'dirty (1):\n  a\n'; echo err >&2; exit 1` through a logger mod on `tool.call` `Bash`.
- Spawn and step order. The settle tally keeps a step only after `meterSpawnForward(input).then(noteSpawn)` has resolved. If the engine resolves that chain after the subagent's first `turn.step`, those steps are dropped (`noteSettleStep` returns `null` for an unknown id).
- A call the engine backgrounds at its own timeout is drawn with `exit 0`, because only `input.run_in_background` is read. An example is `gh pr checks <n> --watch` (`skills/settle/SKILL.md:396`, which passes no background flag). Whether the engine marks such a result was not checked in this repo.
- Four new event-field reads are unverified at the floor engine 2.1.287: Skill `e.args`, `turn.step` input `effort`, spawn input `model` and Bash `run_in_background`. Captures exist only for 2.1.289–2.1.310. A missing spawn `model` is drawn as `inherit`.
- Whether a typed `/interlock:settle --review` also raises `tool.call` on `Skill`. If it does, the run starts twice and logs a spurious replacement line; the spec meter relies on the same assumption.
- The engine's inline output limit for Bash results, which decides how often M1 fires.
