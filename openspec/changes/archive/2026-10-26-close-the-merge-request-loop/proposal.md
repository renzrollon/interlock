## Why

After `/interlock:ship` commits, nothing carries the branch to a merge request whose verdict reflects the review and the fixes that were actually done on it. `/interlock:mr` publishes a verdict but runs no review, posts no findings, fixes nothing and replies to nothing; the review skills review a diff before the merge request exists and write nothing the verdict can read; and three ceilings in the verdict itself hold every change of this repository at `HUMAN` whatever evidence arrives. PR #22 showed the result: three review comments posted by hand-adapted user-level skills, one hand fix commit, two hand-written reply tables citing a commit a later force-push removed, no verdict block and no label.

The owner's question is one sentence: after a ship, does this merge request need a person, or can it merge? Today the honest answer is "a person, always", and the loop that would change that answer is the missing middle of `mr`.

## What Changes

- **`/interlock:mr` gains the loop.** With `--review`, after pushing the branch and creating (as a draft) or updating the merge request, the skill runs the `review-code` pipeline against the merge request's own diff (`origin/<target>...HEAD`), posts the surviving findings as one comment the CLI rendered, runs bounded remediation rounds that commit their fixes, pushes, posts one reply table per review comment that the CLI computed from the re-review on the pushed head, marks the draft ready after the last push, confirms the scenarios and verifies the head with records bound to it, waits for the platform's checks, and assesses the verdict from evidence produced for that head. A round that changed nothing posts every finding as open and ends the loop without a push. The round cap and its stop rule are the ship loop's, read from `interlock limits`; no new number enters prose. The skill stays person-invoked and still never merges, approves, requests changes or resolves a thread.
- **New CLI family `interlock mr`** in its own module, so `bin/interlock` stays under its size pin: `comment` renders the findings comment with stable ids from an adjudicated review; `replies` computes each finding's status (fixed, open, new) by comparing the review before the round with the re-review on the pushed head, under one finding identity both readers share; `remediate-brief` prints the fix-only briefing for one round from the same plan and stop rule the ship loop uses; `conformance-brief` prints the scenario and living-requirement confirmation briefing a run's strict tail would have issued, bound to the head, so a lean ship's merge request can still earn the conformance signals; `test-paths` names which changed files the test guard would protect, over the staged tree, so a round that edited or created a test is reverted and spoken, never committed.
- **`interlock review` gains `--out <file>`, `--head <sha>` and `--dimensions <file>`**, and `review-code` gains `--base <ref>` and `--out <file>` and writes its dimension record, so the adjudicated record lands in a file the verdict reads, names the commit it reviewed, and carries which dimensions ran and which were skipped. `interlock verify judge` gains `--head <sha>`; the handoff gains an optional `head`; `merge-confidence` refuses a review, verification or handoff record bound to another commit.
- **The verdict's risk signal reads touched paths at merge.** `risk.class` no longer reads the change's artifact prose when assessing a merge, and its severity path rules skip documentation and test paths there; a text-only signal cannot fire at merge. The classifier's continuity use, `interlock risk` and the spec-stage checkpoint are unchanged. This resolves ledger decision D1 of `label-and-harden-the-merge-verdict` by aligning the code with the living requirement's own title.
- **A run's evidence file carries its run record to the commits that follow it.** When the head descends from the commit the run made, on the same merge base, `--run` supplies the run record (`run.integrity`) and refuses the tree-bound entries (review, verification, handoff, coverage) with the reason on standard error; an ancestry git cannot decide is refused with its own reason. Any other mismatch still refuses the whole file, and no base is ever taken from it. The loop replaces three of the dropped entries with its own records and the coverage figures only where the profile configures coverage.
- **The block says what `MERGE` is not.** The `--markdown` block carries one legend line in every verdict: `MERGE` means every local signal is green and is not a statement about the platform's branch rules, required approvals, code owners, a draft, unresolved threads or a merge queue.
- **The ship summary names the next step.** A clean completion prints a line naming the push and `/interlock:mr --create --review`, beside the archive reminder.
- **A `blast-radius` review dimension.** An eighth bundled brief for `review-code`: the behaviour changes a diff makes to existing callers, data and concurrency effects, and rollback, enumerated through the graph when one exists and skipped aloud when none does, with the skip carried to the verdict as the `blast-radius-skipped` flag.
- **This repository's `REVIEW.md` gains an `## Always Human Review` list** naming its CI workflow directory, so a merge request that edits CI reads `HUMAN` by policy rather than by accident.
- **Docs, README and CHANGELOG** describe the loop, the new flags and the verdict changes; the three platform recipes and the GitLab reader keep their "not exercised" marking, and the GitLab lines of the loop are marked the same way.

Not in this change: a CI job that re-assesses, an adapter from platform review comments written by people into findings, a live read of the platform's branch rules, resolving review threads, stacked or dependent merge requests, and any change to the strict tail's single-worker review.

## Capabilities

### New Capabilities
- `review/merge-request-loop`: the review, remediation, reply and re-assessment loop `/interlock:mr --review` drives; the `interlock mr` command family that renders its comments, computes reply statuses under one finding identity, briefs a fix round under the ship loop's stop rule and a head-bound conformance confirmation, and names protected test paths over the staged tree; `interlock review --out --head --dimensions`; the evidence the loop hands the verdict and the order it hands it in.
- `review/blast-radius-dimension`: the eighth review dimension: when it runs, what its brief asks, what it reads from the graph, and how its absence is spoken and recorded.

### Modified Capabilities
- `review/merge-confidence`: the risk signal classifies touched paths only at merge, with documentation and test paths outside its severity path rules; a run's evidence file supplies its run record to descendant commits on the same merge base and refuses its tree-bound entries, naming what it kept and what it dropped, and tells an undecided ancestry from a foreign commit; a review, verification or handoff record bound to another commit is refused; the ran signal carries the `blast-radius-skipped` flag; the `--markdown` block carries the legend line.
- `review/merge-request-delivery`: the skill hands the command evidence produced by its own loop for the head under review, beside the run's file, passes coverage only when the loop produced it, and still passes nothing left in the working directory by other means; with `--create` it pushes first and, with `--review`, creates a draft it marks ready after the last push.
- `ship/close-summary`: a clean completion names the merge-request step beside the archive reminder.
