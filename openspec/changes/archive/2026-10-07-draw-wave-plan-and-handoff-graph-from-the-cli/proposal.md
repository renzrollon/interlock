## Why

A ship run already records every node and every edge a diagram would need, and nothing draws any of it. The plan `interlock waves` emits is `waves[] → batches[] → lanes[] → tasks[]` with every fold, deferral and model decision beside it as a named list (`deferred[].after`, `folded[]`, `lanes[]`, `serialized[]`, `clamped[]` — `lib/waves.mjs:1241-1265`, `:1339-1348`); the wave state keeps the cursor, the completed and failed ids, the skipped verifications and the halt (`lib/waves.mjs:2137-2167`, `:2422-2473`); the trajectory under `.claude/ship/runs/` holds the walk in `seq` order, typed `run-start`, `wave-action`, `cli-exit`, `agent-spawn`, `agent-result`, `verify-judgement`, `run-halt`, `run-complete`, `run-receipt` (`lib/run-log.mjs:58-70`, `:415-530`). What a person gets of all that is three line-per-fact text renderers, `formatPlan`, `formatRunState` and `formatRunLog`, and one PNG screenshot of the first of them in `docs/01-first-hour.md`. No Mermaid fence exists in `README.md`, `docs/`, `CHANGELOG.md` or any skill (grep, 2026-10-06), and the README poster's own design prompt says its ship strip is stale (`docs/assets/DESIGN-PROMPT.md:286`). The deep-research report `reports/Interlock mods beyond the ship meter.md` and its note `research_notes/Interlock mods beyond the ship meter/ship_wave_and_handoff_diagrams.md` (key questions 6 and 7) recommend the same thing this change does: draw both diagrams from the records that exist, in a pure renderer the CLI exposes, before any pane does.

The renderer has to be shaped for its second reader before it has one. The sibling change `draw-the-wave-board-in-the-meter-pane` draws the wave board inside the ship meter, and the meter runs in the engine with no Node: `hooks/mod.mjs` imports only `lib/launch-rule.mjs` and `lib/meter-quiet.mjs` (`hooks/mod.mjs:51-52`), and `test/spine/mod-pins.test.mjs` walks that closure and fails on any `node:` specifier or any import outside the plugin (`test/spine/mod-pins.test.mjs:114-140`). `lib/waves.mjs` imports `node:crypto` (`:103`) and `lib/run-log.mjs` imports `node:fs` and `node:path` (`:40-46`), so neither can be the renderer, and the lane naming rule the board must share with the spawn title, the briefing file and the trajectory line — `laneLabel`, `laneTitle` — lives in `lib/waves.mjs:519-546` today. The pane's rows are one `Text` per line with no colour (`hooks/mod.mjs:409-434`), so the board's natural shape is an array of lines at a given width.

Two facts in the records decide the shape and are easy to get wrong. Waves are keyed by position, never by `group`: the real plan on disk holds two waves with `group: 1` (`.claude/ship/plan.json`, waves 0 and 1) and its receipt lists two `wave: 1` rows, because dependency layering emits a later layer under the same section number and the singleton fold keeps it there. And implementer `agent-spawn` records are written by `wave-state next` for every lane of a wave at once (`bin/interlock:1083-1119`), so their `ts` is step-emission time, not when the host started the agent; the one real trajectory on disk (`6e9d0b02…`, 26 records, halted at wave index 1) also predates the `agent-result` recorder, so a handoff graph of it has spawns with no recorded result and must say so rather than draw a lane as finished.

## What Changes

- **Two pure, Node-free renderers under `lib/`.** `lib/draw-plan.mjs` draws the wave board and its Mermaid twin from the plan object `planWaves` emits, plus an optional overlay from the wave state; `lib/draw-run.mjs` draws the handoff graph, as text and as Mermaid, from a trajectory's records in `seq` order, joined to the run's own state and manifest when they name the run. Each returns an array of lines, takes `columns` as a number and reads nothing: no `node:` import, no import outside `lib/`, no file, no environment, no clock. They print facts and the CLI's own recorded words — a task is `ok`, `failed`, `current`, `pending` or `not reached` because the state says so — and compute no verdict, no threshold and no colour.
- **The lane naming rule moves to a Node-free module, written once.** `laneLabel`, `laneTitle`, `laneTier`, `laneModel` and `laneEffort` move from `lib/waves.mjs` to a new `lib/lane.mjs`; `lib/waves.mjs` re-exports them, so every import of them today is unchanged. The board names a lane exactly as its spawn title, its briefing file and its trajectory line do, and a fourth copy of the rule the code says was already written three times (`lib/waves.mjs:513-518`) is not added.
- **The wave board.** One bordered block per wave, keyed by `waveIndex` and labelled with its index, group, kind, batch count and `RED` marker; one row per lane with its batch, label, ids, model, tier, effort, `←dependsOn` ids and, with an overlay, the state word; a verify-gate cell per wave boundary; a `then:` tail. Rows are composed at full length and cut at the width with an ellipsis, the gist last, so the pane's `wrap: 'truncate-end'` and the CLI's cut agree. Below the published minimum width the module returns one spoken line instead of a board.
- **The overlay shows what the state recorded and says what it cannot place.** Task states join by id, the cursor and the verify cells by wave position. A skipped verification is recorded by `group` (`lib/waves.mjs:2443-2473`), so when two passed waves share a group and the records do not cover both, the cell says which the state does not record rather than guessing. A failure whose id names no planned task — the real state holds `task-1.6-verify-settings` — is listed under the board by its wave, never dropped. An overlay whose wave count differs from the plan's is applied by id only and says so. A missing overlay is a plan-only board whose header says `plan only`.
- **The Mermaid plan.** `flowchart LR`, a `%% source: …` comment first, one `subgraph` per wave and per batch of a multi-batch wave, one node per lane, dotted `dependsOn` edges from `deferred[].after`, hexagon verify gates and subroutine commit, verify-final and close gates.
- **The handoff graph.** `flowchart TD` and a text board: ping and implementer nodes labelled by `seq`, `wave-action` edges labelled with their `source`, `cli-exit` durations and exit codes on the ping nodes, the wave-to-wave edge carrying each packet's status and audit verdict from `state.handoffs` and `state.evidenceAudits`, each spawn's briefing sha from the manifest's `dispatched[]`, the halt as its own node, the receipt as the last. A spawn with no `agent-result` reads `result: not recorded`; a source the CLI could not use is named in the header (`state.json: absent`, `run.json: another run`).
- **Exposure through the CLI, exit codes unchanged.** `interlock waves` gains `--format board|mermaid`, `--plan <file>` (render a stored plan instead of planning from `--classified`), `--state <file>` (the overlay) and `--columns <n>`; `interlock run-log show <runId>` gains `--format board|mermaid` and `--columns <n>`. `--format` is exclusive with `--json`, as `report --html` is (`bin/interlock:1912-1915`). Width comes from `--columns`, else `process.stdout.columns`, else a published default; the pure modules never read the terminal. A missing plan, state or trajectory prints a spoken line (`no plan at <path>`) and exits 0, like `run-log show` does today for a run that was never recorded; an unknown format is a usage error.
- **Two published numbers, restated nowhere.** `interlock limits` prints `wave board min width (columns)` and `wave board default width (columns)`, both keys in `lib/limits.mjs`, read by the renderer and the CLI, pinned by `test/spine/limits.test.mjs`.
- **Fixtures from the real run, and tests before code.** The real `.claude/ship/plan.json`, `state.json` and the 26-record trajectory of run `6e9d0b02…` are copied under `test/fixtures/ship/halted-run-6e9d0b02/`, since `.claude/ship/` is gitignored and no test may read the live corpus. `test/spine/draw-plan.test.mjs` and `test/spine/draw-run.test.mjs` cover an empty plan, a single wave, shared group numbers, a missing overlay, titles cut at the width, a width below the minimum, deferred edges, the halt node and a trajectory with no `agent-result`, and pin that neither renderer imports a `node:` module or anything outside the plugin. `test/spine/cli.test.mjs` covers the flags.
- **Docs and the changelog.** `docs/07-cli-and-configuration.md` documents the flags; `docs/10-agentic-workflow-ship-and-spec.md` carries one Mermaid block generated from the fixture plan, pinned by a test that re-renders the fixture and compares the fence body for equality, so the diagram cannot drift as a hand-drawn one would; `docs/assets/DESIGN-PROMPT.md` points at it beside its stale-strip note; `CHANGELOG.md` Unreleased carries the entry; `briefs/claude-code-teams-and-orchestration-briefs.md` gains a dated paragraph under "App ideas, revised" naming this change and its sibling, since no brief asked for a diagram. No Mermaid runtime anywhere: the HTML report's pin against references that resolve to a host (`test/spine/report-html.test.mjs:127-135`) stands, and a diagram in `lib/report-html.mjs` is out of scope.

## Capabilities

### New Capabilities

- `ship/diagrams`: what the CLI draws of a plan and of a run, from which records, and what it never computes. The wave board keyed by wave position with lanes named as their agents are; the overlay that shows only recorded facts and names each attribution the state does not force; the Mermaid plan and the pinned docs block; the handoff graph from the trajectory in `seq` order with its two stated caveats; the purity of the renderers and the two published widths; the CLI flags and their exit codes. Placed under `ship/` beside `run-program`, `halt-resume-card` and `handoff-evidence` rather than under `waves/`, because the board is one of two diagrams of the same run and the sibling change draws it inside the ship meter — the capability is a surface of the run, not of the planner.

### Modified Capabilities

- `ship-run`: the requirement "Session-query over trajectories" gains the drawn forms of `show`: `--format board|mermaid` reports the same records in sequence order, joins the run's own state and manifest only when they name the run, says which source it lacked, and still interprets no new state machine.

`waves` is unchanged: `formatPlan`'s text and the plan object are byte-identical after this change, and the lane rules keep their behaviour while moving file. `hooks/ship-meter` is unchanged here; the sibling change widens the Workflow relay in `lib/run.mjs` and draws in the pane.
