## D11 — detail

Raised 2026-08-28 on the instruction to write a design prompt using three.js / ThreeUI instead of the default design scheme. Written up here rather than settled because either answer is defensible and the wrong one is expensive.

**If exploration only:** nothing changes. `report/html-surface` stands, the shipped file stays hand-emitted inline SVG per D6, and Prompt 4 in `design-prompts.md` is a look-development artefact.

**If the shipping target:** three consequences, none of which this change currently plans for.

1. `report/html-surface` §Requirement: The document is self-contained forbids referencing an external script and requiring a runtime dependency. Raw three.js can satisfy it if vendored and inlined (~600 KB, one inline `<script>`, no network). **ThreeUI cannot** — `@designcodeio/threeui` is a React npm package needing React peer dependencies, and its component source is behind Pro access, so it is unavailable as copy-in source regardless of the spec.
2. `package.json` declares no `dependencies` and the repo has no build step. Vendoring three.js is the project's first bundled dependency and needs its own task, provenance note, and update story.
3. D3 and D5 reason from an instrument aesthetic — the page must not persuade, and absence must not recede. Prompt 4 reconciles those by binding the shader to *coverage* rather than to indicator values, but that reconciliation is a design claim that has not been tested against a rendered comp yet.

Answering it: run Prompt 4, look at the comp, then flip this row in place — class to `agent_resolved`, the answer in `resolution`, `human decision <date>` in `evidence` — and if the answer is "shipping target", amend `report/html-surface`, add a companion decision to D6, and add a vendoring task to `tasks.md`.
