## Context

The spec flow (`skills/spec/SKILL.md`) ends at a human checkpoint after `/interlock:review-artifacts` has passed and `decisions.md` has been audited. Every decision the flow makes is a CLI exit code or a JSON field: `interlock ledger`, `interlock validate`, `interlock gate`, `interlock ready`. Model judgement enters only through reviewers whose output a deterministic gate reads. The spec meter (`hooks/mod.mjs` + `lib/spec-meter.mjs`) draws that flow from the CLI lines that cross the Bash tool, reads no file, and makes no verdict. The eval suite (`evals/`, `test/evals.test.mjs`, `lib/evals-*.mjs`) grades model-facing surfaces with cases the structural test pins by name.

This change adds a model consult to the end of that flow without changing any of those properties: the model is bracketed by two CLI steps that own the caps and the file, the meter learns one more keyed line, and the consult's usefulness is measured by eval cases whose human labels a CLI tallies. It also adds the first committed, plugin-written file outside a change folder (`docs/notes/compound.md`), which is why one decision stays with a person.

The explore brief at `.claude/handoff/explore-add-checkpoint-advisor-20261019-151839.md` is the ground for the decisions below; its rows are carried into `decisions.md` as D1–D19 unrenumbered, and the rows this design added are D20–D29. The artifact review's two blockers (the `specGap` malformed path, the brief cap against the never-cut sections) are resolved in D22 and D27 below.

## Goals / Non-Goals

**Goals**

- One stronger-model, read-only consult after a clean artifact review, whose draft is validated by code and rendered to `openspec/changes/<change>/advisor.md`, and whose absence is written down (D2, D5, D8).
- Every cap, citation check and verdict in `lib/` and visible in `interlock limits`; no threshold in skill prose (D12, D27).
- The spec pane shows what the human is waiting on, from CLI stdout alone (D9, D21).
- Ten eval cases from archived ledgers whose labels feed `interlock advisor --verdict` (D10, D11, D17, D23, D24).
- A compound-notes table derived from `specGap` findings, written non-fatally by both adjudicators, retrieved by path for the brief (D14, D15, D16, D22).
- One judged-type set and a type join in triage, so the first `llm` graders are classified correctly (D13, D25).

**Non-Goals**

- Gating anything on the advisor's output. `interlock ready`, `interlock ledger` and `interlock validate` never read `advisor.md` (D7).
- Bets 4, 5, 7 and 8 of the note; the Wave Note and the Change Desk (D1).
- Running the consult through `claude -p`, the ACP host or the server-side advisor tool (D2).
- A second note format or a second label format; the ledger's table rules and `evals/CALIBRATION-LAYOUT.md` are reused.

## Decisions

### How the consult runs (D2, D3, D4, D20)

The consult is one Agent-tool spawn of a plugin agent, `interlock:advisor`, from `skills/spec/SKILL.md` (D2). The alternatives were rejected in the brief's options table: an inline pass runs on the session model with the review's context and cannot help repeating it; `claude -p` is the metered category the repository does not build on; the host adapters in `lib/host/` serve the ship loop's spawns, not a skill's. The agent's model is declared once, `model: opus` in `agents/advisor.md`, and the skill prose never names a model (D3). Its tools are `Read` only, with `Skill`, `Agent`, `Bash`, `Write`, `Edit` and `mcp__*` disallowed (D4): the brief inlines every artifact, so `Read` is for the one brief path the prompt names, and the agent body says to read nothing else; `test/spine/plugin-agents.test.mjs` requires a non-empty tool list, so an empty list was not an option. The agent's description says only what it is for: spawned by the spec skill's consult step with a brief path, replies with the brief's JSON, not useful without a brief (D29). It does not copy the `Never invoke from a user conversation` clause of `agents/worker.md` and `agents/ping.md`. That clause exists so a model refuses a spawn typed in a session; the advisor's one spawn site is a user-invoked skill whose Agent call is the session's own turn, so a model honouring the clause would refuse the consult every time, the `--failed` path would run on every spec, and `consult-spawned` would read zero on every Spec Range case.

The consult runs only on the clean-gate path (D20). §5 of the skill already halts on a blocker, and a consult after a halt would hand questions to a reviewer who has been told the spec is wrong. The new section sits between the autonomy lines and the hand-off, so the keyed-line order the meter pins is `… autonomy → advisor → checkpoint`.

### The CLI brackets (D5, D8, D12, D21, D26, D27)

`interlock advisor <change> --brief` assembles the brief and writes it under `.claude/metrics/advisor-brief-<change>-<ts>.md`; `interlock advisor <change> --check <draft>` validates the model's JSON and renders `openspec/changes/<change>/advisor.md`, keeping the raw draft at `.claude/metrics/advisor-<change>-<ts>.json` where the skill wrote it (D5). The change folder is the right home because the file is reviewed with the artifacts and travels with the change; `.claude/metrics` is where the flow already keeps per-run evidence nobody commits.

`--check` always exits 0 (D8). A consult is advice; a failed consult is a fact to record, not a reason to stop. `--check --failed "<reason>"` writes the did-not-run stanza, and the skill continues to the hand-off, which says so. The skill never retries and never falls back to drafting in its own prose: a retry would spend a second opus call on a flaky step, and prose questions would be exactly the unmeasured consult this change exists to avoid. When the `--failed` line itself exits non-zero (the change stopped resolving between the gate and the consult) the skill reports that line's first output line as the reason in the hand-off and still continues; nothing else is written, because there is no folder to write into.

The check assigns `Q<n>` and `R<n>` by draft position and ignores any id the model wrote, so a duplicated or missing id cannot collide a pane key or blur the `## Dropped` table. It validates first (a missing field, an unresolvable cite) and caps second, so a bad citation inside the first ten never hides an eleventh good question behind `over cap`; the thirteen-question scenario in the delta spec fixes that order. An empty draft is a drafted consult with no rows; a `questions` or `risks` that is not an array is a consult that did not run, named as such. The stamp in the status line, the brief's path and the draft's path are chosen by `bin/interlock` and passed in: `test/spine/prompts.test.mjs` requires byte-identical output for the same input, so neither the brief assembler nor the renderer reads a clock. The brief itself tolerates a findings file it cannot read (`review findings: unreadable — <reason>`, exit 0) because the consult is worth more than the list of what not to repeat.

The kill criterion lives in `lib/limits.mjs` and is tallied by `interlock advisor --verdict --labels <evals dir>` (D12), reading labels through the same `readLabels` that `interlock evals calibrate` uses. `readLabels` returns one entry per label file and a case may hold several transcripts per grader, so the tally defines its terms rather than assuming one label each: it reads only `spec-range-*` cases and only the `matches-label` and `answered-already` graders; a case is labelled when both graders carry at least one well-formed label; a case's label on a grader is the majority of its files, a tie counting as neither pass nor fail; every other label file in the tree is neither counted nor listed. The verdict is the flag form, not a positional subcommand (D21): the meter classifies `interlock advisor` lines by prefix and takes the change from the second positional word, so `interlock advisor verdict` would have read `verdict` as a change name. With the flag form the reader sees `--` and names no change, and the two steps the meter does read share a `step` field so one reader serves both; any other `step` is shown unparsed.

The risk kinds are a closed enum, `RISK_KINDS` in `lib/advisor.mjs`, with fourteen values lifted from the kinds `docs/02-the-checkpoint.md` tells a human to look for (D26): `scope-expansion`, `unstated-assumption`, `reuse-missed`, `unpinned-dependency`, `error-path-missing`, `single-caller-abstraction`, `decision-without-rationale`, `deferred-work`, `vague-task`, `sibling-left`, `same-file-split`, `untestable-spec`, `function-named-scenario`, `no-failure-path`. The brief prints the list; the check drops anything else by name. A risk says where it lies by `task` (a checkbox id) or by `cite` (an artifact heading, in a question's form), and is dropped only when it names neither or what it names does not resolve: seven of the fourteen kinds (`scope-expansion`, `unstated-assumption`, `reuse-missed`, `decision-without-rationale`, `untestable-spec`, `function-named-scenario`, `no-failure-path`) describe proposal, design or spec defects no checkbox names, so a task-only risk would have dropped half the enum on arrival. The rendered table is `## Risks` with a `where` column for that reason.

The initial cap values are design decisions, recorded here and nowhere in prose (D27): `maxAdvisorQuestions: 10` and `advisorVerdictMinLabels: 10` from the note's "ten labelled specs"; `advisorKeepMinMatches: 3` and `advisorRepeatMaxPercent: 50` from its kill criterion (fewer than three useful of ten, or more than half repeating); `maxAdvisorBriefChars: 160_000`, sized so every Spec Range fixture fits uncut (their four-artifact totals run from 15,936 to 143,632 bytes, and `tasks.md` alone reaches 28,373 bytes for `label-and-harden-the-merge-verdict`), because a cap at the first draft's 24,000 would have cut `design.md` and the specs on eight of the ten fixtures and hidden the artifact most archived `needs_human` rows arose from; `maxAdvisorNoteRows: 20`. The cap still bounds the brief: cuts happen whole-section in a fixed order, the delta specs one file at a time largest first, and when the never-cut sections alone exceed the cap the brief is written anyway with `cap exceeded by <n> chars` under `## Omitted` and `overrun` in the JSON, so a cap that cannot be met is spoken rather than met by cutting the one file the consult must read. The percent is an integer because `test/spine/limits.test.mjs` requires every cap to be one.

### Every spec, not only high risk (D6)

The consult runs on every spec. The note asked whether to gate it on `high`/`critical`; `lib/risk.mjs` floors an unclassifiable change at `high`, and the archived ledger for `label-and-harden-the-merge-verdict` records 58 of 62 archived changes at those classes, so a class gate would run the consult on about 94% of changes while adding a branch and a reason to re-argue the classifier. The cost is one opus call per spec; the kill criterion is how that cost is reviewed.

### The advisor never writes the ledger (D7)

`advisor.md` is advisory. The ledger is the human's record of what needed a person, and `interlock ready` blocks on it; a machine writing `needs_human` rows from a draft would let a model block continuity on taste. A question becomes a decision only when a person writes it into `decisions.md`, and the closing line of `advisor.md` says exactly that. A test pins that the readiness, ledger and validate decisions are identical with and without `advisor.md`.

### The meter (D9, D21)

The pane learns the advisor's rows from the `--check --json` stdout as a keyed line, never from `$.fs.read` (D9): the spec-meter living spec forbids file reads, `test/spine/mod-pins.test.mjs` caps `$.fs.read` at the two the ship meter already uses, and a pane that read `advisor.md` would be the first observer with an opinion about a file. The new lines are `spec-advisor`, one `spec-advisor-q-<id>` per draft question, `spec-consult` from the existing `agent.spawn` hook (no new hooked event), and `spec-waiting`, composed from the check step's `questions` count and the ledger line's `needsHuman`. Those are counts in the CLI's words, not a threshold comparison, which is the line the living spec draws. The draft's Write is counted the way the findings file's is.

### Spec Range (D10, D11, D17, D19, D23, D24)

A fixture is an archived change folder without its `decisions.md` and without any `advisor.md`, plus a `label.md` citing the archived row (D10). The label is the question a human actually had to answer; a fixture that kept the ledger would carry the answer. The ten cases and rows are listed in the `evals/spec-range` delta spec; the `judge-against-base-and-living-specs` ledger reuses the id D3 four times, so its label cites the line number of the first.

Grading is deterministic where it can be and judged where it must (D11): `file_exists` on `advisor.md`, `tool_used` on the one `interlock:advisor` spawn (`arm: with-only`, an indicator the harness excludes from the score, shown against the baseline) and on the `--check` line; then two `llm` graders, `matches-label` and `answered-already`, whose human calibration labels are the kill criterion's data. Only `advisor-written` and `check-ran` can fail a case deterministically; a run that drafted questions in its own prose fails `check-ran`. Both judged graders carry deferral rows until the cases have run; who labels them and when is D19, pending a person, with the recommended default that the repository owner labels after the first pass. Each case sets `runs: 1`, as seven of the eleven existing cases do, so one label per grader per case is the expected shape and the verdict's majority rule is for the day someone raises it.

Fixtures are placed by `context.scaffold_script` under `--scaffold` (D17). The harness documents that each run starts in an empty workspace, that a scaffold script runs before the agent and only under that flag, and that anything inside a case directory belongs to that case; so the fixture lives inside the case directory, `evals/spec-range-<slug>/fixture/`, and the script copies it by its own location (D23), not under a shared `evals/spec-range/fixtures/` as the brief first proposed. The fixture folder is named by the change without the archive's date prefix, so `interlock advisor <change>` resolves it, and holds only the four artifact kinds; `add-report-dashboard`'s archived `design-prompts.md` is left out. Verifying the mechanism live is not an implementer's task: a `claude plugin eval … --scaffold` run needs a live model session, network and money the ship sandbox does not have, so the first live run is the owner's step at the checkpoint, beside D19's labelling, and a scaffold that turns out not to work is a follow-up change rather than a branch inside this one. The cases carry no `smoke` tag, so they run in the scheduled full job, which gains `--scaffold` (D24); the harness also documents that `file_exists` counts only files created during the run, which the CLI-written `advisor.md` is.

### Compound notes (D14, D15, D16, D18, D22)

A note is derived from a surviving finding that carries `specGap: true` (D14). The field is set by the domain and technical-lead briefs only, because those are the two dimensions whose job is to compare the diff against what was promised and planned; the others would mark every surprise. The field is optional and specified in the new `spec/compound-notes` capability rather than as a MODIFIED review spec (D22): `FINDING_SCHEMA` already passes optional fields through `resolveReview`, and the evidence-gate requirement about severity is untouched. A non-boolean value is a new non-blocking entry, `anomalies.specGapShape`, beside `anomalies.requirementCitations` in `resolveReview`, the one place the resolver already reports a shape problem without making a verdict of it. It is deliberately not the bad-severity path: `evaluateGate` drops a malformed-severity finding and fails the gate whenever `malformed` is non-empty, so routing a typo on an advisory field there would have let `specGap: "yes"` block a review, contradicting the rule that no gate reads a note. The gate's `passed`, `blockers` and `malformed` are pinned identical for every value of the field. A row's `rule` is the finding's `suggestion`, else the first sentence of its `description`, stored as-is for a person to reword. The finding shape reviewers are shown, in `lib/prompts/review.mjs` and in `skills/review-code/SKILL.md` §2, lists the field as optional, so a reviewer told to set it has seen it in the reply shape.

The writers are the two places findings are adjudicated: `/interlock:review-code` §4, by a CLI line after the gate, and `lib/run.mjs`'s review adjudication, after it writes the review metrics (D15). Both are non-fatal and spoken, `COMPOUND NOTES NOT WRITTEN: <reason>`, which places the notes with the outcome corpus and review metrics rather than with the trajectory; a lost note costs a future spec a hint, not a run its record. The banner gets a `###` section in docs/04 because the banner ratchet in `test/workflows.test.mjs` admits no new undocumented banner. The commit brief's rule to stage the files the run touched is what stages the table; no staging rule is added, but the committer has to be told the file was touched (D28): `adjudicateReview` returns the appended table's path, the run carries it on the manifest, and `assembleCommitPrompt`'s input names it as a touched file, with the input shape registered in `PROMPTS.commit.inputs` so the registry test sees it. Leaving the committer to infer the append from `git status` would have been unpinned model behaviour.

Retrieval is `specMentionedPaths(tasks.md)` intersected with the `file` column, both through `canonicalizePath`, cut at `maxAdvisorNoteRows` whole rows with the omitted count named (D16). This is the graph-free pattern `lib/spec-coverage.mjs` already uses, and it needs no index. `parseNotes` returns the well-formed rows under `rows` and everything else under `problems` with line numbers, so a malformed row is neither read as a note nor lost; the brief carries the good rows and says how many were unreadable. The table's row helpers are lifted from `lib/ledger.mjs` into `lib/md-table.mjs` so the two sibling formats read a cell the same way.

The table's committed home, `docs/notes/compound.md`, is D18 and stays with a person: it is the first plugin-written file outside a change folder that a repository commits. The tasks implement the recommended default; the path is one constant in `lib/notes.mjs` and the contract file, so a different answer at the checkpoint is a two-line change before the ship.

### One judged-type set (D13, D25)

`lib/evals-types.mjs` exports `JUDGED_GRADER_TYPES`, imported by triage, calibrate and `test/evals.test.mjs` (D13). The set keeps triage's legacy aliases (`judge`, `judged`, `model-judge`, `llm-judge`, `semantic`) beside `llm` and `baseline` so results files and tests written against either spelling keep their classification (D25); the structural test intersects it with the known types to assert that `llm` and `baseline` are the judged ones. Triage joins a trial grader's type by name from the case's grader list in the results, or from a `graderTypes` map its caller passes as a second argument, `triage(results, { graderTypes })`. `bin/interlock` builds that map from each case's `graders/<name>.md` frontmatter under a new `interlock evals triage --eval-dir <dir>` flag, through a reader beside `readLabels` in `lib/evals-calibrate.mjs`, which already walks that tree; `lib/evals-triage.mjs` keeps reading no file and importing nothing but the shared set, and `normalizeCase` carries the case's grader list onto the trials for the join. A grader it could not type is named `type unknown, treated as deterministic`, so a dip is loud rather than filed as variance. `skills/evals/SKILL.md`'s sentence naming `llm` and `baseline` as the two judge-calling types classifies nothing but is a fourth spelling, so the skill suite pins the two tokens beside the set.

### Scope (D1)

Bets 1, 2, 3 and 6 of the note; not 4, 5, 7, 8. The excluded bets touch `lib/run.mjs` lane packing, spawn kinds and CI posture, each a change with its own blast radius. The Wave Note and the Change Desk stay unbuilt because the note gates them on the advisor's verdict.

## Risks / Trade-offs

- **`bin/interlock` is near the directory's 256 KiB file cap** (234 kB of 262 kB). Two subcommands with usage text fit if dispatch stays thin; `test/spine/` already pins the cap over shipped files, so a breach fails the suite rather than the directory scan. Mitigation: every branch of `advisor` and `note` is a one-line call into `lib/`.
- **The eval harness details are documented, not probed.** Whether a scaffold script can locate its case directory, whether the plugin's `bin/` is on the eval sandbox's PATH, and whether `file_exists` counts a file a Bash child wrote are each stated or implied by the harness docs and verified only by the first live `--scaffold` run, which is the owner's step (D17) because it needs a live model session and network the ship sandbox lacks. If any fails, the cases ship unrun behind their deferral rows and a follow-up change carries the fix.
- **Fixture sizes.** The ten fixtures' four-artifact totals run from 15,936 to 143,632 bytes, two of their `tasks.md` alone above 26,000; `maxAdvisorBriefChars` sits above the largest so none is cut, and the overrun line exists for the change that exceeds it anyway.
- **Eval cost.** The full job runs ten cases, each one opus consult inside the harness's `claude -p` child, in two arms under the workflow's existing cost ceiling. A ceiling hit truncates the run and the report says so; the cases carry no `smoke` tag, so no pull request pays it.
- **Opus per spec.** The consult adds one stronger-model call to every spec run. The kill criterion exists to review that cost with data; until ten labels exist the verdict prints `INSUFFICIENT LABELS`, and the consult runs anyway. That is a deliberate order: a consult that never runs produces nothing to label.
- **The `specGap` signal is model-set.** A reviewer may over-mark. Notes are never read by a gate, and the table is a human-editable file, so an over-marked row costs one line of a brief and one deletion.
- **A shared writer.** Two writers append to one committed file. The append skips a row whose change, file and rule are already present, and the ship loop's append is non-fatal; a lane that cannot write it banners and goes on.
- **Risk-classifier keywords.** The artifact prose avoids the tokens `lib/risk.mjs` reads as critical; the class this change receives is read at the checkpoint, not argued here.
