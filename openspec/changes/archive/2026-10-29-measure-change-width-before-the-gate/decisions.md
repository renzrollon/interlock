# Decisions — measure-change-width-before-the-gate

| id | question | class | resolution | evidence |
|----|----------|-------|------------|----------|
| D1 | What values do `maxChangeCapabilities` and `maxChangeTasks` take? | needs_human | — (recommended: 8 capabilities and 32 tasks; design D1 reads them off the archive: 8 sits at the 95th percentile of delta spec files and flags the 2026-10-29 change at 12 while leaving 73 of 75 archived changes within it; 32 tasks sits between the 90th and 95th percentiles and flags five archived changes; the implementation lands these until the owner answers and reports which it used) | 75 archived changes under openspec/changes/archive/: delta spec files p50 2 · p90 6 · p95 7.3, two above 8 (both 13); checkbox tasks p50 14 · p90 29 · p95 41, five above 32; the blocked 2026-10-29 change had 12 delta spec files and 20 tasks (memory `spec-one-artifact-gate-per-run`) |
| D2 | Does the width get a verb of its own or ride on `interlock validate`? | agent_resolved | It rides on `interlock validate`: the spec skill, the spec meter and the inventory smoke already run and read that line, the inspection already holds both counts, and a new verb would cost bytes in `bin/interlock` (245,586 of a 256 KiB limit), a keyed line, a skill line and an inventory row; the `validate` case in `bin/interlock` is unchanged (design D2) | lib/artifacts.mjs:267-345 (`inspectChange` walks `specs/` into `specFiles` and parses `tasks.md`); bin/interlock:3313-3319; lib/spec-meter.mjs:333 (validate reader); memory `plugin-directory-holds` (256 KiB file limit) |
| D3 | May a wide change be not-ready, or exit non-zero? | agent_resolved | No: `ready` is the implementability verdict and a wide change is implementable; `wide` is its own boolean with `over` naming the exceeded caps, and the exit code is unchanged, so `--continue`, the inventory smoke and every exit-code consumer keep their meaning (design D3) | openspec/specs/spec/machine-readable-gate-lines/spec.md (validate line: `ready` is the verdict); skills/spec/continuity.md (`interlock ready` reads the findings file, not the exit code) |
| D4 | When is the width measured, before or after the artifacts are written? | agent_resolved | After, in §4: the inputs are the delta spec files and the task list, which exist only after §3; the explore brief carries no capability list to count; what the check saves is the gate, where the 2026-10-29 cost ran away, and it yields the split material (design D4) | shared/EXPLORE-BRIEF.md (findings, files, options; no capability list); skills/spec/SKILL.md §1b and §4 |
| D5 | What does the spec skill do with a wide change? | agent_resolved | Prints the `CHANGE WIDE:` line verbatim, runs no artifact gate, writes no autonomy line, and stops at the checkpoint with a proposed epic of briefs; `interlock ready` finds no findings file and refuses `--continue`; the owner may still run the gate by hand (design D5) | skills/spec/SKILL.md §5 (one gate per run; blockers stop at the checkpoint); skills/spec/continuity.md (no findings file reads as not ready); memory `spec-one-artifact-gate-per-run` |
| D6 | How does the spec meter show the width without comparing a count? | agent_resolved | It reads `width.wide` and `width.over` as optional fields and appends `WIDE (<over>)` to the status and `wide (<over>)` to the pane from the boolean alone; a record without `width` reads as today, so an older CLI's record stays parsed (design D6) | openspec/specs/hooks/spec-meter/spec.md (the module compares no count to a threshold; a record lacking a named field is unparsed); lib/spec-meter.mjs:495-496, 540-541 |
| D7 | What counts as a capability and as a task? | agent_resolved | A capability is a `spec.md` file under the change's `specs/` at any depth, so a stray note does not count; a task is the checkbox count `ready` already judges, so width and readiness read one parse of one file (design D7) | lib/artifacts.mjs:324 (`walkSpecs` lists every markdown file); lib/artifacts.mjs:176 (`parseTasks`); openspec 1.15.0 requires `specs/<capability>/spec.md` |
| D8 | Who proposes the split, the CLI or the skill? | agent_resolved | The CLI prints the capability directories; the skill groups them into briefs as prose the owner reviews at the checkpoint, naming each brief's capabilities from that list and nothing else; the suite pins the tokens (design D8) | skills/spec/SKILL.md §1b ("One change or an epic") and §6 checkpoint report; test/skills.test.mjs token-pin convention (.claude/CLAUDE.md "assert tokens, not sentences") |
