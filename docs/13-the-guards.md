# 13 — The guards

Interlock's pitch is that its caps and gates are code, not markdown a model can talk past. For a long time that pitch had a hole: every deterministic constraint lived *inside* the workflow (`workflows/ship.js`) or in a skill's prose, and both of those an agent *executes* rather than *obeys*. The moment an agent was holding the Edit tool, nothing outside its own instructions stopped it from editing the wrong file.

Claude Code's declared channel for enforcement outside the agent is the **hook** — a script the *host* runs, in its own process, on every matching tool call. This plugin ships six of them: one that reports at session start, one that records what a ship run cannot see about itself (a session ending mid-run, what each Workflow agent spent and which model served it, each permission event), three that can deny a tool call before it reaches the filesystem, and one that can deny a second ship launch nobody asked for. That last guard has a second form inside the hooks module, which runs first on a host that loads plugin mods ([Two forms, and which is active](#two-forms-and-which-is-active)).

The three stage guards bind **only agents running inside an Interlock ship run.** Outside a run they are inert by construction — see [The fail-open rule](#the-fail-open-rule). The launch guard binds only a session that has already launched ship and has had no human message since. Installing the plugin does not change how your own editing or committing behaves.

## The six hooks

| Hook | Event | What it does |
|---|---|---|
| `hooks/preflight.mjs` | `SessionStart` | Runs `interlock doctor` and surfaces any failing check with its fix, plus any [interrupted-run note](./04-when-it-stops.md#previous-run-interrupted-interrupted-note-unreadable-and-interrupted-note-not-marked) a previous session left, and marks each note it speaks. In an OpenSpec project (a working root with `openspec/`) it also writes this session start's report to `.claude/ship/preflight.json`, with the halt resume cards of open changes it listed from each card's stamp, for the ship meter to draw. Advisory — it reports, it never blocks the session. |
| `hooks/recorder.mjs` | `SessionEnd` | When the session that owns a live ship run ends, writes one note under the state home's `.claude/ship/interrupted/` naming the run, the stage and the session. Reports and never blocks: it returns no decision on any path and exits 0, and in any other session it writes nothing at all. |
| `hooks/recorder.mjs` | `SubagentStart`, matcher `^workflow-subagent$` | Records a Workflow agent of a live run once, under its agent id, in `.claude/ship/agent-usage/<runId>/<agentId>.json`. A later firing for the same agent (the host also fires it on a resume and a teammate message) leaves the file as it is. Reports and never blocks. |
| `hooks/recorder.mjs` | `SubagentStop`, matcher `^workflow-subagent$` | Sums the agent's own transcript into the same file: input, output, cache-read and cache-creation tokens per assistant message, the models that served it, and the briefing sha256 its bootstrap ended on, which `run close` joins to the spawn it dispatched. A transcript it cannot read is left unrecorded, never written as zero. Reports and never blocks: no decision, exit 0, so it can never keep the agent it reports on running. |
| `hooks/recorder.mjs` | `PermissionRequest` | While a run is live, one file per event: the tool name, the agent and the host's reason, never the tool's input. `run close` counts them as `PERMISSION PROMPTS DURING RUN`. Reports and never blocks: it returns no decision, so the prompt is the host's exactly as before. |
| `hooks/recorder.mjs` | `PermissionDenied` | The same, for a tool call auto mode refused, counted as `AUTO MODE DENIED <n> TOOL CALLS`. Reports and never blocks. |
| `hooks/guard-tests.mjs` | `PreToolUse` on `Edit`/`Write` | Denies edits to a **test file** while the run is in `remediation` or `fix-tests`. An agent making a red check green must not be able to weaken the check. A linked worktree has no test profile of its own, so when the working root has none the guard takes its test roots from the profile `run start` recorded as the manifest's `testProfilePath`. A recorded path that cannot be read leaves the guard with no test roots and the suffix rule alone, said on stderr; a manifest without a recorded path, or no manifest at all, allows the edit, as the guard does when no profile names where tests live. |
| `hooks/guard-tasks.mjs` | `PreToolUse` on `Edit`/`Write` | Denies an edit that flips a **checkbox** in the active change's `tasks.md`. The tick is the CLI's job, keyed off recorded outcomes; a hand-edit is never the authority. |
| `hooks/guard-commit.mjs` | `PreToolUse` on `Bash` | Denies a `git commit` unless the run is in the `commit` stage. The deterministic form of the `disable-model-invocation` flag on `skills/commit`. |
| `hooks/guard-relaunch.mjs` | `PreToolUse` and `PostToolUse` on `Workflow`; `UserPromptSubmit`; `UserPromptExpansion` | Denies a **second ship launch** in one session when no human prompt has arrived since the last launch. One script on four events: the `PreToolUse` branch is the only one that can deny, `PostToolUse` records each launch the runtime accepted, and the two prompt events record when a person last spoke. See [The launch ledger](#the-launch-ledger). Only the `/interlock:ship` path reaches it: `bin/interlock-run` refuses the Workflow host, so a runner-host run never calls the Workflow tool. |
| `hooks/mod.mjs` (a hooks module, not a settings hook) | engine events: `session.start`, `prompt.submit`, `session.receive` (a task notification), `tool.call` on `Workflow`, `Bash`, `Skill`, `Edit` and `Write`, `turn.step`, `turn.complete`, `agent.spawn`, `classic.SessionStart` (the session boundary), `ui.render` (`Spinner`, the `AbovePrompt` band, the `interlock-meter`, `interlock-preflight`, `interlock-handoff` and `interlock-spec` `Pane`s), `command.run` (`/interlock-meter`, `/interlock-preflight`, `/interlock-handoff`, `/interlock-spec`) | The **ship meter**, the **spec meter** and the **in-process launch guard**. The meter draws a live ship run in the terminal and the Desktop Code tab: a status line, one toast per degradation banner the moment a step raises it, one toast per settings guard's refusal in the guard's own words, `quiet <n> min` once the run has gone without activity for the published threshold, and `/interlock-meter`, a pane of waves, per-agent figures, the session's context and cost as the engine reports them, plan windows and banners. Outside a run it draws the session start's preflight report on the band above the prompt, with `/interlock-preflight` and `/interlock-handoff`. The spec meter draws an `/interlock:spec` run, with a status line and `/interlock-spec`, from the lines the flow already runs. Neither decides anything. The launch guard's branch of the `Workflow` hook decides one thing, the same thing `guard-relaunch` decides, by the same rule. See [The ship meter](#the-ship-meter) and [Two forms, and which is active](#two-forms-and-which-is-active). |

Each of the four guards, when it denies, returns a machine-readable reason in the host's `PreToolUse` shape — the guard name, the offending path or command, and the current stage, or for the launch guard the session and the times of its last launch and last human prompt — so the blocked agent gets actionable feedback rather than an opaque failure. The launch guard's in-process form returns the same reason, which the engine hands the model as the Workflow tool's error text. On a host that loads the ship meter, a denial also reaches the person: the engine hands the module's tool hooks the blocked call's errored result, its text the guard's reason behind `PreToolUse:<tool> hook error: `, and the meter toasts that reason from the guard's name on, once per distinct text per run, while the blocked agent still receives it as tool-error text. It reads only a result whose text names one of the four guards, so another plugin's denial and a command that failed are not spoken; it does so only while its run is live, except for the launch guard's refusals, which are spoken in any interactive session because a relaunch comes after the run it repeats has closed. Below the mods floor a denial reaches only the blocked agent.

Why these three? Each is a failure mode this repository has already paid for. An agent whose job is to make a red check green can edit the test that defines the check. Tick fidelity was wrong enough to warrant its own shipped change (`2026-08-25-tick-tasks-from-recorded-outcomes`) — that removed the *incentive* to hand-tick, this removes the *capability*. And "don't commit outside the commit stage" lived only as prose. The guards are defense-in-depth *alongside* the existing flags, not a replacement for them.

The fourth guard covers the most expensive mistake on record. A parent chat called Workflow again over leftover checkboxes, and that cost another 20+ agents including a full review cycle. `skills/ship/SKILL.md` forbids it, `test/skills.test.mjs` pins the sentence, and `evals/trampoline-launch` measures whether the model obeys. None of that stops a model that does not. The guard's deny quotes the skill's sentence and names the remedy: send a new message asking to ship the leftovers, or type `/interlock:ship` again.

The recorder covers a different hole: what a run cannot see about itself. A Workflow script's `agent()` returns the agent's result and nothing else — no token usage, no served model, no word of a permission prompt — and a session that ends mid-run takes the run with it before its close. One file dispatches on all five events, so a new reporting branch joins it rather than adding a second recorder. The two subagent entries match `^workflow-subagent$`, anchored, because that is the type the host reports for every agent a Workflow script spawns, whatever `type` the script named; a plugin type such as `interlock:worker` reaches a subagent event only as an internal agent of a `claude --agent` session, and the branch checks the type again so that such an agent writes nothing. The permission entries have no matcher. The recorder writes down what the host said and nothing more: the join, the banners and every verdict belong to `run close` ([04](./04-when-it-stops.md#cache-accounting-partial-agent-usage-unjoined-and-agent-usage-unreadable)).

## The ship meter

`hooks/hooks.json` names one **hooks module**, `hooks/mod.mjs`, which Claude Code 2.1.287 and later load inside the engine itself: no Node, no filesystem, and `$` as its only way out. The file is `{ "hooks": {}, "modules": ["./mod.mjs"] }`. The empty `hooks` record is for older hosts, which read `hooks/hooks.json` as their settings-hooks file and refuse it without one (Claude Code 2.1.161 does). Every settings hook in the table above stays in `.claude-plugin/plugin.json`; on a host that cannot load mods they run exactly as before, and the module is never loaded.

What it hooks, and why each one observes:

- **`session.start`** registers `/interlock-meter`, `/interlock-preflight`, `/interlock-handoff` and `/interlock-spec`, records whether the session is interactive and which surface it draws on, and logs once which engine it loaded in. In a non-interactive session (`-p`, the SDK, a runner lane) every other hook returns at its first line for the life of the module.
- **`tool.call` on `Workflow`** first runs the launch guard's branch, in every session ([below](#two-forms-and-which-is-active)). Then it lets the call run and, when it launched the plugin's own ship workflow (`workflows/ship.js`, `interlock:ship`, or a resume of a run this session recorded), marks the run live and keeps the result's run id. In an interactive session it toasts the launch guard's own refusal in the rule's words, and a refusal from `guard-relaunch` read off the result, whether or not a run is live. It opens the pane unasked, which the engine seats only in a wide terminal; if it declines, one toast names `/interlock-meter`. Then it starts the module's one timer, the host's own interval (`$.clock.every`) at the period `interlock limits` prints as `meter tick (ms)`, which recomputes how long the run has been quiet and draws `quiet <n> min` from `meter quiet after (ms)` on. It ends at the close, a halt and the session boundary below.
- **`tool.call` on `Bash`**, while a run is live and the command begins `interlock `, lets the call run and reads the CLI's own stdout off the result as a step record: action, wave, batch position where the step carries one, spawns, banners. From the same records it keeps what the wave board draws: the plan summary the adoption and replan steps carry (the latest replaces any earlier), the ids each recorded batch names as ok, failed and not attempted, each skipped verification with its reason and wave position, where the run is, and the halt. A `plan` or `recorded` of the wrong shape is named once on the debug log and ignored, and the rest of the step applies. Every other Bash call during a live run is read for one thing only: an errored result whose text names a guard (`guard-commit`), which is toasted and counted as below. A result that is not a step changes nothing and leaves one debug-log line.
- **`tool.call` on `Edit` and `Write`**, the tools the manifest's `Edit|Write` matcher names for `guard-tests` and `guard-tasks`, return at their first line unless a run is live. During a run each lets the call run and reads its result: when it is errored and its text names one of the four guards, the text from the guard's name on is toasted once per distinct text per run and counted on the pane's `guard denials:` line by guard. Anything else (a clean result, another plugin's denial, a failed edit) changes nothing and logs nothing. The tool's input is never read or shown, and every result is returned as it came.
- **`turn.step`, `turn.complete`, `agent.spawn`** tally each agent's requests, tokens and served models, keep its turn's reason and duration, and, where the host raises the spawn event, join the agent to its lane by briefing hash. When a run agent's turn ends with any reason other than `answer`, `turn.complete` raises one toast per agent per run: the lane's title or `lane unknown`, the agent id, and the reason word as the host sent it. It reads the reason word alone, not `isAborted`, a refusal's category or the turn's usage, and names no cause. The event is passed on as it came. Display only: a request with no usage marks the tally partial and never reads as zero, and the meter makes no substitution verdict (that is `run close`'s). With each step on the `Bash` hook, they are also what the quiet figure counts as activity: a run agent's request starting and its answer arriving, its turn ending, a spawn. Each is stamped from the engine's clock; a read that fails leaves the stamp as it was and the word absent, and is named once per run on the debug log.
- **`classic.SessionStart`** with source `clear`, `resume` or `fork` (`/clear`, `/resume`, `/branch`) ends the run the meter holds, before the settings hooks beneath run: it cancels the interval, starts a fresh run record, clears the status line and redraws the pane to its no-run text. `session.start` does not fire at that boundary; this event does, and it is the one on which the engine empties the session's state, so the launch guard's record (`interlock.ledger`) resets on the same event and the two stay in step. A `compact` source is not a boundary: a compaction keeps the session, its tasks and its state, so the run is still the session's run. `startup`, a missing source and one the module cannot read change nothing, and the event is passed on as it came. The pane is not closed (there is no call to close it): it says no run is live, which is true, and Escape dismisses it. The first step from the earlier run to cross afterwards is named once on the debug log and otherwise ignored. After the settings hooks beneath have run, the event also reads the preflight's report, for every source. The engine's test kit raises this event; Claude Code 2.1.291 raises no classic event to a hooks module, at startup or at `/clear`, so in a real session the boundary reset does not run there, and the report is read at the next prompt instead.
- **`ui.render` on `Spinner`** adds the step, the wave and the quiet word to the spinner; **on the `Pane`** it draws the meter, including the wave board, which is `lib/draw-plan.mjs`'s board laid out as one card per wave from the steps' plan summary. The module reads no file for it: not the plan, not the wave state, not the trajectory. The pane also carries two session lines: the context fill and the session's cost, read from the same plain `$.session.usage()` call the plan windows come from (never with a breakdown, which is not free), shown as the engine answered them and said to be absent where it did not. **`command.run`** opens it.
- **`prompt.submit`** and **`session.receive`** belong to the launch guard: the first records when a person last spoke, the second names a relayed task notification on the debug log. Both pass what they receive on unchanged. A person's prompt in an interactive session also reads the preflight's report (below), because it is the one event that reaches a module after the preflight has written it, at startup and after a `/clear` alike.
- **`ui.render` on `AbovePrompt`**, and on the `interlock-preflight` and `interlock-handoff` `Pane`s, draw the session start's report; **`command.run`** opens each pane.

**Outside a run: the session start's report.** Besides the spec meter (below), the module draws exactly two things with no live run, both from the file `hooks/preflight.mjs` writes in an OpenSpec project, `.claude/ship/preflight.json` (schema `interlock.preflight/1`). When the report carries a `fail` or `warn` check, a doctor that did not run or could not be parsed, an interrupted-run note spoken at that session start, or a halt resume card, the band above the prompt shows the preflight's first line, each such check as `<status> <id>: <detail>`, each note's banner, each card's path with its change, run id, written time and `/interlock-handoff`, and the time the report was written with `/interlock-preflight`. A **Hide** control collapses it until a later session start's report (a compaction's keeps it hidden); it keeps other plugins' band content beneath its own and yields while a survey holds the band. An all-ok report draws nothing. `/interlock-preflight` opens the whole report: the message, every check with its fix lines, the notes with whether each mark landed, the cards, the count of cards for archived changes, and every note and card the hook could not read. `/interlock-handoff` renders each listed card, newest first, through `Markdown`, read from its path when the pane is drawn and cut to `handoff pane chars` from `interlock limits` with a line saying what was left out. The report is read at each prompt you submit (and when either command is typed), and recognised by its own written time, so the band appears at the first prompt of a session, not before it: nothing reaches a module between the preflight's write and that prompt. That is why `$.fs.read` is on the module's allow-list: for that one file and for a card it names, and for nothing else, never a run's trajectory, manifest, wave state or spill. `$.fs.list`, `$.fs.exists` and `$.fs.write` stay forbidden: the hook lists the cards and checks the directories in Node, and the module writes nothing. A file that is absent, unreadable or not a report draws nothing and is named once on the debug log; in a repository with no OpenSpec project there is no file, and the module draws nothing.

**The spec meter.** The same module draws an `/interlock:spec` run, from what already crosses it. The run starts when the spec skill is loaded in an interactive session: `prompt.submit` reads the first word of a submitted prompt (`/interlock:spec`) and **`tool.call` on `Skill`** reads the skill a Skill call names. Both pass the prompt and the call on unchanged, with no text of their own. The briefs reject rewriting a skill's prompt, and the engine raised no `skill.prompt` event for a plugin skill on 2.1.291, so that event is not hooked. While the spec run is live, the `Bash` hook also reads the results of the flow's keyed `openspec` and `interlock` lines, by the fields each line's JSON carries. The `Edit` and `Write` hooks count writes by path under the change's directory, the explore brief and the findings file, and never read the input or set a status. `agent.spawn` counts `Explore` investigators. It calls nothing new, reads no file, writes nothing, and keeps no session state: its record is module state, ended at the checkpoint, at an accepted ship launch (judged by the launch rule the guard uses) and at the session boundary. The module owns one status line, written by one composer, with the ship position first, then the spec line. Every rule and word is `lib/spec-meter.mjs`'s, a pure module the import walk covers. `test/spine/mod-pins.test.mjs` pins one `$.ui.status(` call, the two observers building no text, no `skill.prompt` hook, and no `complete` spelled by the module or its rules. `test/spine/spec-meter.test.mjs` pins every fenced `openspec`/`interlock` line in the three skills to the classifier. [07](./07-cli-and-configuration.md#the-spec-meter-interlock-spec) has what it shows.

Apart from the launch guard's one refusal, it returns no deny, no substitute result and no catch handler, and calls no model, prompt, message, process, network, file write or permission check. Its one timer is the host's interval, started for a live run and cancelled with it; a sleep inside a hook, which the engine charges to that hook's own budget, is a forbidden token. `test/spine/mod-pins.test.mjs` reads the module as text and fails on any engine call outside the fourteen it may make (the meter's ten, the interval among them, the launch guard's clock, which the meter reads too, and its state read and write, and the one file read, `$.fs.read`), on a module that spells more than two file reads or names a trajectory, manifest, wave-state or spill path, on any forbidden token, on a deny that is not the launch rule's verdict, on a guard name `lib/meter-refusals.mjs` reads that the four guard scripts do not print, and on a session-state key `types/index.d.ts` does not declare; `claude plugin validate . --strict` lists the same hooks, calls and state keys; `test/mod/meter.test.ts`, `test/mod/relaunch.test.ts` and `test/mod/session-start.test.ts` exercise it under `claude plugin test`, the meter, the band and the two panes on both surfaces.

Where the engine reports a problem: a hook that throws or overruns its budget is **skipped** and the chain runs as if it were not there. While a session hot-reloads a plugin folder (a `--plugin-dir` session), the transcript shows one dim line naming the plugin, the event and the reason; in any other session that line goes to the debug log (`claude --debug`). A pane tree a surface cannot draw is **refused**: the engine draws its own and logs `ui.render (Pane) refused: <reason>` the same way. Neither ever fails the run: the meter is a view of records the CLI already keeps, and the close summary and the receipt are the record.

## The launch ledger

The launch guard cannot read the stage marker: the mistake it bounds happens *after* `run close` has cleared it. So it keeps its own record, one small file per session at `.claude/ship/launch-ledger/<session_id>.json`. The file holds the ship launches the runtime accepted (time, `taskId`, `runId`, workflow name, persisted script path) and the time of the last human prompt. `lib/launch-ledger.mjs` owns the file. The rule (what a ship launch is, what a human prompt is, the decision and its words) is `lib/launch-rule.mjs`, which imports nothing from Node; the ledger module re-exports it unchanged and the in-process form imports it directly, so one function decides in both forms. The hook is plumbing over them, the way the stage guards are plumbing over `lib/ship-stage.mjs`.

- **Only an accepted launch creates it.** The `PostToolUse` branch writes it, and only for a response whose `status` says the workflow launched. A launch the runtime refused never counts against the next one. In practice a refused launch never reaches the hook at all: the engine rejects an unknown workflow before `PreToolUse` runs.
- **A prompt never creates it.** The prompt branches make one existence check and stop when the session has no ledger. Every plugin hook runs on every prompt in every repository, so a prompt in a repository that never shipped writes nothing.
- **The completion wake is not a person.** When a background workflow finishes, the host wakes the session by firing `UserPromptSubmit` with the task notification as the prompt. That is the turn in which a relaunch happens, so a prompt beginning `<task-notification>` is not counted. Without that exclusion the wake would reset the clock and the guard would allow the very call it exists to deny.
- **A resume is a launch.** The completion wake's own diagnostics suggest passing the persisted script back with `resumeFromRunId`. That call names neither `workflows/ship.js` nor `interlock:ship`, so the guard matches it against the run id and script path the session's ledger recorded.
- **Its lifetime is a published cap.** A ledger whose newest launch is older than `launch ledger max age (ms)` in `interlock limits` reads as absent, and every launch write sweeps sibling ledgers past it. Ageing out only ever turns a deny into an allow. Deleting the directory resets the guard.

What it does not do:

- **It does not judge the prompt.** Any human prompt re-arms one launch. Whether the message "explicitly asks to ship leftover tasks" stays with the prose and the eval.
- **It does not close the queued-prompt hole.** A message you type and queue while the run is in flight is a human prompt, recorded before the completion wake. A relaunch after that wake passes the guard. The guard bounds the case that cost twenty agents, a relaunch with no human message at all between the run and the next launch, and nothing wider. Any other machine-originated prompt it does not recognise, a loop or cron firing for instance, also re-arms a launch, which errs toward allow.
- **It does nothing with hooks disabled.** With hooks off (`disableAllHooks`, or a policy that admits only managed hooks), enforcement falls back to the skill's prose and `evals/trampoline-launch`. That is the state before this guard existed.


### Two forms, and which is active

The launch guard ships in two forms, over one rule.

- **The settings form** is `hooks/guard-relaunch.mjs`, registered four times in `.claude-plugin/plugin.json`, with the file ledger above. It runs wherever the plugin's settings hooks run. It is the only enforcement on a host below Claude Code 2.1.287, which cannot load plugin mods, and wherever user mods are stopped while settings hooks still run: an organisation's `allowManagedModsOnly` policy, and possibly `--safe-mode` or `--bare`. `interlock doctor`'s `mods` row says which side of the mods floor the `claude` it probed is on. The engine behind a Desktop Code tab is a different binary, and the meter logs the engine it loaded in at session start.
- **The in-process form** is the launch guard's branch of `hooks/mod.mjs`'s `Workflow` hook, on a host that loads the module. It reads the origin the engine stamps on every prompt instead of a prompt's text: `composer` (your own Enter, typed or queued), `bridge` (Remote Control) and `sdk` (a `claude -p` or Agent SDK turn) are a person; a background task's notification, a scheduled trigger, a peer session, a channel, a coordinator, an observer, a plugin's own prompt and a prompt with no origin are not, and each of those leaves one debug-log line naming its kind. The completion wake arrives that way, as a prompt whose origin is `task-notification`, and not through `session.receive` (captured on 2.1.289). Its record is the session's own state, the key `interlock.ledger` declared in `types/index.d.ts`, in the file ledger's shape: it survives a reload of the module, `/clear`, `/resume` and `/branch` empty it (so the next launch is allowed), and it is never read from or written to the machine-wide store. It writes no file. A `claude -p "/interlock:ship <change>"` run has one `sdk` prompt and then a launch, so a second launch in the same run is refused as in a terminal.

**Precedence.** On a host that loads the module, the engine runs its `tool.call` hook before the plugins' `PreToolUse` settings hooks. Its refusal ends the call: `guard-relaunch.mjs` never starts, no workflow starts, and the model receives one reason, not two, in the same words. Its allow falls through, and the settings hook decides from its own file ledger as it does on an older host.

**The pane shows the next launch's ruling.** The meter's pane carries a `launch guard:` line in its `refusals` section: `next launch allowed`, `next launch refused: <the rule's reason>`, or `facts unreadable; the next launch is allowed` when the session's record or the clock cannot be read. It is the rule's current ruling over the session's record, read the same way the `Workflow` hook reads it, so it changes when a launch is accepted and when you next send a message. The line is drawn in the no-run pane too, since the guard runs in every session. It describes the in-process form only: below the mods floor there is no pane, and the settings form decides from its file ledger.

**The one way they read differently.** The settings form counts every `UserPromptSubmit` whose text does not begin with `<task-notification>` as a person, so a peer's message, a `SendMessage` delivery, a scheduled trigger or a channel message re-arms it. The in-process form counts none of them. On a host that loads the module the stricter reading decides first, so it is the effective rule there; below the mods floor the settings reading stands. Both agree on the completion wake and on every prompt you type.

**The hole is shared.** A prompt typed and queued during the run still re-arms one launch, and that hole is named, not closed, in both forms: the engine stamps a queued prompt `composer` exactly as it stamps one typed at an idle prompt.

**Retiring the settings registrations waits on the plugin's version floor.** The four registrations stay until the floor the plugin documents reaches the mods floor. Removing them sooner would leave every older host, a Desktop engine below 2.1.287 included, with the prose alone. That is not this change.

## The stage marker

A hook is **stateless**. It shares no memory with `workflows/ship.js`, it is spawned per tool call, and environment variables do not survive across the separate subagent processes the workflow spawns. So a guard cannot ask the workflow "what stage are we in" — the only channel that reliably spans the run process and the hook process is the filesystem.

So the run *publishes* its stage, and the guard *reads* it. `lib/ship-stage.mjs` owns the marker:

```json
{ "stage": "remediation", "change": "add-foo", "index": 7, "pid": 12345 }
```

- **`stage`** — one of `implement`, `verify`, `review`, `remediation`, `fix-tests`, `commit`. A value outside that set reads as `unknown`.
- **`change`** — the change being shipped; the marker lives at `.claude/ship/<change>/stage.json`.
- **`index`** — a monotonically increasing write counter for this run, so a caller that knows the current run's count can reject a marker an abandoned run left behind.
- **`pid`** — the process that published the marker. A guard that finds no live process for `pid` treats the marker as orphaned. `pid` is a *hint* (pids recycle), backstopped by `index`; neither is trusted alone.

### Lifecycle

The **agent performing each step** writes the marker as it enters that stage — `implement` on the wave loop's lane briefings, `review` before the review fan-out, `remediation` before each fix round, `fix-tests` before the final verify (which repairs a red suite by root cause, exactly when weakening a test is the hazard), and `commit` before the commit step, which is the one stage `guard-commit` lets a commit through. The writer is the agent rather than a driver because the marker's `pid` has to belong to a process that is alive for the run.

`run close` in `lib/run.mjs` **clears** it, on every terminal path — commit, halt, apply-only, no-commit. The program routes a halt through `run close --halt` and both drivers' `stop()` call it, so a completion and a halt clear the same way. Without that clear, a completed run leaves `stage: "commit"` behind and `guard-tasks` denies every `tasks.md` checkbox edit for the rest of the session; a halt leaves `remediation` or `fix-tests` and `guard-tests` denies every test-file edit. A clear that fails is spoken as a degradation banner, never as an exit code.

No driver carries the marker's path or JSON shape. `lib/prompts/stage.mjs` renders the publish fragment from `lib/ship-stage.mjs`'s own `stagePath`, `MARKER_FIELDS` and `STAGES`, so there is exactly one definition; `test/spine/ship-stage-drift.test.mjs` fails if any driver declares a marker literal at all.

A marker write that fails is a **non-fatal warning** on the run's trajectory, surfaced through the same banner channel every other run warning uses. The run continues: the marker is a guard input, not a gate the run itself depends on.

## The fail-open rule

When a guard cannot determine the stage — marker absent, unreadable, malformed, stale, or the process gone — the edit guards **allow** the tool call.

This is deliberate, and it is the asymmetry to be honest about. A guard that blocked test edits whenever it could not find a marker would break ordinary TDD the moment the plugin is installed — a cost strictly larger than the guard's benefit, which exists *only* during a run's remediation window. Fail-open means a **lost or stale marker during a real run** silently disables the guard for that window; the alternative (fail-closed) would, on the same lost marker, brick every edit in the session, which is a larger and louder harm with no upside.

| guard | marker absent / stale / unreadable | why |
|---|---|---|
| `guard-tests` | **allow** | The hazard (weakening a check) exists only during remediation, which requires a present, fresh `remediation`/`fix-tests` marker to trigger the deny. |
| `guard-tasks` | **allow** | A missing marker is not an active run; hand-ticking outside a run is the human's own business. |
| `guard-commit` | **allow** | Its job is to bound in-run agents, not the human's shell. Outside a run there is nothing to protect. |
| `guard-relaunch` | **allow** on every unknown: no session id or an unsafe one, a ledger absent, unreadable, malformed or past its published age, a tool input it does not recognise as a ship launch, its own crash | It reads the ledger, not the stage marker. A false deny costs one typed message, and that is still a denial, so a ledger it cannot trust never produces one. An unreadable ledger is named on stderr. |
| launch guard, in process (`hooks/mod.mjs`) | **allow** on every unknown: session state or a clock it cannot read, a record that is not one, a launch past its published age, an origin it does not know (which counts as no person, so it can only keep an earlier launch counted), a cleared session, a hook that throws (the engine skips it and runs the chain) | Its allow falls through to `guard-relaunch`, which decides from its own ledger. A record it cannot read, or a launch or prompt it cannot record, is named on the debug log. |

The staleness check (`index` + `pid`) narrows the window in which a leftover marker from a killed run could spuriously block an edit in a later session; it does not close it, and the fail-open default is what makes that residual window safe rather than harmful. A guard that hits an unexpected error while evaluating a call exits in the allow direction too, with a diagnostic on stderr — a protocol mismatch or a bug degrades the guard to inert, never to a wedged session.

The recorder is not a guard and has no row in that table: it decides nothing, so there is nothing for it to fail open *to*. Its rule is narrower. Every branch writes only when a live stage marker exists and the run manifest names that marker's change and carries a run id. `SessionEnd` also needs the manifest to name the session that is ending, and the two subagent branches need the agent type to be exactly `workflow-subagent`. In every other case — no marker, an orphaned marker, a manifest without a run id, another session ending, a runner run with no session, an internal agent, its own crash — it creates no file and no directory. Every plugin hook runs in every session in every repository, so a recorder that wrote on a guess would leave files in repositories that never ran Interlock. It starts no process and runs no git: one directory create and one write per record.

### Two corpus classes, side by side on purpose

The interrupted-run note is **outcome-class**: a note that cannot be written is a line on the hook's stderr, an unreadable note is a manifest note, and neither ever moves an exit code. The run trajectory under `.claude/ship/runs` is the opposite, **fatal-class**: a failed append exits 1, because a run nobody can reconstruct defeats the reason the file exists. The difference is deliberate. The note points at records written elsewhere — the trajectory, `tasks.md`, the plan. The trajectory *is* the record. Do not make the two consistent: a fatal note would stop a session from ending cleanly over bookkeeping, and an outcome-class trajectory would let a run go unrecorded without a word. No hook ever writes the trajectory, and the recorder is no exception.

The agent-usage sidecar is outcome-class too. It is one small file per agent, and one per permission event, under the working root's `.claude/ship/agent-usage/<runId>/`, each written whole rather than appended to a log, so a writer that can only replace a file could write the same records and the join would not change. A file the hook cannot write is a line on its stderr; a file the close cannot read is named in the run's notes as `AGENT USAGE UNREADABLE`; neither moves an exit code. What a missing file costs is spoken instead: its wave's cache figures become unknown and the close banners `CACHE ACCOUNTING PARTIAL`. The `agent-result` events the close derives from the sidecar are trajectory lines, so `run close` writes them, in the fatal class, like every other line in that file.

Where each lives is split by kind as well. The note goes to the state home with the trajectory — the main checkout, for a run in a linked worktree — because the next `run start`, the preflight and `interlock report` look for it there. The sidecar stays in the working root beside the run manifest, because the close that reads it runs in the same root. The recorder takes the state home from the run manifest, where `run start` recorded it, and never runs git to find it: a hook that ran version control on every event in every session would be a cost every session paid, run or no run.

No new dependencies: the settings hooks are Node ESM scripts using only `node:` built-ins, matching the rest of `lib/`. The hooks module imports nothing that reaches `node:`; the only bare specifier it may name is the engine's own `claude-code`.
